# 並列改善ラウンド

3 つの改善ループを**同時に**走らせ、出てきた PR を**その場で審査して取り込む**。
1 ラウンド = 「3 つ並行で改善 → まとめてレビュー → マージ」。

`/improve` が 1 回 1 ループなのに対し、こちらは 1 ラウンドで 3 ループぶん進む。
そのぶんトークンを多く使い、衝突も起きやすい。**衝突の解決はこのスキルの主な仕事**。

## 手順

### 1. 出発点を揃える

```bash
git checkout master && git fetch origin && git merge --ff-only origin/master
gh pr list --state open
```

**先に open な PR を片付ける。** 積まれたまま 3 つ並行で走らせると、
同じ場所を触る PR が 4 件以上になって解決不能になりやすい。
残っていれば `/review-prs` を先に済ませてから次へ進む。

`docs/journal/` の直近 2〜3 件と `docs/issues/` の open な件を読み、
各ループに渡す「今回の狙い」を決める。

### 2. 現状を測る

```bash
npm run sim -- --games 24 --hiders 1 --seekers 1
npm run sim -- --games 24 --hiders 2 --seekers 2
npm run sim -- --games 24 --hiders 3 --seekers 3
```

この数字を 3 つのエージェント全員に渡す。各自が測り直すと時間の無駄になるうえ、
別々の基準値で判断してしまう。

### 3. 3 つを並列で走らせる

Agent ツールを**1 つのメッセージで 3 つ同時に**呼ぶ。
`isolation: "worktree"` を指定すると、各エージェントが独立した作業コピーを持つので、
互いのファイルを踏まない。

各エージェントへのプロンプトには必ず次を含める。

- 対応するスキル名（`improve-seeker` / `improve-hider` / `improve-balance`）を
  Skill ツールで読み、その手順に従うこと
- 手順 2 で測った勝率（測り直さなくてよい）
- 担当範囲外のファイルを触らないこと（表は各スキルにある）
- **`EnterWorktree` と `ExitWorktree` は呼ばないこと**（すでに隔離済みのため）
- ブランチを切ってコミットし、push して `gh pr create` まで済ませること
- PR 本文に「何を直したか・観測した事実・勝率の前後」を書くこと
- 改善が見つからなければ**無理に変更を作らず**、その旨を報告して終えること

```
Agent(subagent_type: "general-purpose", isolation: "worktree",
      description: "逃げる側の行動改善",
      prompt: "Skill ツールで improve-hider を読み、その手順に従って…")
```

3 つとも完了するまで待つ。**先に終わったものを見て他を止めない。**

### 4. 出てきた PR を審査して取り込む

```bash
gh pr list --state open
```

`/review-prs` の手順に従って、**1 件ずつ**処理する。並列で作られた PR は
`src/ai` の同じ関数を触っていることが多い。最初の 1 件をマージした時点で
残りは必ず衝突するので、次のように進める。

1. 1 件目をレビューしてマージ
2. 2 件目のブランチに master を取り込み、衝突を解決
3. **解決後に勝率を測り直す。** ここが最も重要。
   2 つの変更は別々に測られており、組み合わせた状態は誰も測っていない
4. 前より悪化していたら、その PR はマージせず保留にして理由をコメントする
5. 3 件目も同様

「個別には改善、合わせると悪化」は実際に起きる（逃走方向の選び方と移動速度のように、
片方が他方の前提を崩す場合）。**組み合わせた実測値だけを信じる。**

### 5. ラウンドの結果を記録する

各エージェントが自分の日記を書くが、**ラウンド全体の結果は司令塔が書く**。

```markdown
## HH:MM 並列ラウンド

**やったこと** — seeker / hider / balance を並行で 1 サイクル。
PR #12（鬼の探索）と #13（逃走方向）をマージ、#14（アリーナ拡大）は保留。

**分かったこと** — #13 単体では 3v3 が 29% → 34% だったが、#12 と組み合わせると 31% に留まった。
鬼の探索改善が逃走改善の効果を打ち消している。両立させるなら…

**次にやること** — …
```

## 報告

- 測定した勝率（ラウンド開始時）
- 3 つのエージェントがそれぞれ何をしたか（変更なしなら「変更なし」）
- マージした PR と保留した PR、保留の理由
- **ラウンド終了時の勝率**（マージ後の実測値。開始時との差）

## 判断の原則

- **並列で作られた PR を、個別の申告値だけで信じない。** 組み合わせて測り直す
- **全部マージしようとしない。** 悪化させる PR は保留するのが正しい仕事
- **3 つとも空振りしたラウンドも記録する。** 手詰まりが 2 ラウンド続いたら、
  行動側ではなく `/improve-balance` に寄せる（あるいは人間の判断を仰ぐ）
- 衝突解決で**片方の変更を落とさない。** 落とすとその PR の勝率報告が意味を失う。
  両立しないなら保留にして、どちらを取るべきかを PR にコメントする

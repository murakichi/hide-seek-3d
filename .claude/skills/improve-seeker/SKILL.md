# 鬼の行動改善

鬼の**振る舞い**だけを直す。**ゲームルールは変えない。**
速度・視界・制限時間・アリーナの広さ・捕獲判定を触りたくなったら、それは
このサイクルの仕事ではない（後述の「ルールの限界に当たったら」へ）。

## 触ってよい範囲

- `src/ai/seeker.ts` — 鬼の思考。ここが主戦場
- `src/ai/params.ts` の `seeker` 側の値
- `src/ai/tuned.json` の `seeker`（`npm run tune -- --side seeker` の出力）
- `src/sim/_probe.ts` — 仮説を数値で確かめる使い捨ての計測スクリプト

**触ってはいけない:**

- `src/core/**` — ルールと物理。ここを変えると別のゲームになる
- `src/ai/hider.ts`、`params.ts` の `hider` 側 — 相手を弱くするのは改善ではない
- `src/ai/context.ts`、`src/ai/nav.ts` — 攻守で共有している。どうしても必要なら
  共有側の挙動を変えないことを確認し、PR にその旨を書く（逃げる側の改善サイクルと衝突する）

## 手順

### 0. 最新を取り込み、前回までを読む

```bash
git checkout master && git fetch origin && git merge --ff-only origin/master
```

`docs/journal/` の直近 2〜3 件を読む。前回の「次にやること」と、**試して駄目だった案**を
把握する。`docs/issues/` に鬼側の open な件があれば、優先度の高いものから 1 つ選ぶ。
無ければ手順 1 の測定で、鬼の勝率が一番低い構成を対象にする。

`EnterWorktree` でこの作業用の worktree を切る（`fix-seeker-*` など）。

### 1. 現状を測る

```bash
npm run sim -- --games 80 --hiders 1 --seekers 1
npm run sim -- --games 80 --hiders 2 --seekers 2
npm run sim -- --games 80 --hiders 3 --seekers 3
```

表示は逃げ側の勝率なので、**鬼の勝率はその裏**（100% − 逃げ側勝率）。
`初補足まで` の秒数が、鬼の探索効率を最も素直に表す。ここが縮めば探索が改善している。

3 構成すべてを見る。**24 試合では判断できない。** 同じコードでも 3v3 は 24 試合と
80 試合で 20 ポイント以上ずれた実績がある。採否を決めるなら**最低 80 試合、
できれば 2 シード**。シードを変えるには `_probe.ts` の `sweep`（`seed0` を取る）を使う。

単発の勝率差より、**3 構成が揃って同じ向きに動いていること**の方が強い証拠になる。
1 構成だけ大きく動いて他が逆向きなら、それはたいていノイズ。

### 2. 逃げ切られた試合をトレースで見る

```bash
npm run trace -- --hiders 2 --seekers 2 --find-win --interval 5
```

`--find-win` は**逃げ側が勝った試合**、つまり鬼が取り逃した試合を探す。
鬼の観点で、次のような「おかしさ」を探す。

- **時間切れまで一度も発見していない** — 探索の網が粗い。行っていない領域がある
- **同じ場所を何度も通っている** — 探索済みマップが効いていない
- **複数の鬼が同じ方向へ固まっている** — 担当領域の分散が効いていない
- **発見してから見失うのが早い** — 追跡中の進路取りが悪い、または遮蔽に弱い
- **箱の前で止まっている** — 排除やロック解除の判断で詰まっている
- **相手が高所にいるのに登れていない** — 踏み台の選び方（ジャンプ台の優先）が働いていない
- **ロックされた箱の周辺を調べていない** — 隠れ家の手がかりを活かせていない

### 3. 原因を 1 つだけ直す

1 サイクルで直すのは 1 つ。同時に複数変えるとどれが効いたか分からなくなる。

- **ロジックの欠陥**（詰まる、到達不能な目標を選ぶ、探索が偏る）
  → `seeker.ts` を直す。これが最も効果が大きい。
- **数値の当てはまりが悪いだけ** → `npm run tune -- --side seeker --iters 30 --games 10` に任せる。
  既定で `1x1,2x2,3x3` の全構成を評価する。1 構成に絞ると、その人数でしか通用しない値を
  採用してしまう（実際に 2v2 単独で最適化して勝率 100% になり、別シードでは 67% だったことがある）。
- **原因が絞れていない** → 直さずに `src/sim/_probe.ts` を書く。仮説を数値で確かめてから直す。

### 4. 再測定する

手順 1 と同じコマンドを回し、狙った構成で鬼の勝率が上がり、**他の構成が悪化していないこと**を
確認する。悪化していたら戻す。tune の結果を採用したなら `--seed` を変えて汎化を確かめる。

**ゲームバランスは考えない。** 逃げ側の勝率が下がっても、それはこのサイクルの
判断材料ではない。鬼が強くなったなら、それは目的どおり。全体の釣り合いは
`/improve-balance` が別途取る。ここでは**鬼が賢くなったかどうか**だけを見る。

### 5. 記録する

- `docs/journal/YYYY-MM-DD.md` — やったこと・分かったこと・次にやること。
  **試して駄目だった案とその理由**を必ず残す
- `docs/balance-log.md` — 変更・理由・勝率（前回値つき）
- `docs/issues/` — 着手した issue に追記。直ったら `status: closed` にして「解決」節を書く

### 6. PR を作る

```bash
git fetch origin && git merge origin/master   # 衝突はここで解決する
npm run build
git push -u origin <ブランチ名>
gh pr create --title "..." --body "..."
```

衝突を解決したら**勝率を測り直す**。本文には何を直したか・トレースで観測した事実・
勝率の前後（1v1 / 2v2 / 3v3）を書く。マージは `/review-prs` が行う。
最後に `ExitWorktree` で抜ける。

## ルールの限界に当たったら

行動をどう直しても解けない、ルール側の問題だと判断したら、**config は触らずに issue を立てる。**

そう判断してよい例:

- 視界が狭すぎて、追跡時間内にアリーナ全域を確認しきれない
- 逃げる側が速すぎて、発見しても原理的に追いつけない
- ロックの解除に時間がかかりすぎて、籠城を崩す手段が実質無い
- 煙幕の効果時間が長すぎて、一度撒かれると追跡が必ず切れる

issue には**行動側で何を試して駄目だったか**を書く。それが無いとルールを変える判断ができない。
`priority` と、変更を提案するルール（どの定数をどちらへ）を明記する。

ルール変更そのものは `/improve-balance` の仕事。このサイクルでは行わない。

**これは最後の手段。** 「逃げ側が勝ちすぎ / 負けすぎだから」は理由にならない
（それはバランスの話で、このサイクルの関心事ではない）。使ってよいのは
**鬼の行動をどう書き換えても物理的に不可能**だと数値で示せたときだけ。
実際に修正を試す前に issue へ逃げると、鬼側に残っている改善余地を
見落としたまま「ルールのせい」にすることになる。

## 目安

**このサイクルに勝率の目標値は無い。** 見るのは鬼が賢くなったかどうか。

- **`初補足まで` の秒数が縮んだか** — 探索効率の最も素直な指標
- **鬼の勝率が上がったか** — 3 構成すべてで。1 構成だけ上がって他が下がるのは
  その人数でしか通用しない変更を掴んでいる
- **トレースで見て動きが自然になったか** — 数字が同じでも、詰まりや無駄な往復が
  消えていればそれは改善

逃げ側の勝率が目標域（35〜50%）から外れることを気にする必要はない。
釣り合いを取るのは `/improve-balance` の仕事で、そちらは逃げ側の行動や
ルール定数という別の手札を持っている。**ここで手加減すると、鬼側に残った
改善余地が見えなくなる。**

# 改善サイクルの司令塔

**このスキル自身はコードを直さない。** 現状を測って、どのループを回すべきかを決め、
そのスキルを呼ぶ。1 回の実行で回すのは**1 ループだけ**。

## 手順

### 1. 積まれた PR を先に捌く

```bash
git checkout master && git fetch origin && git merge --ff-only origin/master
gh pr list --state open
```

**open な PR が 2 件以上あるなら、まず `/review-prs` を呼んで終了する。**
PR を溜めたまま新しい作業を始めると、`src/ai` の同じ場所で衝突が増え続ける。

1 件だけなら、そのまま次へ進んでよい。

### 2. 前回までを読む

`docs/journal/` の直近 2〜3 件を読む。次を把握する。

- 前回どのループを回して、何が起きたか
- **同じループを 2 回続けて回して改善が出ていないか**（出ていないなら別のループへ）
- 「次にやること」に指名があるか

`gh issue list` の open な件と、それぞれの担当ラベル（`seeker` / `hider` / `balance`）を確認する。

### 3. 現状を知る

**手元で勝率を測らない**（CLAUDE.md「勝率は CI が測る」）。直近マージされた PR に
CI が貼った表を読む。

```bash
gh pr list --state merged --limit 3     # 直近のマージ済み PR
gh pr view <n> --comments               # 「勝率（逃げる側）」の表を読む
```

数字はすべて逃げる側の勝率。目標は **どの構成でも 35〜50%**。
まだ CI の表が付いた PR が無ければ、`gh workflow run 勝率` を master 上で起動して
その実行のジョブサマリを読む（`gh run watch`）。

### 4. どのループを回すか決める

上から順に当てはめ、最初に該当したものを選ぶ。

1. **open PR が 2 件以上** → `/review-prs`
2. **`priority: high` の issue がある** → その担当のループ
   （鬼の行動なら `/improve-seeker`、逃げる側なら `/improve-hider`、ルールなら `/improve-balance`）
3. **目標を外れている構成がある** → 外れ幅が最も大きい構成を対象に、
   - 逃げ側が 35% 未満 → `/improve-hider`
   - 逃げ側が 50% 超 → `/improve-seeker`
4. **全構成が 35〜50% に収まっている** → `/improve-balance`
   （遊び心地の改善、効いていない機能の廃止、新しい選択肢の追加）

ただし **同じループが 2 回続けて空振り**（日記に「勝率が動かなかった」が 2 回並ぶ）しているなら、
その判定を飛ばして次点のループを選ぶ。行動で手詰まりなら `/improve-balance` へ、
バランスで手詰まりなら勝率が最も低い側の行動へ。

### 5. 選んだループを呼ぶ

Skill ツールでそのスキルを起動し、**最後まで実行させる**（worktree を切って PR を作るところまで）。
司令塔側で先回りしてコードを直さない。判断と実行の担当を分けておかないと、
どの変更が効いたのか追えなくなる。

### 6. 呼んだ結果を記録する

呼んだループが日記を書くので、司令塔は**選定の理由だけ**を 1 行足す。

```markdown
## HH:MM 司令塔: /improve-hider を選択
1v1 12.5% / 2v2 25.0% / 3v3 29.2%。1v1 が目標から最も外れており、
issue #8 も逃げる側の担当だったため。
```

## 報告

次を簡潔に伝える。

- 測定した勝率（3 構成）
- どのループを選んだか、その理由
- 呼んだループの結果（変更内容と PR 番号、または「改善が見つからなかった」）

## 判断の原則

- **1 回の実行で 1 ループ。** 欲張って複数回すと、勝率が動いた原因が分からなくなる
- **勝率を目標に近づけるのが目的。** 上げることでも下げることでもない
- **空振りも成果。** 「この案は効かなかった」が日記に残れば、次のサイクルが短くなる

## ユーザーからの報告を受け取ったら

**ユーザーが実際にプレイして見つけたことは、敵サイドのループにも同時に伝えられている。**
片方だけが知っている情報ではない。前提にすること。

- こちらが穴を塞いでも、**相手側はその穴を積極的に使う実装を入れてくる**
- こちらが弱点を突く実装を入れても、相手側は対策を入れてくる
- **今の測定値は、相手が対応した時点で無効になる。** 手順 0 で相手側の PR と issue を
  必ず確認し、対応が入っていたら測り直す

**報告された穴は、勝率にも CI にも現れないことが多い。**
AI がその戦術を使わないからで、現れないことは「無い」ことを意味しない。
`src/sim/_probe-*.ts` に再現環境を組んで直接確かめること。
盤面を手で組み、相手を狙った状態に置いて、こちらが対処できるかだけを見ればよい。

実例: 「低い台から少し離れた高い台へ飛び移ると鬼が来られない」という報告は、
600 試合の CI では一度も現れなかった。人間が遊んだ 1 試合の方が情報量が多いことがある。

対応するときは、**相手が対策してきた場合にどうなるかまで考えること。**
「鬼が追ってこられるようになった」なら、相手は「登ってきた鬼を高所から振り切る」を
狙ってくる。片側だけを見て安全だと結論しない。

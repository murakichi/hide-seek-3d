# ゲームバランスの調整

このサイクルだけが**ゲームルールを変えてよい**。
`/improve-seeker` と `/improve-hider` が「行動をどう直しても解けない」と判断して
立てた issue を引き取るのが主な仕事。

## 触ってよい範囲

数値の調整だけでなく、**機能の追加と廃止もこのサイクルの仕事**。

- `src/core/config.ts` — 速度・加速・ジャンプ・視界・制限時間・アリーナ・アイテム。主戦場
- `src/core/arena.ts` — 障害物やアイテムの配置と量
- **新しい機能の追加** — アイテム、地形要素、行動の選択肢。
  `types.ts` / `game.ts` / `render` / `ui`、および AI がそれを使うための最小限の実装まで
- **効いていない機能の廃止** — 測って寄与が確認できないものは消す
- ルール変更に**追随するための** AI 側の前提値。例えば速度を変えたら
  `hider.ts` の `fleeDirection` のレイ長や `followPath` の到達判定も直す
  （速度だけ変えると AI が壁に突っ込む。実際に踏んだ失敗）

**触ってはいけない:**

- **AI の戦術そのもの。** 探索の仕方、逃走先の選び方、運搬の段取りは
  `/improve-seeker` と `/improve-hider` の担当。ここで一緒に変えると、
  勝率が動いた原因がルールなのか戦術なのか分からなくなる。
  新機能を AI が「使える」ようにするのは可、その機能を使った戦術の作り込みは行動サイクルへ回す
- `src/core/game.ts` の既存の物理・判定順序 — 壊すと全サイクルの前提が崩れる。
  変更するなら理由と再現手順を PR に詳しく書く

### 機能を追加するとき

- **決定論を壊さない。** `Math.random()` や実時間を使わない。乱数は `Rng`、時間は `DT`
- **`src/core` から `three` や DOM を参照しない。** ヘッドレス対戦が壊れる
- 追加したら AI が最低限それを使えるようにする。誰も使わない機能は測定できない
- **追加した機能は必ず「効いたか」を測る。** 効果が確認できなければ次のサイクルで廃止候補

### 機能を廃止するとき

複雑さは、それ自体がコストになる。次のどれかに当てはまるものは消してよい。

- 勝率にも遊び心地にも寄与が確認できない（測って誤差の範囲だった）
- 他の機能と役割が重複していて、片方で足りる
- AI も人間もほとんど使っていない（トレースや観戦で確認できる）

廃止も 1 サイクルの立派な成果として扱う。日記には「なぜ効かなかったのか」を残す
（例: 補給パックはスタミナを回復するが、スタミナは勝敗の支配要因ではなかった）。

## 手順

### 0. 最新を取り込み、前回までを読む

```bash
git checkout master && git fetch origin && git merge --ff-only origin/master
```

`docs/journal/` の直近 2〜3 件と `docs/balance-log.md` を読む。
**過去にどの定数をどちらへ動かして何が起きたか**を把握する。同じ調整を往復しない。

`gh issue list --label balance` から、行動サイクルが立てた「ルールの限界」issue を
優先度順（`priority:high` から）に 1 つ選ぶ。
無ければ手順 1 の測定で、目標（全構成 35〜50%）から最も外れている構成を対象にする。

`EnterWorktree` で worktree を切る（`balance-*` など）。

### 1. 現状を知る

**手元で勝率を測らない**（CLAUDE.md「勝率は CI が測る」）。基準値は直近マージされた
PR に CI が貼った表にある。

```bash
gh pr list --state merged --limit 3     # 直近のマージ済み PR
gh pr view <n> --comments               # 「勝率（逃げる側）」の表を読む
```

ルール変更は全構成に効くので、3 構成すべてを見る。
`初補足`（探索の速さ）と `平均生存`（勝率より分散が小さい）も併せて見る。

### 2. どちらの問題かを見極める

**勝率が偏っている原因が、ルールなのか行動なのかを先に切り分ける。**
行動の問題をルールで殴ると、AI が直った後に今度は逆へ振れる。

- issue に「行動側で何を試して駄目だったか」が書かれているか。無ければ、
  それは行動サイクルへ差し戻す（issue にコメントを追記して閉じない）
- トレースで、負けている側が**やるべきことをやったうえで**負けているかを見る
  ```bash
  npm run trace -- --hiders 1 --seekers 1 --find-loss --interval 3
  ```
  詰まっている・止まっている・明らかに変な目標へ向かっているなら、それは行動の問題

### 3. 変更を 1 つだけ入れる

定数を動かす、機能を足す、機能を消す — どれでもよいが**1 サイクルで 1 つ**。
複数入れると効果が打ち消し合って何も分からなくなる。

よく効く順に、だいたいこの順で検討する。

| 症状 | 見るべき定数 |
| --- | --- |
| 見つかった後に必ず捕まる | `HIDER_SPEED` / `SEEKER_SPEED` の差、`SEEKER_DASH_COST` |
| 隠れる意味がない・すぐ見つかる | `VIEW_DIST`、`VIEW_FOV`、`ARENA_HALF`、障害物の量 |
| 逃げ切りが simple に難しい | `HUNT_TIME`、`huntTimeFor()` の人数補正 |
| 準備が間に合わない | `PREP_TIME`、`GRAB_SPEED`、`GRAB_SLOWDOWN` |
| 追いかけっこが単調 | 煙幕（`SMOKE_*`）、ジャンプ台、補給パックの量と配置 |
| 移動が気持ちよくない | `HIDER_SPEED`、`ACCEL_GROUND`、`JUMP_IMPULSE`、`ARENA_HALF` |
| 手札が足りず打つ手が無い | 機能の追加を検討する（新しいアイテム、地形、行動の選択肢） |
| 複雑なだけで誰も使っていない | 機能の廃止を検討する |

**速度・アリーナを変えたら、AI の先読み距離も必ず一緒に見直す。**
`fleeDirection` のレイ長、`followPath` の到達判定、詰まり判定のしきい値は
すべて速度に対する相対値として決めてある。片方だけ変えると AI が壁に突っ込む。

### 4. 測定は CI に出す

手元では疎通だけ確かめ、数字は draft PR を出して CI に測らせる。
**全構成を見る。** ルール変更は 1 構成だけを直すことができない。

```bash
npm run sim -- --games 6 --hiders 2 --seekers 2                  # 落ちないこと
git push -u origin <ブランチ名> && gh pr create --draft --fill
gh pr checks --watch && gh pr view --comments
```

目標は **どの構成でも逃げ側 35〜50%**。1 つを直して他が目標を外れたなら、その変更は採らない。
CI の表は master との差分つきなので、「動かした量」がそのまま読める。

数値が動かなかった場合も、それは収穫として日記に残す
（補給パックを足したとき、勝率は誤差の範囲でしか動かなかった。
スタミナは勝敗の支配要因ではないと分かった、という形で残っている）。

### 5. 遊び心地を確かめる

数値だけでは判断できない変更（速度、ジャンプ、アイテム）は、観戦で実際に見る。

```bash
npm run dev
```

観戦モードで 2 on 2 を選び、早送り（`1/2/4/8`）で数試合眺める。
数値が良くても、動きが不自然だったり展開が単調なら採らない。

### 6. 記録して PR を作る

- `docs/balance-log.md` — **変更した定数・前後の値・理由・全構成の勝率（前回値つき）**。
  ルール変更はここが最も重要な記録になる
- `docs/journal/YYYY-MM-DD.md` — やったこと・分かったこと・次にやること
- GitHub issue — 引き取った issue に `gh issue comment` で結果を書く。直ったら
  原因と直し方をコメントしてから `gh issue close`。
  行動側に差し戻すならその旨をコメントとして追記し、open のまま残す

```bash
git fetch origin && git merge origin/master
npm run build
git push -u origin <ブランチ名>               # 手順 4 で draft を出していれば push だけでよい
gh pr ready                                   # 差分が良ければ draft を外す
gh pr checks --watch && gh pr view --comments # マージ直前の値を確認する
```

衝突を解決したら push し直して測り直させる。CI が出した差分を本文と
`docs/balance-log.md` に転記する。マージは `/review-prs` が行う。
最後に `ExitWorktree` で抜ける。

## 判断の原則

- **勝率を目標に近づけることが目的であって、上げることが目的ではない。**
  逃げ側が勝ちすぎている場合も同じサイクルで扱う
- **遊び心地は勝率に優先することがある。** 50/50 でも展開が単調なら失敗
- **迷ったら変えない。** ルールを往復させると、行動サイクル側が
  「前提が変わり続ける」状態になって改善が積み上がらない

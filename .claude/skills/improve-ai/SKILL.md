# AI 改善サイクル

このプロジェクトの AI を 1 サイクルぶん改善する。**推測でパラメータを振らないこと。**
必ずトレースで実際の試合展開を見てから、原因を 1 つに絞って直す。

## 前提

- ゲームコア (`src/core`) は決定論シミュレーション。同じ seed なら必ず同じ試合になる。
- AI は `src/ai`。戦術パラメータは `src/ai/params.ts`、自動探索の結果は `src/ai/tuned.json`。
- ゲームバランスの定数（速度・時間・視界・アリーナ）は `src/core/config.ts`。
  これは AI の強さではなく遊び心地の問題なので、`tune` の対象ではない。

## 手順

### 0. 前回までを読み、worktree を切る

`docs/journal/` の直近 2〜3 件を読む。前回の「次にやること」と、
**試して駄目だった案**を把握する（同じ案を再発明しない）。

`docs/issues/` を見て open の件があれば、優先度の高いものから 1 つ選ぶ。
無ければ手順 1 の測定で一番低い構成を対象にする。

`EnterWorktree` でこの作業用の worktree を切る。以降の編集はその中で行う。

### 1. 現状を測る

```bash
npm run sim -- --games 24 --hiders 1 --seekers 1
npm run sim -- --games 24 --hiders 2 --seekers 2
npm run sim -- --games 24 --hiders 3 --seekers 3
```

3 構成すべてを見る。1 構成だけ見て直すと、他の構成を壊したことに気づけない。
数値は `docs/balance-log.md` の前回値と比べる。24 試合の勝率は ±10 ポイント程度ぶれるので、
その範囲の差を「改善」と読まないこと。

### 2. 負け筋をトレースで見る

一番勝率の低い構成について、負け試合を再生する。

```bash
npm run trace -- --hiders 3 --seekers 3 --find-loss --interval 5
```

出力には発見・見失い・捕獲・ロックの時刻と座標、各エージェントの思考状態が出る。
次のような「おかしさ」を探す:

- 準備フェーズ終了時に、逃げる側が拠点から遠い場所にいる（移動や運搬が破綻している）
- 同じ座標に留まり続けている（経路が取れず詰まっている）
- 追跡開始直後に発見されている（隠れ場所の選び方が悪い）
- 逃げる側が固まっている（拠点の分散が効いていない）
- 見失いが一度も起きない（遮蔽が使えていない）

### 3. 原因を 1 つだけ直す

1 サイクルで直すのは 1 つ。同時に複数変えると、どれが効いたか分からなくなる。

- **ロジックの欠陥**（詰まる、到達不能な目標を選ぶ、状態遷移で入力が空になる）
  → `src/ai` のコードを直す。これが最も効果が大きい。
- **数値の当てはまりが悪いだけ** → `npm run tune` に任せる:

```bash
npm run tune -- --side hider  --iters 30 --games 10
npm run tune -- --side seeker --iters 30 --games 10
```

  `--sizes` は既定で `1x1,2x2,3x3` の全構成を評価する。1 構成に絞ると、その人数でしか
  通用しない値を採用してしまうので、絞るなら理由を書き残すこと。

- **遊び心地の問題**（遅い、単調、ジャンプが無意味）→ `src/core/config.ts` を直す。
  ただし速度を変えたら、AI の先読み距離（`fleeDirection` のレイ、`followPath` の到達判定）も
  一緒に見直すこと。速度だけ上げると AI が壁に突っ込むようになる。

### 4. 再測定して確認する

手順 1 と同じコマンドを回し、直した構成が改善し、**他の構成が悪化していないこと**を確認する。
悪化していたら変更を戻す。tune の結果を採用した場合は、`--seed` を変えて汎化を確かめる:

```bash
npm run sim -- --games 24 --hiders 2 --seekers 2
npm run tune -- --side hider --iters 1 --games 24 --seed 777 --dry-run
```

### 5. 記録して閉じる

3 つとも書く。どれか 1 つでは次のサイクルが同じ調査を繰り返す。

- **`docs/journal/YYYY-MM-DD.md`** — やったこと・分かったこと・次にやること。
  試して駄目だった案とその理由をここに残す。書き方は `docs/journal/README.md`。
- **`docs/balance-log.md`** — 変更・理由・勝率（前回値つき）。
- **`docs/issues/`** — 着手した issue に分かったことを追記する。直ったなら
  `status: closed` にして「解決」節を書く。**途中で気づいた別の問題は
  その場で直さず、新しい issue を立てる。**

最後にブランチを push して PR を作る。master へ直接マージしない。

**PR を作る前に master を取り込む。** サイクルを並行して回していると、
作業中に master が進んで `src/ai` の同じ場所が変わっていることがある。
ここで取り込んでおけば、レビュー側で解決するより自分の変更の意図を保ちやすい。

```bash
git fetch origin
git merge origin/master
```

衝突したら解決し、**解決後にもう一度勝率を測る**。2 つの変更が個別に良くても、
組み合わせて悪化することがある。数字が変わったら PR 本文はその実測値を書く。

```bash
npm run build
git push -u origin <ブランチ名>
gh pr create --title "..." --body "..."
```

PR 本文には**何を直したか・トレースで観測した事実・勝率の前後（1v1 / 2v2 / 3v3）**を書く。
レビューとマージは `/review-prs` が行う。作り終えたら `ExitWorktree` で抜ける。

### 6. 改善が見つからなかった場合

1 サイクル回して勝率が動かなかったなら、それも収穫なので日記に書く
（「この案は効かなかった」は次のサイクルの時間を節約する）。
原因が絞れていないなら、修正ではなく**計測用のスクリプトを書く**方に倒す。
`src/sim/_probe.ts` のように、仮説を数値で確かめられる形にしてから直す。

## 目安

逃げる側の勝率は **どの構成でも 35〜50%** を目標にする。
どちらかに寄り切っていると、勝敗が立ち回りではなく初期配置で決まってしまう。

# 逃げる側の行動改善

**このサイクルの目的は 2 つだけ。逃げる側の勝率を上げることと、挙動の欠陥を潰すこと。**
ゲームバランスは考えない。勝率が目標帯の上に出ていても、そこは
`/improve-balance` と `/improve-seeker` の仕事なので、手加減はしない。
勝てる手があるなら取る。

**ゲームルールは変えない。** 速度・視界・制限時間・アリーナの広さ・捕獲判定を
触りたくなったら、それはこのサイクルの仕事ではない（後述の「ルールの限界に当たったら」へ）。

## 勝ち筋の探し方

**ゲームシステムと鬼のソースは読んでよい。むしろ読むこと。**
`src/core/**` と `src/ai/seeker.ts` を読んで、**使われていない仕様**や
**鬼の思考の穴**を探し、それを突く。読むのは自由、変更するのは禁止。

過去に効いたのはどれも「使える仕様を使っていなかった」型の欠陥だった:

- 小さい箱（h=1.3）は `CLIMB_REACH`（1.64）以下なので跳べば乗り越えられるのに、
  逃走方向の候補から一律で捨てていた。箱を挟んで射線を切る動きが取れていなかった。
- 見失った鬼の位置を 4 秒で忘れ、拠点へ最短で帰るときに鬼の正面へ出ていた。

探すときの着眼点:

- `src/core/config.ts` の定数で、`hider.ts` が一度も参照していないもの
  （ジャンプ台、ランプ、段差、スタミナ、煙幕、箱のロック解除…）
- `src/ai/seeker.ts` が「見ていない」もの。鬼が何を手がかりに探索先を決めているかを読み、
  その手がかりに乗らない動きを取る（例: ロックした箱を囮に使う、記憶の切れる時刻を突く）
- 物理（`src/core/physics.ts`）で成立するのに AI が使っていない動き

## 触ってよい範囲

- `src/ai/hider.ts` — 逃げる側の思考。ここが主戦場
- `src/ai/params.ts` の `hider` 側の値
- `src/ai/tuned.json` の `hider`（`npm run tune -- --side hider` の出力）
- `src/sim/_probe.ts` — 仮説を数値で確かめる使い捨ての計測スクリプト

**読むのは自由。変更してはいけない:**

- `src/core/**` — ルールと物理。ここを変えると別のゲームになる
- `src/ai/seeker.ts`、`params.ts` の `seeker` 側 — 相手を弱くするのは改善ではない
- `src/ai/context.ts`、`src/ai/nav.ts` — 攻守で共有している。どうしても必要なら
  共有側の挙動を変えないことを確認し、PR にその旨を書く（鬼の改善サイクルと衝突する）

## 手順

### 0. 最新を取り込み、「これから何が変わるか」まで把握する

```bash
git checkout master && git fetch origin && git merge --ff-only origin/master
git log --oneline -10                  # master に何が入ったか
gh pr list --state open                # ★ これから何が入るか
gh issue list --state open             # 担当外も含めて全部見る
```

`docs/journal/` の直近 2〜3 件を読む。前回の「次にやること」と、**試して駄目だった案**を
把握する（同じ案を再発明しない）。`gh issue list --label hider` の open から
優先度の高いものを 1 つ選ぶ。無ければ手順 1 の測定で一番低い構成を対象にする。

**open な PR は必ず中身まで読む。**`gh pr view <n>` で、これから master に入る変更が

- 自分が触る場所（`hider.ts` の同じ関数、`params.ts` の hider 側）に当たるか
- ルール（`src/core/**`）や計測の基準値を動かすか
- 自分が今から測ろうとしている前提を壊すか

を確かめる。当たるなら、**その PR を取り込んだ状態を土台にして測る**（`git merge origin/<branch>`）。
これを怠ると、サイクルの終わりに PR がマージされていて基準値が全部古くなり、測り直しになる。
実際に 2 サイクル連続でこれを踏んだ（2026-08-11 の日記）。

同じ理由で、**手順 4 の再測定の直前と、手順 6 の PR 作成の直前に `git fetch` して
master が動いていないか確認する。**動いていたら取り込んでから測り直す。

`EnterWorktree` でこの作業用の worktree を切る（`fix-hider-*` など）。以降の編集はその中で行う。

### 1. 現状を知る

**手元で勝率を測らない**（CLAUDE.md「勝率は CI が測る」）。基準値は直近マージされた
PR に CI が貼った表にある。

```bash
gh pr list --state merged --limit 3     # 直近のマージ済み PR
gh pr view <n> --comments               # 「勝率（逃げる側）」の表を読む
```

3 構成すべてを見る。1 構成だけ直すと他を壊したことに気づけない。
`平均生存` は勝率より分散が小さいので、変化の兆しを見るのに向いている。
手元では疎通だけ確かめる（数字は当てにしない）。

```bash
npm run sim -- --games 6 --hiders 2 --seekers 2
```

### 2. 負け筋をトレースで見る

```bash
npm run trace -- --hiders 3 --seekers 3 --find-loss --interval 5
```

逃げる側の観点で、次のような「おかしさ」を探す。

- **準備フェーズ終了時に拠点から遠い** — 運搬や移動が破綻している
- **同じ座標に留まり続けている** — 経路が取れず詰まっている
- **追跡開始の直後に発見されている** — 隠れ場所の選び方が悪い
- **逃げる側が固まっている** — 拠点の分散が効いていない
- **「見失い」が一度も起きない** — 遮蔽を使えていない。追われ方が直線的すぎる
- **捕まる直前に壁や隅にいる** — 逃走方向の選択が袋小路に入っている
- **煙幕を使わないまま捕まっている** — 使用条件が厳しすぎる

### 3. 原因を 1 つだけ直す

1 サイクルで直すのは 1 つ。同時に複数変えるとどれが効いたか分からなくなる。

- **ロジックの欠陥**（詰まる、到達不能な目標を選ぶ、状態遷移で入力が空になる）
  → `hider.ts` を直す。これが最も効果が大きい。過去の改善はすべてこれだった。
- **数値の当てはまりが悪いだけ** → `npm run tune -- --side hider --iters 30 --games 10` に任せる。
  既定で `1x1,2x2,3x3` の全構成を評価する。1 構成に絞ると、その人数でしか通用しない値を
  採用してしまう（実際に 2v2 単独で最適化して 1v1 が 42% → 17% に落ちたことがある）。
- **原因が絞れていない** → 直さずに `src/sim/_probe.ts` を書く。仮説を数値で確かめてから直す。
  「4.7% のティックで移動入力がゼロ」のような数字が出て初めて手が打てる。

### 4. 手元で確かめて、測定は CI に出す

```bash
npm run sim -- --games 6 --hiders 2 --seekers 2                   # 落ちないこと
npm run trace -- --hiders 3 --seekers 3 --find-loss --interval 5  # 直した挙動が消えたか
```

6 試合の勝率は当てにならない。ここでは**手順 2 で見つけた「おかしさ」がトレースから
消えたか**で判断する。勝率の採否判定は draft PR を出して CI にやらせる。

```bash
git push -u origin <ブランチ名> && gh pr create --draft --fill
gh pr checks --watch && gh pr view --comments
```

狙った構成が改善し、**他の構成が悪化していないこと**を CI の差分で確認する。
悪化していたら直して push する（同じコメントが更新される）。
CI は 4 つの seed で測るので、tune の結果を採用した場合の汎化もここで見える。

### 5. 記録する

- `docs/journal/YYYY-MM-DD.md` — やったこと・分かったこと・次にやること。
  **試して駄目だった案とその理由**を必ず残す
- `docs/balance-log.md` — 変更・理由・勝率（前回値つき）
- GitHub issue — 着手した件に `gh issue comment` で追記。直ったら原因と直し方を
  コメントしてから `gh issue close`

### 6. PR を作る

```bash
git fetch origin && git merge origin/master   # 衝突はここで解決する
npm run build
git push -u origin <ブランチ名>               # 手順 4 で draft を出していれば push だけでよい
gh pr ready                                   # 差分が良ければ draft を外す
gh pr checks --watch && gh pr view --comments # マージ直前の値を確認する
```

衝突を解決したら push し直して**測り直させる**。本文には何を直したか・
トレースで観測した事実・CI が出した勝率の差分（1v1 / 2v2 / 3v3）を書く。
マージは `/review-prs` が行う。
最後に `ExitWorktree` で抜ける。

## ルールの限界に当たったら

行動をどう直しても解けない、ルール側の問題だと判断したら、**config は触らずに issue を立てる。**

そう判断してよい例:

- 逃げる側と鬼の速度差が小さすぎて、平地では原理的に振り切れない
- 追跡時間が長すぎて、どんな隠れ方をしても最後は見つかる
- アリーナが狭すぎて、鬼の視界が全域を覆ってしまう
- 準備時間が短すぎて、箱を運ぶ戦術がそもそも成立しない

issue には**行動側で何を試して駄目だったか**を書く。それが無いと、
ルールを変える判断ができない。`gh issue create --label "balance,priority:high"` で立てる。
CLAUDE.md の「issue は GitHub issue を使う」の形式に従い、
`priority` と、変更を提案するルール（どの定数をどちらへ）を明記する。

ルール変更そのものは人間が判断する。このサイクルでは行わない。

## 採否の基準

**勝率が上がったか、挙動の欠陥が消えたか。この 2 つだけで決める。**
「目標帯（35〜50%）を超えるから見送る」という判断はしない。
勝率が上振れすること自体は `/improve-balance` と `/improve-seeker` が扱う問題で、
このサイクルが手加減して調整する話ではない。

判定は必ず複数シード・複数構成で行う。24 試合の勝率は 3v3 で 20 ポイント以上ぶれる。
**最低でも各値 100 試合以上、3 シード。**3 構成で向きが揃うかどうかを見る。
1 構成だけ、1 シードだけで「効いた」と読まない。

## ユーザーからの報告を受け取ったら

**ユーザーが実際にプレイして見つけたことは、敵サイドのループにも同時に伝えられている。**
片方だけが知っている情報ではない。前提にすること。

- こちらが穴を塞いでも、**相手側はその穴を積極的に使う実装を入れてくる**
- こちらが弱点を突く実装を入れても、相手側は対策を入れてくる
- **今の測定値は、相手が対応した時点で無効になる。** 手順 0 で相手側の PR と issue を
  必ず確認し、対応が入っていたら測り直す

**報告された穴は、勝率にも CI にも現れないことが多い。**
AI がその戦術を使わないからで、現れないことは「無い」ことを意味しない。
`src/sim/_probe-*.ts` に再現環境を組んで直接確かめること。
盤面を手で組み、相手を狙った状態に置いて、こちらが対処できるかだけを見ればよい。

実例: 「低い台から少し離れた高い台へ飛び移ると鬼が来られない」という報告は、
600 試合の CI では一度も現れなかった。人間が遊んだ 1 試合の方が情報量が多いことがある。

対応するときは、**相手が対策してきた場合にどうなるかまで考えること。**
「鬼が追ってこられるようになった」なら、相手は「登ってきた鬼を高所から振り切る」を
狙ってくる。片側だけを見て安全だと結論しない。

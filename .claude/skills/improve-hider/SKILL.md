# 逃げる側の行動改善

逃げる側の**振る舞い**だけを直す。**ゲームルールは変えない。**
速度・視界・制限時間・アリーナの広さ・捕獲判定を触りたくなったら、それは
このサイクルの仕事ではない（後述の「ルールの限界に当たったら」へ）。

## 触ってよい範囲

- `src/ai/hider.ts` — 逃げる側の思考。ここが主戦場
- `src/ai/params.ts` の `hider` 側の値
- `src/ai/tuned.json` の `hider`（`npm run tune -- --side hider` の出力）
- `src/sim/_probe.ts` — 仮説を数値で確かめる使い捨ての計測スクリプト

**触ってはいけない:**

- `src/core/**` — ルールと物理。ここを変えると別のゲームになる
- `src/ai/seeker.ts`、`params.ts` の `seeker` 側 — 相手を弱くするのは改善ではない
- `src/ai/context.ts`、`src/ai/nav.ts` — 攻守で共有している。どうしても必要なら
  共有側の挙動を変えないことを確認し、PR にその旨を書く（鬼の改善サイクルと衝突する）

## 手順

### 0. 最新を取り込み、前回までを読む

```bash
git checkout master && git fetch origin && git merge --ff-only origin/master
```

`docs/journal/` の直近 2〜3 件を読む。前回の「次にやること」と、**試して駄目だった案**を
把握する（同じ案を再発明しない）。`docs/issues/` に逃げる側の open な件があれば、
優先度の高いものから 1 つ選ぶ。無ければ手順 1 の測定で一番低い構成を対象にする。

`EnterWorktree` でこの作業用の worktree を切る（`fix-hider-*` など）。以降の編集はその中で行う。

### 1. 現状を測る

```bash
npm run sim -- --games 24 --hiders 1 --seekers 1
npm run sim -- --games 24 --hiders 2 --seekers 2
npm run sim -- --games 24 --hiders 3 --seekers 3
```

3 構成すべてを見る。1 構成だけ直すと他を壊したことに気づけない。
24 試合の勝率は ±10 ポイントぶれるので、その範囲の差を「改善」と読まない。
`平均生存人数` は勝率より分散が小さいので、変化の兆しを見るのに向いている。

### 2. 負け筋をトレースで見る

```bash
npm run trace -- --hiders 3 --seekers 3 --find-loss --interval 5
```

逃げる側の観点で、次のような「おかしさ」を探す。

- **準備フェーズ終了時に拠点から遠い** — 運搬や移動が破綻している
- **同じ座標に留まり続けている** — 経路が取れず詰まっている
- **追跡開始の直後に発見されている** — 隠れ場所の選び方が悪い
- **逃げる側が固まっている** — 拠点の分散が効いていない
- **「見失い」が一度も起きない** — 遮蔽を使えていない。追われ方が直線的すぎる
- **捕まる直前に壁や隅にいる** — 逃走方向の選択が袋小路に入っている
- **煙幕を使わないまま捕まっている** — 使用条件が厳しすぎる

### 3. 原因を 1 つだけ直す

1 サイクルで直すのは 1 つ。同時に複数変えるとどれが効いたか分からなくなる。

- **ロジックの欠陥**（詰まる、到達不能な目標を選ぶ、状態遷移で入力が空になる）
  → `hider.ts` を直す。これが最も効果が大きい。過去の改善はすべてこれだった。
- **数値の当てはまりが悪いだけ** → `npm run tune -- --side hider --iters 30 --games 10` に任せる。
  既定で `1x1,2x2,3x3` の全構成を評価する。1 構成に絞ると、その人数でしか通用しない値を
  採用してしまう（実際に 2v2 単独で最適化して 1v1 が 42% → 17% に落ちたことがある）。
- **原因が絞れていない** → 直さずに `src/sim/_probe.ts` を書く。仮説を数値で確かめてから直す。
  「4.7% のティックで移動入力がゼロ」のような数字が出て初めて手が打てる。

### 4. 再測定する

手順 1 と同じコマンドを回し、狙った構成が改善し、**他の構成が悪化していないこと**を確認する。
悪化していたら戻す。tune の結果を採用したなら `--seed` を変えて汎化を確かめる。

### 5. 記録する

- `docs/journal/YYYY-MM-DD.md` — やったこと・分かったこと・次にやること。
  **試して駄目だった案とその理由**を必ず残す
- `docs/balance-log.md` — 変更・理由・勝率（前回値つき）
- `docs/issues/` — 着手した issue に追記。直ったら `status: closed` にして「解決」節を書く

### 6. PR を作る

```bash
git fetch origin && git merge origin/master   # 衝突はここで解決する
npm run build
git push -u origin <ブランチ名>
gh pr create --title "..." --body "..."
```

衝突を解決したら**勝率を測り直す**。本文には何を直したか・トレースで観測した事実・
勝率の前後（1v1 / 2v2 / 3v3）を書く。マージは `/review-prs` が行う。
最後に `ExitWorktree` で抜ける。

## ルールの限界に当たったら

行動をどう直しても解けない、ルール側の問題だと判断したら、**config は触らずに issue を立てる。**

そう判断してよい例:

- 逃げる側と鬼の速度差が小さすぎて、平地では原理的に振り切れない
- 追跡時間が長すぎて、どんな隠れ方をしても最後は見つかる
- アリーナが狭すぎて、鬼の視界が全域を覆ってしまう
- 準備時間が短すぎて、箱を運ぶ戦術がそもそも成立しない

issue には**行動側で何を試して駄目だったか**を書く。それが無いと、
ルールを変える判断ができない。`docs/issues/README.md` の形式に従い、
`priority` と、変更を提案するルール（どの定数をどちらへ）を明記する。

ルール変更そのものは人間が判断する。このサイクルでは行わない。

## 目安

逃げる側の勝率は **どの構成でも 35〜50%** を目標にする。
どちらかに寄り切っていると、勝敗が立ち回りではなく初期配置で決まってしまう。

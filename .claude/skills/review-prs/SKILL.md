# PR のレビューとマージ

`/improve-ai` などが作った PR を確認して取り込む。
**中身を読まずにマージしないこと。** CI が緑でも、勝率の退行や決定論の破壊は CI では落ちない。

## 手順

### 1. open な PR を一覧する

```bash
gh pr list --state open
```

無ければ何もせず終了する（「PR はありません」とだけ報告する）。
複数あるときは古い順に 1 件ずつ処理する。

### 2. 中身を確認する

```bash
gh pr view <番号>
gh pr diff <番号>
gh pr checks <番号>
```

CI が走っていない、または失敗しているなら、ログを見て原因を書く。
失敗したままマージしない。

### 3. 差分を審査する

このプロジェクト固有の観点で見る。一般的なレビューよりここが重要。

- **`src/core` の決定論が壊れていないか。** `Math.random()`、`Date.now()`、
  実時間への依存が入っていないか。入っていればマージせず指摘する。
- **`src/core` が `three` や DOM を参照していないか。** ヘッドレス実行が壊れる。
- **勝率が報告されているか。** AI やバランスを触る PR は、本文に
  1v1 / 2v2 / 3v3 の数字と前回値があるはず。無ければ求める。
  ±10 ポイント以内の差を「改善」と主張している場合は、試合数を増やして測り直させる。
- **速度や視界を変えた PR で、AI の先読み距離も一緒に見直されているか。**
  片方だけだと AI が壁に突っ込むようになる（過去に実際に起きた）。
- **`docs/journal/` と `docs/issues/` が更新されているか。** 記録が無い変更は、
  次のサイクルで同じ調査を繰り返すことになる。

### 4. 判断する

- **問題なし** → マージする。
  ```bash
  gh pr merge <番号> --merge --delete-branch
  ```
  master への push で Pages が自動デプロイされる。
- **直せば通る軽微な問題** → 自分で直す。PR のブランチに追加コミットして push し、
  CI が通ってからマージする。何を直したかは PR にコメントで残す。
  ```bash
  gh pr comment <番号> --body "..."
  ```
- **設計の判断が要る / 勝率が退行している** → マージせず、`gh pr comment` で
  懸念を具体的に書く。何をどう確かめれば判断できるかまで書く。

### 5. 後始末

マージしたら master を最新にし、対応する issue が閉じられているか確認する。

```bash
git checkout master && git pull
gh pr list --state open
```

## 報告

処理した PR ごとに、番号・タイトル・判断（マージ / 保留）・理由を 1 行で報告する。
保留したものは何が足りないかを明示する。

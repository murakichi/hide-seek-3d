## 「逃げ道の多い場所へ逃げる」は逆効果だった（issue #9、不採用）

**やったこと** — issue #9「逃走が壁沿いの往復になる」を拾い、`fleeDirection` の採点に
「着地点から走り出せる向きの割合」（`fleeOpenWeight`）を加点する項を足した。
**測ったら 3 構成すべてで「入れない」が最良だったので、実装ごと取り下げた。**
このサイクルの成果物は計測と記録だけで、AI の挙動は変えていない。

**分かったこと 1 — 現象そのものは実在した。**
issue #9 はトレース 1 本を根拠にしていたので、まず全試合で数え直した（各 40 試合）。

```
                          1v1     3v3
逃走中に壁まで 6m 未満    48.7%   73.8%   （面積比なら 47%）
往復（6〜20 秒前の位置へ 5m 以内に戻る）  238 回  426 回
発見のうち直前 3 秒に往復していた  46.1%   38.5%
捕獲地点の壁までの距離     5.3m    3.9m   （一様なら 7.3m）
```

発見の 4 割前後が往復の直後。捕獲地点も壁寄りに偏っている。現象は確かにある。

**分かったこと 2 — 原因の見立てが間違っていた。**
`fleeDirection` の採点は、鬼から離れる項が最大 80 点前後で支配的なのに対し、
壁ペナルティは最大 24 点しかない。だからまっすぐ壁へ走るコースが常に最高得点になり、
着いた先で折り返すしかなくなる——という構造自体は読みどおりだった。
そこで「着いた先に逃げ道が残っているか」を加点したところ、こうなった:

```
fleeOpenWeight |  1v1    2v2    3v3      （各値 120 試合 / 3 シード、3v3 は 90 試合）
             0 | 53.3   65.0   65.6
            40 | 41.7   55.8   53.3
            80 | 26.7   57.5   48.9
```

1v1 は 3 シードすべてで下がった（52.5/57.5/50.0 → 22.5/35.0/22.5）。
**開けた場所は逃げ道が多いと同時に、鬼から見通せる場所でもある。**
この AI にとっては「逃げ道の数」より「視線が切れること」の方がはるかに価値が高い。
`fleeCoverBonus` が既に効いているところへ、それと逆を向く項を足していたことになる。

**意外だったこと — 往復は悪手ではないかもしれない。**
往復と発見の相関（46.1%）は本物だが、因果とは限らない。遮蔽のある一角に留まれば
往復もするし、鬼もそこを繰り返し探しに来る。両方が同じ原因から出ている可能性がある。
「見た目が下手な動き」を悪手だと決めつけて直しにかかったのが失敗の原因。
issue #9 には「往復＝悪手という前提を疑うべき」と書いて priority を low に下げた。

**分かったこと 3 — 煙幕は使えていた。**
issue #9 の未計測項目。1v1 で 40 試合あたり 75 回、3v3 で 217 回使われており、
捕獲時点の残りは平均 0.16〜0.26 回ぶん。ほぼ撃ち切っている。ここは問題ではない。

**分かったこと 4 — 逃げる側にはもう伸ばす余地を作るべきではない。**
現在の勝率は 1v1 53.0% / 2v2 55.0% / 3v3 56.0%（issue #11、各 300 試合）で、
目標帯 35〜50% の上。この状態で逃げる側の行動を良くする変更は、通っても害になる。
`/improve-hider` の次の仕事は勝率を上げることではなく、
**上げずに済む形の改善（見栄え・堅牢性）か、鬼側（issue #11）が片付くまで待つこと**。

**ついでに直したもの** — `npm run sim` に `--seed` を追加した。
これが無いために、`fleeTurnCost` の作業も #8 の作業も今回も、
複数シードで測るたびに使い捨てのハーネスを書き直していた。既定値は 1234 のまま。

**次にやること** — 鬼側（issue #11）が片付いて勝率が目標帯に戻るまで、
逃げる側は勝率を上げる変更を入れない。`threatKeepAway` / `threatMemory` の

## 箱を乗り越える向きを逃走候補に入れた（3 構成そろって +5〜7 ポイント）

**やったこと** — `fleeDirection` のレイが箱で止まっていたのを、**跳んで乗り越えられる
高さの箱なら通過扱い**に変えた。その向きを選んだときは詰まるのを待たずにジャンプする。

**分かったこと — 使える仕様を使っていなかった。**
小箱の高さは 1.3、素の登坂力 `CLIMB_REACH` は 1.64 なので、逃げる側は跳べば小箱に登れる。
ところが `fleeDirection` は `nav.isBlockedWorld` でレイを止めており、nav は登れる箱も
一律で「塞がれている」と扱う。結果 `clear < 2` で候補から外れ、
**箱を挟める向き＝逃げ道が増える向きを最初から全部捨てていた。**

勝率（`_ab.ts`、1v1・2v2 は各 300 試合、3v3 は 180 試合、3 シード）:

```
        前(master)   後
1v1       55.3      62.0   (+6.7)   シード別 65.0 / 65.0 / 56.0
2v2       59.0      64.0   (+5.0)   シード別 63.0 / 66.0 / 63.0
3v3       61.7      67.8   (+6.1)   シード別 70.0 / 75.0 / 58.3
```

前の値は自分でも測り直して 55.3% と一致した。3 構成が同じ向きに動いている。

`fleeClimbCost`（乗り越えの代償）は 0 / 8 / 20 / 32 / 45 と振ったが、1v1 は
57.5〜68.3 の間を行き来するだけで単調ではない。**効いているのは
「乗り越えを候補に入れたこと」自体**で、代償の値はほとんど効いていない。
どの値でも master を下回らなかったので、測った中で最良だった 20 を採用した。

**意外だったこと — 視線を切る回数は増えていない。**
「箱を挟んで射線を切る」つもりの変更だったが、1v1 の計測では視線を切った回数は
13.0 → 14.0 回/分でほぼ横ばい。それでも生存率は 52.5% → 72.5%、捕獲は 19 → 11 件。
逃走中に地面より高い位置に居るティックは 7.2% → 11.3%。

トレースを見ると効いているのは**遮蔽ではなく経路**だった。箱を越えられると逃げ道が
増えるので、鬼が回り込んでも詰みにならない。同じ seed=1234 の負け試合が
t=37.3 → t=63.6 まで延びた。前サイクルで `fleeOpenWeight`（開けた場所を好む）が
悪化したのと矛盾しないのが面白い。
**開けた場所へ出るのは駄目だが、閉じた場所の通り抜け方が増えるのは良い。**

**駄目だった案 1 — 鬼の予測位置を距離の基準にする（`fleeLeadTime`）。**
「追ってくる鬼の進路を横切って迎撃されている」という仮説を `_probe` で確かめ、
3v3 の捕獲の 37.0%（1v1 は 15.8%）が直前 1.5 秒に迎撃コースを走っており、
両構成とも捕獲の 43% は 2 秒前にまだ 10m 以上離れていた（最後の 1 秒で 8m 詰められている）。
そこで鬼の位置を速度で外挿し、その予測点からの距離で採点した。**壊滅した:**

```
lead(秒)  1v1    3v3      （各 120 / 90 試合、3 シード）
   0     53.3   63.3
   0.6   15.8   34.4
   1.0    5.0    6.7
   1.6    4.2    5.6
```

原因は明快で、**追ってくる相手の速度はこちらを向いている**ので、等速で外挿した
予測点は自分のほぼ真上に来る。それを距離の基準にすると「離れる向き」の勾配が消え、
どちらへ逃げればいいのか分からなくなる。
**追跡者を線形外挿しても、自分の遅延コピーが出てくるだけで情報にならない。**

**駄目だった案 2 — 予測点は使わず、時刻を合わせた「すれ違い」だけ減点する。**
案 1 の反省を入れ、距離の採点は今の位置のまま、0.35 / 0.7 / 1.0 倍の時刻で
自分と鬼の位置を突き合わせ、近すぎるコースだけ減点した。これも単調に悪化:
1v1 で 53.3 → 42.5（0.6 秒）→ 36.7（1.0 秒）→ 32.5（1.6 秒）。
理由は同じで、鬼が追ってくる以上**正しく逃げている向きほど鬼の未来位置の近くを通る**ので、
減点が正解の方向にばかり当たる。追跡者相手の先読みは、この形では成立しない。

**次にやること** — 高さの仕様がまだ丸ごと余っている（issue #13）。
`CATCH_VERTICAL` は 1.6 で大箱の高さは 2.2 なので、**大箱の上に立つと地上の鬼からは
捕獲判定が成立しない**（`src/core/game.ts` の捕獲判定）。素の登坂力 1.64 では大箱に
直接は登れないが、小箱を踏み台にする（2.2 − 1.3 = 0.9）・ランプ・ジャンプ台
（到達高 3.0）の 3 経路がすでに実装済みで、`hider.ts` はそのどれも参照していない。
今回のトレースでも捕まったときの高さは 1.2（小箱の上）で `CATCH_VERTICAL` に
届いていなかった。上の「箱を縦に積める」案が入れば踏み台を自作できるので、噛み合う。

## 箱を持ち上げて積めるようにした

**やったこと** — 箱を掴んだままジャンプすると箱も持ち上がり、別の箱の上で手を離すと
積み上がるようにした。ユーザーからの要望（戦略の幅を増やしたい）。

**設計** — `Obstacle` に底面の高さ `y` を足し、上面を `y + h` にした。
既存の障害物はすべて `y = 0` なので `h` の意味は変わらない。
掴んでいる間、箱の底は持ち手の足元に付いてくる。手を離すと落ち、
真下の箱の上面か地面で止まる。

**判断が要ったところ — 垂直の重なりをどこまで許すか。**
ジャンプの頂点は 1.29 m、低い箱の高さは 1.3 m。素直に「1 mm でも重なったら置けない」に
すると、跳んでも 0.007 m 足りずに低い箱の上へ載せられない。
そこで垂直の重なりが `STEP_HEIGHT`（0.35）以内なら「上に乗っている」とみなすことにした。
エージェントが段差を乗り越えるのと同じ許容なので、新しい概念を持ち込まずに済む。
副産物として、**大きい箱（2.2 m）の上には跳んでも載せられない**（重なりが 0.9 m）。
ジャンプ台（頂点 3.0 m）が要る。段階が生まれたので、そのまま仕様にした。

**意外だったこと — 何も積まなくても勝率が動いた。**
実装直後の 1v1 が 56.7% → 61.7%（各 60 試合）。積む操作は入れていないのに動いたので
おかしいと思って調べたら、**箱をジャンプ台の上に置けるようになっていた**。
ジャンプ台は高さ 0.25 m なので、垂直の重なりが許容 0.35 以内に収まってしまう。
台を塞ぐと踏めなくなるので、ジャンプ台だけは従来どおり footprint ごと置けないままにした。

それでも差が残ったが、こちらは原因が違って、**AI が箱を掴んだまま既にジャンプしていた**。
つまり機能が実際に働いていた。バグではない。

**効いたかどうか — バランスは動かなかった。**

| 構成 | 変更前 | 変更後 | 試合数 |
| --- | --- | --- | --- |
| 1v1 | 55.3% | 55.3% | 各 300（100 × 3 シード） |
| 2v2 | 59.0% | 59.7% | 各 300 |
| 3v3 | 61.7% | 60.0% | 各 180 |

3 構成の向きが揃わないので、判定基準どおり「差なし」。理由ははっきりしていて、
**AI がまだ意図的に積んでいない**（追跡開始時点で積まれている箱は 0.03〜0.33 個/試合、
そのうち「目線より低かった箱が積まれて遮蔽になった」のは 0.00〜0.13 個/試合）。
運搬中につかえたら跳ぶ、という最小限の橋渡しだけ入れてあるが、
積む場所を選ぶ判断は入れていない（それは逃げる側のサイクルの仕事）。

物理として成立していることは `src/sim/_stacktest.ts` で確認した。
入力を手で組んで、掴む → 跳ぶ → 運ぶ → 離す、で下の箱の上面 1.30 に着地する。

**次にやること** — 積み方の作り込みを issue にして `/improve-hider` へ渡した。
ただし逃げる側は現在 55〜60% で目標帯の上なので、鬼側（issue #11）が先。
遮蔽が増えると逃げる側がさらに強くなる可能性があるため、
積むようになった時点で必ず測り直すこと。

なお 8/10 のサイクルで「配置された箱の高さを 1.3 → 1.5 にしても勝率は動かない」と
測っている。今回は「プレイヤーが積み上げて 2.6 m を作る」話で軸が違うが、
**遮蔽を増やしても勝敗が動かなかった前例がある**ことは踏まえておくこと。


## 鬼が追いつけなかったのは、相手の現在位置を追っていたから

**やったこと** — 鬼の追跡目標を、相手の**現在位置**から、速度で先読みした
**迎撃点**に変えた（`chaseLeadTime`、既定 0.6 秒）。issue #11 の対応。

**分かったこと — トレースで見た事実がそのまま原因だった。**
1v1 の逃げ切られ試合（seed=1234）で、鬼は t=49 以降ほぼずっと `chase` 状態なのに
一度も距離を詰められていなかった。

```
t=50 距離 13.7 / t=55 距離 9.3 / t=60 距離 9.2 / t=65 距離 9.3
t=70 距離 10.8 / t=75 距離 9.2 / t=85 距離 12.0 / t=90 距離 9.0 / t=100 距離 9.1
```

50 秒追って 9〜13 m のまま。鬼は逃げ側より遅い（8.8 対 9.4）ので、
現在位置を追う純追尾では真後ろにつくだけで**原理的に追いつけない**。
逃げ側は激しく方向転換しているので、先読みして内側を取れば詰められる。

同一コードでの A/B（`_sweep.ts`、1v1・2v2 各 300 試合 / 3v3 180 試合、3 シード合算）:

```
構成 | 純追尾(0)  迎撃(0.6) |  差   | シード別
1v1  |   61.0%     29.7%   | -31.3 | 63/64/56 → 28/29/32
2v2  |   61.7%     45.7%   | -16.0 | 62/61/62 → 46/47/44
3v3  |   65.0%     60.6%   |  -4.4 | 71.7/73.3/50.0 → 61.7/58.3/61.7
```

9 個のシード別の値のうち 8 個が改善。3v3 の 1 つ（50.0 → 61.7）だけ逆を向いた。
**3v3 は効きが弱い。** 鬼が 3 人いる方が取り逃しているのは、迎撃を入れても変わらない。

**先読みしすぎると逆に悪化する。** 0.6 秒が最良で、1.2 秒・2 秒はほとんど効かない
（80 試合 ×2 シードで 1v1: 0→23.2, 0.6→9.4, 1.2→18.8, 2→17.5）。
相手が曲がる前提の位置へ先に行ってしまい、直進されると置いていかれる。
「先読みは長いほど賢い」ではなかった。

**視線は相手に置いたままにする必要がある。** 迎撃点を見ると視野角（115 度）から
相手が外れ、回り込んでいる最中に見失う。目標と視線を分離した。

**駄目だった案 1: ジャンプ推進で速度負けを覆す。** `JUMP_IMPULSE_CAP` が 1.18 なので、
跳びながら走れば 8.8 × 1.18 = 10.4 m/s になり逃げ側の 9.4 を上回る、と考えた。
**コードを読んだ時点で棄却。** 空中加速度 34 m/s² が即座に速度を基準値へ引き戻すので、
増速は約 0.05 秒しか持たない。1 ジャンプあたりの得は約 7 cm で、

## 勝率の測定を CI へ移した

**やったこと** — 手元の PC が重いという相談から、勝率測定を PR の CI に移した
（`.github/workflows/winrate.yml`、`src/sim/compare.ts`、`src/sim/report.ts`）。

**測ったこと — 1 試合のコストは構成でかなり違う。**

```
1v1   3.4 秒 / 試合    （初補足 71 秒。決着が遅い＝長く回る）
2v2  10.8 秒 / 試合    ← 最も重い
3v3   5.2 秒 / 試合    （初補足 38 秒。早く決着するぶん安い）
```

人数が増えるほど重い、ではない。**試合が何秒続くか**が支配的で、3v3 は早々に
1 人目が捕まって決着するので 2v2 より安い。`/improve-seeker` の手順どおり
80 試合 × 3 構成を変更前後で回すと 480 試合 ≈ 86 分ぶん CPU を占有していた。

**設計 — 比較対象からは `runSeries` だけを import する。**
CI は PR のベースコミットを `git worktree` で別ディレクトリに出し、head 側の
`compare.ts` がそこの `src/sim/headless.ts` を動的 import する。ベース側の CLI や
オプションには一切触らない。こうしないと、**この PR がマージされる前の master には
`--json` も `compare.ts` も無い**ので、初回の CI が自分自身で落ちる。
「新しい機能を CI に足すとき、比較対象は必ず古い」という制約は先に効かせておく。

`src/ai` と `src/core` が `three` も JSON import も参照していないおかげで、
ベースツリー側に `node_modules` が無くても head の tsx だけで動く。
決定論の縛りが、そのまま「どこで測っても同じ」を保証している。

**意外だったこと — 差分を出せるようになったのが本題だった。**
狙いは CPU を空けることだったが、結果として **master とこの PR を同じ seed 列で
両方走らせて差分を出す**形になった。今までは「前回の測定値を覚えておいて比べる」
運用で、サイクル中に master が動くたびに基準値が古くなって測り直していた
（この日だけで 2 回踏んでいる）。ベースを毎回その場で測り直すので、この問題自体が消える。

**動かして分かったこと — 遅かったのはコードではなく、この PC の混み具合だった。**
初回の CI は 12 ジョブすべて 21 秒〜1 分 13 秒で終わり、600 試合が壁時計 2 分半で片付いた。
ジョブ内の実測は **2v2 で約 0.9 秒 / 試合**。手元の 10.8 秒とは 10 倍以上違う。
`npm run sim` が重かったのは実装の問題ではなく、**改善ループを並行して回している間は
CPU を取り合っていた**ため。「遅い」を実装の欠陥だと決めつけて最適化に入らなくてよかった。
1 台のマシンで測る限り、測定は他の作業と必ず競合する。CI へ出すのはその競合を消す手でもある。

差分はどの構成も 0.0 pt で、seed ごとの内訳も head と base が完全に一致した。
別ツリーから `runSeries` を import する経路が決定論を保っていることの確認になった。

**次にやること** — 測定が実質ただになったので、`--games` を増やす余地がある
（今は構成あたり 100 試合で ±10 pt）。1 構成あたり 300 試合でも壁時計は数分のはず。
必要になったら `gh workflow run 勝率 -f games=50` で試してから既定値を上げる。

なお 8/10 のサイクルで「配置された箱の高さを 1.3 → 1.5 にしても勝率は動かない」と
測っている。今回は「プレイヤーが積み上げて 2.6 m を作る」話で軸が違うが、
**遮蔽を増やしても勝敗が動かなかった前例がある**ことは踏まえておくこと。

## 追跡時間の人数補正が逆を向いていた

**やったこと** — `huntTimeFor` の人数補正を反転した（人数が増えるほど**長く**）。
追跡時間は 1v1 70 → 56 秒、2v2 62 秒のまま、3v3 54 → 68 秒。
あわせて `SEEKER_DASH_COST` を 52 → 34 にする前サイクルの PR #19 を取り下げた。

**分かったこと 1 — 並列で作った PR は、合わせると本当に壊れる。**
前サイクルで `SEEKER_DASH_COST` 52 → 34 を出した（単独で 47.0 / 48.0 / 51.1%）。
同時に鬼側から PR #18（迎撃点を追う）が出ていて、こちらも単独で 29.7 / 45.7 / 60.6%。
**両方入れると 15.0 / 31.0 / 50.6%** で、1v1 は目標帯を 20 ポイント下回った。
どちらも「単独では改善」だったが、同じ問題（鬼が追いつけない）を二重に殴っていた。
CLAUDE.md の警告そのままの事故で、実際に起きた。

**分かったこと 2 — 定数では直せない形の崩れがあった。**
#18 の上で `SEEKER_DASH_COST` を振っても、52 で 28.3 / 45.0 / 57.8、
34 で 15.0 / 31.0 / 50.6。**1v1 を帯に入れると 3v3 が上に外れる。**
この定数は全構成をほぼ同じだけ動かすので、構成間の開き（約 30 ポイント）は縮まらない。
人数で差が付くレバーは `huntTimeFor` しかない。

**意外だったこと — その `huntTimeFor` が逆を向いていた。**
元の式は人数が増えるほど追跡時間を**短く**していた（70 / 62 / 54 秒）。
理屈は「鬼が増えれば探索が速くなるので、そのぶん短くして釣り合いを取る」。
ところが実測では逃げ側勝率が 28.3 → 45.0 → 57.8% と人数に対して単調に**上がって**いた。
探索が速くなる効果より「1 人でも残れば勝ち」の増幅の方が強い。
つまり**最も強い側に最も短い時間を与えていて、開きを広げる方向に効いていた。**

反転（56 / 62 / 68 秒）したら 44.0 / 45.0 / 48.3% で 3 構成とも帯に入り、
開きは 29.5 → 4.3 ポイントになった。
**2v2 は追跡時間が変わらないので 45.0% で完全に不動**だった。
狙った機構だけが動いたことの裏付けになる、いい対照群だった。

**分かったこと 3 — この補正は行動側の状態に依存する。**
#18 抜きの master 単体で同じ反転を測ると 68.7 / 65.0 / 53.3% で、1v1 が大きく上振れして
**逆効果**になる。#18 は 1v1 の鬼を劇的に強くする（61.0 → 29.7%）のに
3v3 はほとんど変えない（65.0 → 60.6%）ので、人数に対する傾きそのものを変える。
補正はその傾きに合わせて決まるので、**行動側が大きく動いたら毎回測り直す**しかない。
そのため今回の PR は #18 のブランチの上に積んで、順序を強制した。

**次にやること** — #18 → 今回の順でマージされたら、master で測り直して帯に入っているか確認する。
逃げる側の issue #10（ダッシュを使わない）が直ると上振れするので、そのときも測り直し。

## 「前に見つけた場所をまた見に行く」は効かなかった（不採用）

**やったこと** — 鬼に「過去に発見した地点」を覚えさせ、巡回先の採点で加点した
（`sightingLure` / `sightingMemory`）。**3 構成を測って取り下げた。**
このサイクルの成果物は計測と記録だけで、AI の挙動は変えていない。
PR #23（鬼の分散）の上に積んで測っている。

**現象そのものは実在した。** 1v1 の逃げ切られ試合のトレースで、逃走者は
同じ拠点（-11,15 付近）へ何度も戻り、鬼はそこで 4 回発見していた
（t=33.3 / 35.1 / 64.3 / 86.7）。にもかかわらず鬼は毎回そこを離れ、
アリーナ全体を巡回し直していた。

```
t=42 patrol goal=(-10,21)  t=48 (14,11)   t=54 (8,-19)
t=60 (-18,-9)   t=72 (-6,15)   t=96 (20,8)   t=102 (-12,-12)
```

鬼が持つ `seekerExplore` は「このセルを最後に**見た**時刻」でしかなく、
「そこで実際に**見つけた**」という情報を持っていない。後者の方が強い手がかりのはず——
という理屈は通っていた。**が、測ると効かない。**

```
構成 | lure 0  lure 12  lure 25 |   （1v1・2v2 各 300 試合 / 3v3 180 試合、3 シード）
1v1  |  28.3%   29.7%    27.3%  | 狙った構成が -1.0 ポイント（ノイズの範囲）
2v2  |   4.0%      —     10.3%  | +6.3 ポイント悪化
3v3  |   5.6%      —      5.0%  | -0.6（ノイズ）
```

1v1 のシード別は 27/28/30 → 28/24/30 で、向きすら揃っていない。
**狙った構成で効かず、別の構成を悪化させたので不採用。**

**なぜ悪化したのかは分かっていない。** 見立てとしては、PR #23 で入れた
「1 つの手がかりへ向かうのは 1 人まで、あぶれた鬼は巡回」が、
**巡回が盤面を広く覆うことを前提にしている**こと。そこへ「前に見つけた場所」への
加点を足すと巡回先が数か所に集まり、せっかく分散させた網をまた狭めてしまう。
2v2 でだけ悪化したことと整合するが、確かめてはいない。

**教訓 —「良い情報を足す」ことが常に良いとは限らない。** 加点は他の項と競合する。
今回は直前のサイクルで入れた仕組みと正面から衝突していた。
1 つ前の自分の変更が何を前提にしているかを見ずに足すと、こうなる。

**測定環境について** — 掃引が 25 分経っても終わらず、プロセスを調べたところ
node が 50 個動いていた。**うち自分のものは 3 個だけ**で、残りは MCP サーバー
（`@napolab/gpt-image`、`@playwright/mcp`）と、**並行して走っている別ループ**の
測定だった（`feat-team-coop-foundation`、`fix-hider-highground` の各 worktree と
メインチェックアウトで 300 試合の sim が動いていた）。
複数ループを同時に回すと測定同士が CPU を奪い合う。
**自分の測定が遅いときは、まず他ループが走っていないかを見ること。**

止めるときは**コマンドラインを見て自分のものだけを選ぶこと。** node プロセスには
MCP サーバーと他ループの測定が混ざっており、名前だけで一括 kill すると
他人の作業とツールを壊す（Claude Code 自体も node で動いている）。

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -like '*<自分の worktree 名>*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

**なお、この直後にマージされた別サイクルで測定用の CI が入っていた。**
`gh workflow run 勝率 -f games=50` で GitHub 側に投げれば、600 試合が壁時計 2 分半、
1 試合あたり 0.9 秒（手元の 10.8 秒の 10 分の 1 以下）で終わる。
**混んだ手元で回すより CI に投げる方が速い。** 次サイクルからはそちらを使う。

**次にやること** — 1v1 は依然として鬼の弱点（逃げ側 28.3%。2v2 4.0% / 3v3 5.6% と
比べて突出して高い）。ただし今回の「巡回先の重み付け」方向は外れたので、別の筋を探す。
トレースで見る限り、鬼は拠点を何度も通過しているのに**通過しただけで見つけられていない**
場面がある（t=54 に鬼が (8,-19)、逃走者が (-11.5,15.7)）。
探索の粒度ではなく、視線の振り方（`scanSpeed`）や、
拠点付近での立ち止まり方を見る方が筋が良いかもしれない。

## 高所（捕獲されない高さ）を取りに行く案は 2 通りとも不採用

**やったこと** — issue #13 / #21 の「高さの仕様が丸ごと余っている」を拾い、
2 通り実装して**どちらも採用に至らなかった**。AI のコードは master のまま。

**分かったこと 1 — 賞金は本物だった。**
捕獲は水平距離と `|y の差| < CATCH_VERTICAL`(1.6) の両方が要る（`src/core/game.ts`）。
`_probe` で数えると:

```
                                  1v1        3v3
追跡中に y > 1.6 に居たティック   3.56%      4.26%
その高さで捕まった回数           0 / 11 件   1 / 77 件
1 人あたりの到達最高高度          2.93       2.50
高所候補（上面 > 1.6）/試合       4.4 個     6.9 個
うち踏み台が 3m 以内に無いもの    2.6 個     3.9 個
```

**高さ 1.6 を超えている間、逃げる側は 88 件中 87 件で捕まっていない。**
しかもそこに居るのは追跡時間の 4% 前後だけ。伸びしろは大きい。
「踏み台が近くに無い高所」＝鬼が登れない足場も 1 試合に 2.6〜3.9 個あり、
95〜100% の試合に最低 1 つ存在する。

**駄目だった案 1 — 高所に居るなら降りない（`holdHighGround`）。**
足場の上に立っていて、まだ誰も同じ高さに登ってきていないなら、その場で粘る。
逃走の方向決めは高さを見ないので、放っておくと自分から降りてしまう——という読み。
実装は素直に効いたが、**勝率は動かなかった**（1v1・2v2 各 300 試合、3v3 180 試合）:

```
        前     後
1v1    61.0   60.7   (-0.3)
2v2    65.0   64.7   (-0.3)
3v3    61.1   62.8   (+1.7)
```

3 構成の向きが揃わないので「差なし」。理由ははっきりしていて、
**そもそも高所に居る時間が 4% しかない**ので、そこでの振る舞いを直しても総量が動かない。

**駄目だった案 2 — 逃走先の採点で高所へ近づくコースを優遇（`fleePerchBonus`）。**
総量を増やしにいったが、**単調に壊滅した**（1v1、各 120 試合 / 3 シード）:

```
perchBonus   0 → 65.8    6 → 44.2    15 → 28.3    30 → 17.5
```

高所へ向かうぶんだけ「鬼から離れる」「遮蔽を取る」を捨てるうえ、
登っている間は足が止まって丸見えになる。

**意外だったこと — 失敗が同じ形で 3 回続いている。**

| 何を足したか | 結果 |
| --- | --- |
| `fleeOpenWeight`（開けた場所を優遇） | 単調に悪化 |
| `fleeLeadTime`（鬼の予測位置を避ける） | 壊滅（53.3 → 5.0） |
| `fleePerchBonus`（高所を優遇） | 壊滅（65.8 → 17.5） |

**`fleeDirection` の採点に新しい項を足す変更は、3 回連続で失敗している。**
一方、この期間で唯一効いた変更（PR #14、箱を乗り越える向きを候補に入れる、+5〜7 ポイント）は
**採点を触らず、候補そのものを増やした**ものだった。

読みとしては、`fleeDirection` の既存の項（進める距離・鬼から離れる・遮蔽・向きの保持）は
既に噛み合っていて、そこへ別の目的関数を混ぜると必ずどれかを削ることになる。
**高所を取りに行きたいなら、逃走の採点に混ぜるのではなく、
「逃走とは別のモード」として実装する必要がある**（例: 鬼が遠いうちに足場へ移動しておく、
追われたら通常の逃走に戻る）。次に試すならその形。

**次にやること** — issue #13 / #21 は open のまま。上の反省をコメントに残した。
実装するなら「逃走中の採点」ではなく「追われていない間の待機先を高所にする」形。
`evade` の非逃走分岐（今は拠点へ帰るだけ）を高所待機に変えるのが素直で、
既存の逃走ロジックと競合しない。

## 高所は 4 回目も駄目。代わりに「鬼を呼び寄せている」ことが分かった

**やったこと** — issue #13 を、前サイクルで自分が書いた設計どおり
「逃走の採点には触らず、**追われていない間の待機先**を拠点から高所に差し替える」形で実装した。
機構は狙いどおり効いたが、**勝率は動かなかったので取り下げた。**

**分かったこと 1 — 機構は効いたのに勝率が動かない。**
CI（各構成 100 試合、seed 4 本）:

```
        master   この PR   差分
1v1      27.0     24.0     -3.0
2v2      10.0     11.0     +1.0
3v3       1.0      1.0     +0.0
```

高さ 1.6 超に居たティックは 4.26% → **9.52%** と倍増している（3v3、30 試合）。
それでも勝率は動かない。**高所に居る時間を倍にしても足りない**か、
あるいは高所へ行くこと自体のコスト（拠点の遮蔽を捨てて開けた足場に立つ、
登る間に足が止まる）が、捕獲されない利得と釣り合ってしまっている。

これで高所の攻略は **4 回目の失敗**（`fleePerchBonus` / 降りない / 待機先の差し替え / 今回）。
「捕獲 88 件中 87 件が高さ 1.6 未満」という賞金の大きさは本物なのに、
**取りに行く手段がことごとく成立しない。**次に触るならまず
「なぜ高所に居ても勝率が上がらないのか」を測る側から入るべき。

**分かったこと 2 — 運搬の空回りは「再挑戦」ではなく「検出の遅れ」だった。**
ユーザーから「箱が壁に引っ掛かって同じ動作を繰り返す」と指摘を受けて測った（3v3 / 30 試合）:

```
箱を掴んでいた時間            18.8 秒/試合（準備は 32 秒）
うち箱が動いていない時間       6.9 秒/試合（36.9%）
「前にも掴んだ箱」の掴み直し   610 回中 472 回（77.4%）
```

**確かに空回りしていた。**そこで `abandon()` の避ける時間を 6 秒 → 無限大にしたら、
**数字がまったく動かなかった**（36.9% → 37.1%、77.4% → 77.6%）。
つまり再挑戦は `planJob` 経由ではない。

内訳を計算すると、空回り 6.9 秒 ÷ 詰まり判定 1.2 秒 ≒ 諦めた回数で説明がつく。
**1 回引っ掛かるたびに必ず 1.2 秒を捨てている**だけで、同じ箱に戻っているのではなかった。
掴み直し 77% の方は、`fetch` の `act.grab = reach < GRAB_RANGE` が間合いの前後で
反転して同じ箱を離しては掴み直す動きを拾っていた可能性が高い。**指標の作り方が悪かった。**
issue #31 に訂正を書いた。狙う場所は「避ける時間」ではなく「検出しきい値」と
「そもそも引っ掛かる原因」。

**分かったこと 3 — 逃げる側は自分の居場所を宣伝していた（issue #32）。**
ユーザーから「鬼は動いた箱の方へ向かうので、逆にブラフに使えるのでは」と提案を受けて
`seeker.ts` を読んだところ、巡回先の採点に

```ts
if (bd < 5) score += p.lockedBoxLure * (1 - bd / 5);   // lockedBoxLure = 8
```

があった。**ロックされた箱の 5m 以内は巡回先として最大 +8 点される。**
逃げる側は 1 試合あたり 7.5 個の箱を**自分の拠点の外周に**並べてロックしているので、
拠点の位置に鬼を呼ぶ標識を 7〜8 本立てていることになる。
砦を作る行為そのものが自分の首を絞めている可能性がある。

実験としては「拠点の箱をロックしない」を測るのが一番きれいで、
**誘引の害と壁の利をそのまま分離できる**。issue #32 に切り出した。

**次にやること** — issue #32（ロックが鬼を呼ぶ）を最優先で測る。
高所（#13 / #21）は手段が 4 回とも成立していないので、いったん置く。
issue #31 は「検出しきい値 1.2 秒を 0.5〜0.8 に下げる」を CI で測るのが次の一手。

## 味方同士の協調の土台を入れた

**やったこと** — `src/ai/coop.ts` に `TeamCoop` を作り、チームごとに 1 つ持たせた。
バラバラだった 3 つの共有（`shelters` / `seekerExplore` / `seekerGoals`）を載せ替えた。
**戦術は 1 つも変えていない。** 挙動が変わっていないことは、試合ごとの結果を
指紋として出して差分ゼロで確認した（`src/sim/_fingerprint.ts`）。

**分かったこと 1 — 協調には強さの違う 3 段階があり、混ぜると事故る。**

| 段階 | 仕組み | 強制力 | 既存の該当 |
| --- | --- | --- | --- |
| 共有知識 | `grid` | 無し（誰の持ち物でもない事実） | `seekerExplore` |
| 意図の共有 | `post` / `others` | 無し（参考にするだけ） | `seekerGoals` |
| 予約 | `claim` / `holder` | 排他（1 つを取り合わない） | `shelters` |

弱い方から使うのが原則。「近くに寄りすぎない」程度で足りるなら意図の共有で済み、
予約にすると取り合いと乗っ取りの面倒を抱え込む。既存の 3 つがちょうど 3 段階に
1 つずつ対応していたので、分類はこれで足りると判断した。

**分かったこと 2 — 「見たものの共有」は既にゲーム本体にあった。**
`game.state.memory[team]` に「最後に見た敵の位置と時刻」がチーム共有で入っている
（`src/core/vision.ts` の `updateMemory`）。1 人が見つければ全員が知る。
協調の土台に作り直しそうになったので、`coop.ts` の冒頭に「ここには無い」と書いた。

**踏んだ設計上の罠 1 — 予約に寿命を付けたら、拠点が消えた。**
「主張し直されなければ捨てる」を既定にしたところ、試合開始時に 1 度だけ割り当てる
拠点が 0.4 秒後の掃除で消えた。予約ごとに寿命を持てるようにして、拠点は
`ttl: Infinity` にした。**「一度だけ主張して放置」は既定のままだと事故になる**ので、
その旨を `ClaimOptions` のコメントに書いた。

**踏んだ設計上の罠 2 — 乗っ取りに閾値を入れないと毎ティック入れ替わる。**
点差 0 で奪えるようにすると、わずかな差で持ち主が毎ティック交代する。
`fleeDirection` が毎ティック方向を選び直して速度が乗らなかったのと同じ形の事故
（あちらは平均 10.7 度/tick の振れとして観測された）。最初から `STEAL_MARGIN` を
入れておいた。実際に取り合う予約を足すときは `params.ts` へ移して自動探索に載せること。

**分かったこと 3 — 逃げる側は追跡中まったく協調していなかった。**
`shelters` は開始時の 1 回きりの割り当てで、追跡が始まった後に味方を参照する箇所が
1 つも無い。鬼は `seekerGoals` で担当を散らしているのに、逃げる側は
「味方を鬼の方へ引き込まない」「囮になる」といった判断を持っていない。
土台ができたので、そこは行動側のサイクルの仕事として issue にした。

**観測を先に用意した。** `npm run trace -- --interval 3` に予約と意図の行を足した。
このプロジェクトは「集計値では原因に辿り着けない」を何度も踏んでいる。
協調は「味方が譲り合って両方止まる」「同じ相手に全員が群がる」のような、
勝率にはじわっとしか出ない壊れ方をするので、先に見えるようにしておいた。

**次にやること** — 土台の上に戦術を載せるのは行動側のサイクル。issue を立てた。
バランス側は次に「小さい箱も視線を切る」（`BOX_HEIGHT_SMALL` 1.3 → 1.5）を測る。
8/10 に測って不採用にしたが、それは逃げ側が帯の下（24.7/35.3/38.3）にいた頃の話で、
今は帯の上寄りなので判断が変わる可能性が高い。

## 鬼が壁際で 54 秒間固まっていた（到達できない目標を選び直さない）

**やったこと** — 目標へ近づけない状態が `repickAfter` 秒続いたら、その目標を諦めて
選び直すようにした。issue #28（追跡の担当分け）を狙って協調の土台（PR #33）を
取り込んだところ、**トレースで別のもっと重い欠陥に当たった**ので、そちらを先に直した。

**分かったこと — 鬼が試合の後半ずっと動いていなかった。**
3v3 の逃げ切られ試合で、鬼 3 人が同時に停止していた。

```
鬼#3 (-21.0,5.5) が t=42→96 の 54 秒間 不動  goal=(14,11)（35m 先）
鬼#4 (6.8,20.4)  が t=48→96 の 48 秒間 不動  goal=(12,11)
鬼#5 (13.4,10.7) が t=60→96 の 36 秒間 不動  goal=(2,11)
```

その間 逃#0 は自由に動き回り、t=84 には鬼#5 の約 6m 先を通っている。
**追跡時間 68 秒のうち 50 秒以上、鬼が 1 人も探索していない試合があった。**

原因は 3 つが噛み合っていた。

1. `pickPatrolGoal` を選び直すのは**到達したときだけ**（`reached(..., 1.4)`）
2. 経路が取れないと `followPath` も `directIfClear` も向きを返さず、
   移動入力がゼロのまま `patrol` が維持される
3. `handleObstruction` の復帰処理（3 秒で goal を捨てる）は `findBlocker` に
   引っかかったときだけ働くが、**`findBlocker` は `o.kind === 'box'` しか見ていない**。
   壁際で詰まると復帰処理そのものが呼ばれない

**「到達したら選び直す」は、到達できる前提が崩れた瞬間に無限ループになる。**
箱を動かせる（PR #16 で積めるようにもなった）ゲームなので、
盤面は試合中に変わる。選んだ時点で到達可能でも、後から塞がれる。

**気づけた理由は協調の土台が意図をトレースに出していたこと。**
`意図 #3 patrol(14,11) #4 patrol(12,11) #5 patrol(2,11)` が 7 スナップショット
（42 秒ぶん）まったく同じで、座標も動いていなかった。
**勝率だけ見ていたら絶対に見つからない。** 3v3 の勝率は #23 の修正で既に
逃げ側 0〜4% まで落ちていて、「鬼は十分強い」と読めてしまう状態だった。
その裏で、鬼が半分の時間止まっていた。

**直し方** — 目標への最短距離を更新できない時間を数え、`repickAfter`（既定 2 秒）を
超えたら目標を捨てて選び直す。`chase` 中は対象外（動く相手を追っている間は
距離が縮まなくても正常）。諦めた目標は 12 秒のあいだ半径 5m を避ける。
**避けないと選び直しても同じ場所が最高点のままで、諦めた意味がなくなる。**

CI の測定（構成ごとに 4 seed × 25 試合＝100 試合）:

```
構成 | master   この PR |  差

## 囮ロックが効いた（issue #32、3 構成そろって +1〜2 ポイント）

**やったこと** — 「ロックした箱が鬼を呼ぶ」を 2 通り試して、2 番目が通った。
運ぶ仕事が無くなったあとの余り時間で、**拠点から 11m 以上離れた箱をロックして囮にする。**

**分かったこと 1 — 誘引は実在した。**
鬼の巡回先の採点はロック箱の 5m 以内を最大 `lockedBoxLure`(8) 点加点する。
逃げる側は 1 試合あたり 7.5 個をロックしており、**その 84.5% が拠点から 6m 以内**。
鬼は追跡時間の **36.3%** をロック箱の 5m 以内で過ごしていた（3v3 / 30 試合）。
準備フェーズ 32 秒で作った砦が、そのまま「ここに居ます」の標識になっていた。

**駄目だった案 — ロックをやめる。**
誘引の害と壁の利を分離する一番きれいな実験のつもりだった。CI（各構成 100 試合、seed 4 本）:

```

1v1      42.0      40.0      -2.0
2v2      10.0       6.0      -4.0
3v3       1.0       1.0      +0.0
```

**壁の利の方が大きかった。**固めないと鬼に押しのけられるので、
標識を消すために壁を捨てるのは割に合わない。

**効いた案 — 消すのではなく、離れた場所にも撒いて薄める。**

```
        master   囮ロック   差分
1v1      42.0      44.0     +2.0
2v2      10.0      11.0     +1.0
3v3       1.0       2.0     +1.0

**そのうち拠点から 6m 以内の割合が 84.5% → 61.8% に下がった**（3v3 / 30 試合）。
1v1 の初補足も 71.7 → 67.2 秒…ではなく、master 比で見ると囮版が短い。
勝率は上がっているので、見つかる時刻ではなく**見つかったあとの分散**が効いていると思われる。

**意外だったこと — 「害を消す」より「害を薄める」方が正しかった。**
最初の実験（ロックをやめる）は、誘引を 36.3% → 0% にできたのに勝率は下がった。
**同じ仕組みに、利と害が同居していた。**こういうときは片方を捨てるのではなく、
利を保ったまま害の指向性だけ壊す方が通る。
今回は「標識を消す」ではなく「標識を増やして意味を無くす」が正解だった。

**設計の注意** — 囮を取りに行くのは、運ぶ仕事が無くなったあとの余り時間だけにしてある
（`decoyLockMargin` = 10 秒を切ったら拾わない）。遠出して追跡開始に拠点へ戻れないのが
一番まずい負け筋なので、往復できる範囲（`decoyLockDist` の 1.6 倍）にも制限を入れた。

**次にやること** — 囮の効き幅は +1〜2 ポイントと小さい。`decoyLockDist` /

## 3v3 が 1% の理由は「見つかること」ではなく「壁に貼り付くこと」だった（不採用）

**やったこと** — 3v3 の勝率が 1%（1v1 は 42%）なので、何が違うのかを測ってから直しに行った。
**原因は特定できたが、直す 3 通りはどれも 3 構成の向きが揃わず、全部取り下げた。**

**分かったこと 1 — 発見の速さは 1v1 と変わらない。**（各 30 試合）

```
                              1v1     3v3
追跡開始から最初に見つかるまで  2.7秒   2.6秒
一度も見つからなかった人         0       0
拠点どうしの距離                 —     28.1m
追跡中の逃走者どうしの距離       —     25.9m
壁まで 3m 未満だったティック   20.2%   45.9%   （一様なら 25.6%）
```

**隠れ場所の分散は効いている（28m 離れている）。発見の速さも同じ。**
違うのは壁への貼り付きだけで、1v1 は一様分布より壁を避けているのに 3v3 は倍近く貼り付く。
トレースでも 3 人が外周（|x| や |z| が 20〜21）を走り、南西の隅で 2 人が 6m まで
近づいて 1 人の鬼に同時発見される試合を確認した。

**分かったこと 2 — 原因は採点の合算だった。**
`fleeDirection` は「鬼から離れられる距離」を**鬼ごとに合算**している。
1 人あたり最大 80 点前後なので 3 人いると 240 点。
壁のペナルティ（`wallGap < 6` で最大 24 点）は比較にならない。
**「全員から離れる」が「アリーナの外周へ逃げる」に化けていた。**

人数で割って平均にすると、機構は狙いどおり動いた（3v3 / 30 試合）:

```
壁まで 3m 未満                    45.9% → 38.2%
1 人の鬼が同時に 2 人以上を見ていた  19.3% → 10.3%
2 人以上が 8m 以内                 21.2% → 12.9%
```

**分かったこと 3 — それでも勝率にならない。** CI（各構成 100 試合 / seed 4 本）:

```
正規化           1v1     2v2     3v3
なし(master)    42.0    10.0     1.0
/ n             42.0     8.0     3.0    ← 3v3 は 3 倍だが 2v2 が -2
/ √n            42.0     4.0     2.0    ← 2v2 が -6 でさらに悪い
```

3v3 は狙いどおり上がる（1% → 3%）のに、**2v2 が必ず落ちる。**
2v2 では合算（＝2 倍）がちょうど良く効いていたということ。
どの正規化でも 3 構成が揃わないので不採用。

**駄目だった案 — 拠点の遮蔽評価を実際の視線判定に直す。**
`chooseShelters` の `cover` は `nav.isBlockedWorld`（経路探索のグリッド）で数えている。
あれは通れるかどうかしか見ておらず、**高さ 1.3 の小箱も「遮蔽」と数える**。
視線は目線 1.4 から引くので小箱は遮蔽にならない（箱の 6 割が小箱）。
**明確な誤用**なので `hasLineOfSight` に直したが、最初に見つかるまでは 2.6 → 2.9 秒、
壁貼り付きは 45.9% → 49.3% とほぼ動かず、取り下げた。
**隠れ場所の質は 3v3 の敗因ではない**（そもそも 1v1 と発見の速さが同じ）。
※ この誤用自体は残っている。PR #37（小箱 1.3 → 1.5）が入ると前提が変わるので、
そのときに測り直す価値がある。

**駄目だった案 — 味方回避を「一番近い味方だけ」にする。**
こちらも人数ぶん合算（最大 −42 点）していたので同じ疑いを持ったが、
壁貼り付きは 45.9% → 47.1% で変わらなかった。支配していたのは味方項ではなく脅威項。

**意外だったこと — 「壁に貼り付く」を直しても勝てない。**
壁貼り付きも同時発見も明確に減ったのに、勝率は 3v3 で +2 止まり。
**壁貼り付きは症状であって死因ではない**可能性が高い。
鬼 3 人が `VIEW_DIST` 19 で 44×44 のアリーナを覆っているので、
外周に居ようが中央に居ようが見つかり続ける、という方が説明として素直。
だとすると 3v3 は行動側では解けない可能性がある。

**次にやること** — 3v3 の 1% が行動側で解けるのかを、もう一段はっきりさせたい。
「見られている時間の割合」を 1v1 / 2v2 / 3v3 で比べて、
3v3 だけ常時見られているなら `/improve-balance` へ渡す材料になる。

## 3v3 は「常に見えている」のではなく「切っても 2.5 秒で拾われる」（issue #43 へ）

**やったこと** — 前サイクルの宿題「見られている時間の割合を 3 構成で比べる」を実行し、
そこから出た仮説を 1 つ実装して測り、**不採用にしたうえでバランス側へ issue を上げた。**

**分かったこと 1 — 前サイクルの見立ては外れだった。**

```
                            1v1     2v2     3v3
見られていたティック        31.6%   40.2%   33.1%
見失い(逃走者 1 人あたり)    6.7回   4.5回   3.4回
見失ってから再発見まで       3.9秒   2.6秒   2.5秒
捕まるまでの生存時間        34.9秒  22.9秒  16.0秒
```

前サイクルは「鬼 3 人が視界で覆っているから常時見えている」と書いたが、
**見られている割合は 3 構成ともほぼ同じ**だった。覆われてはいない。
違うのは**視線を切れる回数**（6.7 → 3.4 回）と**切れている時間**（3.9 → 2.5 秒）。
**切っても 2.5 秒で別の鬼に拾われる。**

**分かったこと 2 — 遮蔽ボーナスが 3v3 で死んでいた。**
`fleeDirection` の遮蔽加点は `seekers.every(...)` で、**全員の視線を同時に切る**
向きにしか点が入らない。鬼が 3 人いるとそんな向きはほとんど無いので、
この項は 3v3 で事実上 0 点のままだった。逃げる側は遮蔽を探すのをやめていた。

「切れた鬼の割合」で部分点を出す形に変えると、機構は動いた（3v3 / 30 試合）:
見られている割合 33.1% → 27.4%、そのまま逃げ切った件数 31 → 36、生存 1 → 3 人。
鬼が 1 人なら `hidden/1` が 0 か 1 なので **1v1 は定義上不変**で、
CI の 1v1 が ±0 になることが自己検証になる（実際に ±0 だった）。

**それでも勝率は動かない。** CI: 旧 master 上で 1v1 ±0 / 2v2 −3 / 3v3 +2、
PR #35 を取り込んだ新 master 上では 1v1 ±0 / 2v2 −4 / 3v3 ±0。

**意外だったこと — 手を替えても必ず「3v3 +2 / 2v2 −2〜4」になる。**
前サイクルの脅威項の正規化（/n）も、今回の遮蔽の割合化も、
まったく別の場所を触っているのに CI の差分がほぼ同じ形になった。
**3v3 を助ける変更は 2v2 を削る**という関係がある。2v2 では現状の設定が
ちょうど良く効いていて、3v3 向けに崩すと 2v2 が壊れる。

**測定でやらかしたこと — 土台違いの比較。**
CI の既定（各 100 試合）では差が誤差に埋もれるので、
`gh workflow run 勝率 -f games=100` で各 400 試合を回した。
ところが `workflow_dispatch` は head しか測らない（base が null）ので、
master 側も別途回して突き合わせた。**その間に master が PR #35 でを進んでいて、
1v1 が「定義上不変」のはずなのに 39.75% と 44.25% でずれた。**
そこで土台違いに気づけた。**「変わらないはずのものが変わったら測り方を疑う」**
という自己検証が実際に効いた例。

**次にやること** — 行動側の手は 5 通り全部失敗したので、issue #43（balance）へ上げた。
3v3 は 400 試合で 1 勝もしていない。提案したのは `VIEW_DIST`(19) を下げる、
鬼の人数に応じて `HUNT_TIME` を縮める、遮蔽の総量を人数に見合わせる、の 3 つ。
逃げる側としては、2v2 を壊さずに 3v3 だけ助ける手が見つかっていないので、
**ルール側が動くまでは 1v1 / 2v2 に効く筋（issue #21 の踏み台どけなど）を優先する。**

## 気配を遮蔽に貫かせても駄目だった。ただし「なぜ効かないか」が 1 段はっきりした

**やったこと** — 逃げる側の近距離察知（`HIDER_SENSE_DIST` = 9m）が遮蔽と煙を貫くようにし、
CI で 600 試合測って取り下げた。コードの変更は無し。

**予想を書いてから測った。外れた。**
「近距離で気づける機会は鬼の人数に比例するので、人数が多い構成ほど効くはず」と
PR に書いてから測ったところ、逆だった。

| 構成 | master | 貫く | 差分 |
| --- | --- | --- | --- |
| 1v1 | 42.0% | 47.0% | +5.0 |
| 2v2 | 10.0% | 7.0% | **−3.0** |
| 3v3 | 1.0% | 2.0% | +1.0 |

**意外だったこと — 機構は狙いどおり動いていた。効いた先が人数で反転した。**

| 構成 | 逃走モード | 見られている | 逃走中に壁 3m 未満 | 逃走中に 2 人以上に見られている |
| --- | --- | --- | --- | --- |
| 1v1 | 36.7% → 44.8% | 31.6% → 38.7% | 14.0% → 15.1% | 0% |
| 2v2 | 46.0% → 47.0% | 40.2% → 38.9% | 34.3% → 35.4% | 17.3% → 15.5% |
| 3v3 | 43.6% → 52.8% | 33.1% → 41.1% | 44.0% → 43.5% | 20.6% → 23.7% |

**3v3 は逃走モードの時間が +9.2 ポイント増えたのに、勝率は +1.0 しか動かない。**
1v1 は +8.1 ポイントの増加が +5.0 の勝率になっている。同じ「もっと逃げる」が、
人数によって得にも損にもなっている。

逃走中の内訳を見ると理由が分かる。3v3 では逃走中の 43.5% が壁 3m 未満、
23.7% が 2 人以上に見られている。PR #39 が特定した
「`fleeDirection` は鬼ごとの点数を合算するので、3 人だと壁ペナルティ 24 点が
240 点に埋もれて外周へ逃げる」がそのまま出ている。
**逃げれば逃げるほど壁際で挟まれる。**

**ここから引き出した一般則** — 逃げる側を強くするルール変更は、
**逃走の量を増やす形である限り 2v2 / 3v3 では payoff しない**。
逃走そのものが多人数で壊れているから、入り口を増やしても出口が詰まっている。
バランス側から逃げ側を持ち上げるなら、**逃走を経由しない形**
（準備フェーズ・時間・捕獲判定など）を選ぶこと。
これは今後のバランス案の足切り条件として使える。

**仮説が 1 つ潰れた** — 「遮蔽が逃げる側の索敵も切るから、遮蔽を増やしても効かない」は外れ。
貫くようにしても 2v2 は悪化した。`BOX_HEIGHT_SMALL` を上げると
3 構成そろって下がる理由は、まだ分かっていない。

**次にやること** — バランス側は逃走を経由しないレバーを探す。
ただし `fleeDirection` の多人数対応（行動側、PR #39 で 3 案とも取り下げ）が入ると
前提が変わるので、そちらの動きを見てから。

## 追跡の担当を分けた（効果は小さい。勝率が床に張り付いていて測れない）

**やったこと** — `pickVisiblePrey` に人数上限（`chaseMaxSeekers`、既定 1）を入れ、
既に味方が向かっている相手は避けて別の相手を選ぶようにした。issue #28。
前サイクルの「次にやること」の続きで、PR #35（固まり修正）の後。

**分かったこと 1 — 最初に書いた計測が、測りたいものを測っていなかった。**
「群がり」を数えるつもりで**視界の重なり**（何人の鬼がその逃走者を見ているか）を
数えていた。今回の修正が変えるのは**誰を追うか**であって、誰に見えるかではない。
案の定、修正前後で視界の重なりはほとんど動かず（19.0% → 18.3%）、
「効いていない」と誤読しかけた。協調の掲示（`targetId`）を数え直したら動いていた。

```
（3v3 / 30 試合、逃走者が 2 人以上生きているティックに対する割合）
                                  制限なし   1人まで
2 人以上の鬼が同じ相手を追っている   15.8%    13.6%
追われている逃走者 1 人あたりの鬼     1.25     1.20
追跡フェーズの総ティック             41130    38772   （試合が 5.7% 早く終わる）
```

**計測を書くときは「変えた対象そのもの」を数えているか確認すること。**
近い量なら動くだろう、では駄目だった。

**分かったこと 2 — 勝率では判定できなかった。**
CI（構成ごとに 100 試合、master は #35 込み）:

```
構成 | master  この PR |  差
1v1  |  37.0%   37.0%  | +0.0 pt
2v2  |   8.0%    7.0%  | -1.0 pt
3v3  |   0.0%    0.0%  | +0.0 pt
```

3v3 は既に 0.0% で、2v2 も 8.0%。**床に張り付いていて、良くなっても数字が動かない。**
唯一動いたのは 2v2 の -1.0 pt と、3v3 の初補足 41.1 → 40.6 秒。
悪化した構成は無い。機構が働いていることは上の担当重複で確認できているので採用したが、
**勝率を根拠には採用していない。**

前サイクルの「勝率が飽和している構成では数字だけ見ていても欠陥は見えない」が、
今度は逆向きに効いた。**欠陥が見えないだけでなく、直した効果も見えない。**
バランス側で逃げ側が帯に戻れば、この変更の価値は今より大きく出るはず。

**駄目だった案 — 見えている相手が全員埋まっていたら引き上げて別の場所を探す。**
`leadMaxSeekers`（#23）と同じ形にすれば効くと思ったが、構成で向きが逆になった
（3v3 は 1.3% → 0.0% と改善、2v2 は 5.0% → 6.3% と悪化。各 40 試合 ×2 シード）。
**「見えているのに誰も追わない」状態が生まれるのが 2v2 では損。**
鬼が 2 人しか居ないと、1 人が引き上げた時点で追跡が完全に切れる。
つまみを増やす価値が無いと判断して入れていない。

**次にやること** — 鬼側の残りは issue #17（ブースト活用）と #20（高所へ追えない）。
どちらも**今の勝率では効果を測れない**（床）。バランス側が逃げ側を帯へ戻すまで、
鬼側は「勝率で測れる改善」が枯れている状態。
測るなら勝率ではなく、初補足・担当重複・トレースの挙動で見ること。

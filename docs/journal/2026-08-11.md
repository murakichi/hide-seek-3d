# 2026-08-11

## 「逃げ道の多い場所へ逃げる」は逆効果だった（issue #9、不採用）

**やったこと** — issue #9「逃走が壁沿いの往復になる」を拾い、`fleeDirection` の採点に
「着地点から走り出せる向きの割合」（`fleeOpenWeight`）を加点する項を足した。
**測ったら 3 構成すべてで「入れない」が最良だったので、実装ごと取り下げた。**
このサイクルの成果物は計測と記録だけで、AI の挙動は変えていない。

**分かったこと 1 — 現象そのものは実在した。**
issue #9 はトレース 1 本を根拠にしていたので、まず全試合で数え直した（各 40 試合）。

```
                          1v1     3v3
逃走中に壁まで 6m 未満    48.7%   73.8%   （面積比なら 47%）
往復（6〜20 秒前の位置へ 5m 以内に戻る）  238 回  426 回
発見のうち直前 3 秒に往復していた  46.1%   38.5%
捕獲地点の壁までの距離     5.3m    3.9m   （一様なら 7.3m）
```

発見の 4 割前後が往復の直後。捕獲地点も壁寄りに偏っている。現象は確かにある。

**分かったこと 2 — 原因の見立てが間違っていた。**
`fleeDirection` の採点は、鬼から離れる項が最大 80 点前後で支配的なのに対し、
壁ペナルティは最大 24 点しかない。だからまっすぐ壁へ走るコースが常に最高得点になり、
着いた先で折り返すしかなくなる——という構造自体は読みどおりだった。
そこで「着いた先に逃げ道が残っているか」を加点したところ、こうなった:

```
fleeOpenWeight |  1v1    2v2    3v3      （各値 120 試合 / 3 シード、3v3 は 90 試合）
             0 | 53.3   65.0   65.6
            40 | 41.7   55.8   53.3
            80 | 26.7   57.5   48.9
```

1v1 は 3 シードすべてで下がった（52.5/57.5/50.0 → 22.5/35.0/22.5）。
**開けた場所は逃げ道が多いと同時に、鬼から見通せる場所でもある。**
この AI にとっては「逃げ道の数」より「視線が切れること」の方がはるかに価値が高い。
`fleeCoverBonus` が既に効いているところへ、それと逆を向く項を足していたことになる。

**意外だったこと — 往復は悪手ではないかもしれない。**
往復と発見の相関（46.1%）は本物だが、因果とは限らない。遮蔽のある一角に留まれば
往復もするし、鬼もそこを繰り返し探しに来る。両方が同じ原因から出ている可能性がある。
「見た目が下手な動き」を悪手だと決めつけて直しにかかったのが失敗の原因。
issue #9 には「往復＝悪手という前提を疑うべき」と書いて priority を low に下げた。

**分かったこと 3 — 煙幕は使えていた。**
issue #9 の未計測項目。1v1 で 40 試合あたり 75 回、3v3 で 217 回使われており、
捕獲時点の残りは平均 0.16〜0.26 回ぶん。ほぼ撃ち切っている。ここは問題ではない。

**分かったこと 4 — 逃げる側にはもう伸ばす余地を作るべきではない。**
現在の勝率は 1v1 53.0% / 2v2 55.0% / 3v3 56.0%（issue #11、各 300 試合）で、
目標帯 35〜50% の上。この状態で逃げる側の行動を良くする変更は、通っても害になる。
`/improve-hider` の次の仕事は勝率を上げることではなく、
**上げずに済む形の改善（見栄え・堅牢性）か、鬼側（issue #11）が片付くまで待つこと**。

**ついでに直したもの** — `npm run sim` に `--seed` を追加した。
これが無いために、`fleeTurnCost` の作業も #8 の作業も今回も、
複数シードで測るたびに使い捨てのハーネスを書き直していた。既定値は 1234 のまま。

**次にやること** — 鬼側（issue #11）が片付いて勝率が目標帯に戻るまで、
逃げる側は勝率を上げる変更を入れない。`threatKeepAway` / `threatMemory` の
`npm run tune` も同じ理由で保留（上振れを助長するため）。
issue #9 に着手するなら「勝率を上げずに往復の見栄えだけ直す」形に限る。

## 遮蔽を増やす案が外れ、issue を GitHub へ移した

**やったこと** — バランス側の 1 サイクル。小さい箱の高さを 1.3 → 1.5 に上げて
遮蔽として働かせる案を 780 試合で測って**不採用**にした。ゲームルールの変更は無し。
あわせて issue の置き場を `docs/issues/` から GitHub issue へ移した。

**分かったこと 1 — 小さい箱は遮蔽として一切働いていなかった。**
視線は目線（1.4）から相手の頭（同じ 1.4）へ引くので、高さ 1.3 の箱は素通しになる。
箱の 6 割が小さい箱なので、11 個ある箱のうち遮蔽になっていたのは 4 個だけ。
準備フェーズで 32 秒かけて積んだ砦が、視線を止めていなかった。

**意外だったこと — 直したのに勝率は上がらず、むしろ 3 構成そろって下がった。**

| 構成 | 見られている割合 | 勝率（1.3 → 1.5） |
| --- | --- | --- |
| 1v1 | 33.1% → 27.3% | 24.7% → 20.3% |
| 2v2 | 71.1% → 56.0% | 35.3% → 33.3% |
| 3v3 | 76.0% → 50.4% | 38.3% → 36.1% |

3v3 で見られている時間が 4 分の 3 から半分になっているのに、勝率は上がらない。
**理由は分からなかった。**「遮蔽は逃げる側の索敵にも効くから不意打ちされるのでは」
という仮説を測ったが、鬼に見られているのに逃げる側が鬼を把握できていない割合は
1.3% → 1.7%（2v2）しか動かず、説明になっていない。仮説は外れ。未解明のまま残す。

これで「足りなさそうなものを足す」が 2 回連続で外れた（補給パック、遮蔽）。

**分かったこと 2 — 逃げる側はスタミナを 9 割残したまま捕まっていた。**
鬼が 14m 以内にいる間のダッシュ使用率は逃げ側 20〜29%（平均スタミナ 84〜91 残し）、
鬼 67〜76%（同 26〜35）。持続ダッシュ率はルール上 逃げ側 56% 対 鬼 37% で、
使い切れば平均速度で 16% 速いのに、その差を捨てていた。
**これで過去に入れた「鬼のダッシュ消費 1.5 倍」が効かなかった理由も説明がつく** —
資源が余っている側に対して相手の資源を削っても意味がない。
ただし issue #8 の修正で勝率が反転したので、これを直す作業は当面不要。
使い捨ての計測は `src/sim/_probe-chase.ts` に残した。

**測り直しについて** — 作業中に master が 2 回進み（`fleeTurnCost`、issue #8 の修正）、
そのたびに取り込んで測り直した。上の A/B は issue #8 の修正**前**のコードで測ったもの。
修正後の現在は 1v1 55.3% / 2v2 59.0% / 3v3 61.7% で、逃げ側が目標帯の上に大きく出ている。

**issue を GitHub issue へ移した** — `docs/issues/*.md` を廃止し、
open な件を GitHub issue #9 / #11 に移した（#8 は解決済みとして close）。
担当ラベル（`seeker` / `hider` / `balance`）と優先度ラベルを付け、
CLAUDE.md と 6 つのスキルの参照を `gh` コマンドに張り替えた。
担当ラベルが、どのループがその issue を拾うかを決める。

**次にやること** — 箱を持ったままジャンプすると箱も上がる（＝箱を縦に積める）機能を
バランス側の次のサイクルで実装する。高さ 1.3 の箱も 2 段重ねれば 2.6 になり、
初めて遮蔽として働く。上の空振りは「配置された箱の高さ」を変えた話で、
「プレイヤーが積み上げて作る」のは別の軸。
逃げ側が目標帯の上（55〜62%）なので、鬼側（issue #11）が先。

## 箱を持ち上げて積めるようにした

**やったこと** — 箱を掴んだままジャンプすると箱も持ち上がり、別の箱の上で手を離すと
積み上がるようにした。ユーザーからの要望（戦略の幅を増やしたい）。

**設計** — `Obstacle` に底面の高さ `y` を足し、上面を `y + h` にした。
既存の障害物はすべて `y = 0` なので `h` の意味は変わらない。
掴んでいる間、箱の底は持ち手の足元に付いてくる。手を離すと落ち、
真下の箱の上面か地面で止まる。

**判断が要ったところ — 垂直の重なりをどこまで許すか。**
ジャンプの頂点は 1.29 m、低い箱の高さは 1.3 m。素直に「1 mm でも重なったら置けない」に
すると、跳んでも 0.007 m 足りずに低い箱の上へ載せられない。
そこで垂直の重なりが `STEP_HEIGHT`（0.35）以内なら「上に乗っている」とみなすことにした。
エージェントが段差を乗り越えるのと同じ許容なので、新しい概念を持ち込まずに済む。
副産物として、**大きい箱（2.2 m）の上には跳んでも載せられない**（重なりが 0.9 m）。
ジャンプ台（頂点 3.0 m）が要る。段階が生まれたので、そのまま仕様にした。

**意外だったこと — 何も積まなくても勝率が動いた。**
実装直後の 1v1 が 56.7% → 61.7%（各 60 試合）。積む操作は入れていないのに動いたので
おかしいと思って調べたら、**箱をジャンプ台の上に置けるようになっていた**。
ジャンプ台は高さ 0.25 m なので、垂直の重なりが許容 0.35 以内に収まってしまう。
台を塞ぐと踏めなくなるので、ジャンプ台だけは従来どおり footprint ごと置けないままにした。

それでも差が残ったが、こちらは原因が違って、**AI が箱を掴んだまま既にジャンプしていた**。
つまり機能が実際に働いていた。バグではない。

**効いたかどうか — バランスは動かなかった。**

| 構成 | 変更前 | 変更後 | 試合数 |
| --- | --- | --- | --- |
| 1v1 | 55.3% | 55.3% | 各 300（100 × 3 シード） |
| 2v2 | 59.0% | 59.7% | 各 300 |
| 3v3 | 61.7% | 60.0% | 各 180 |

3 構成の向きが揃わないので、判定基準どおり「差なし」。理由ははっきりしていて、
**AI がまだ意図的に積んでいない**（追跡開始時点で積まれている箱は 0.03〜0.33 個/試合、
そのうち「目線より低かった箱が積まれて遮蔽になった」のは 0.00〜0.13 個/試合）。
運搬中につかえたら跳ぶ、という最小限の橋渡しだけ入れてあるが、
積む場所を選ぶ判断は入れていない（それは逃げる側のサイクルの仕事）。

物理として成立していることは `src/sim/_stacktest.ts` で確認した。
入力を手で組んで、掴む → 跳ぶ → 運ぶ → 離す、で下の箱の上面 1.30 に着地する。

**次にやること** — 積み方の作り込みを issue にして `/improve-hider` へ渡した。
ただし逃げる側は現在 55〜60% で目標帯の上なので、鬼側（issue #11）が先。
遮蔽が増えると逃げる側がさらに強くなる可能性があるため、
積むようになった時点で必ず測り直すこと。

なお 8/10 のサイクルで「配置された箱の高さを 1.3 → 1.5 にしても勝率は動かない」と
測っている。今回は「プレイヤーが積み上げて 2.6 m を作る」話で軸が違うが、
**遮蔽を増やしても勝敗が動かなかった前例がある**ことは踏まえておくこと。

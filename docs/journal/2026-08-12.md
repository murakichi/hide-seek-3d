## 跳べるようにしたら弱くなった — 4 割の時間を空中で過ごしていた

**やったこと** — PR #50 で入れた `shouldLeap` に発動条件を付けた（PR #66）。
**自分が前サイクルで持ち込んだ回帰を戻す作業。**

**経緯** — #50 は「隙間を挟んだ足場へ跳び移る」修正で、私は「CI で回帰は出ていない」と
報告してマージされた。レビューでも「3v3 +20.0 pt（鬼が弱くなる方向）」と気づかれた
うえで「行動の欠陥修正だから」と通っている。実際に master の 3v3 は
25.0% → 38.0% に悪化していた。

**原因を数値で押さえた**（`_probe-leap.ts`、3v3 / 20 試合）:

```
                                    修正前    修正後
踏み切り（1 試合あたり）              96.1 回   6.7 回
うち高所に相手が居ないのに地上から跳んだ  86.7%     —
鬼が空中に居たティックの割合            40.4%     8.4%
```

`shouldLeap` に条件が無く、**平地でも進行方向に届く足場があれば跳んで**いた。
小箱はアリーナに大量にあるので、追跡中ずっと跳ね回っていたことになる。

**効く理屈は空中の加速度。** `ACCEL_AIR` は 34 で `ACCEL_GROUND` 78 の半分以下。
4 割の時間を空中で過ごせば曲がれないので、追跡も探索も遅くなる。
**跳べるようになったのに弱くなった**のはこれ。

```
構成 | master  修正後 |  差
1v1  |  38.0%   34.0%  |  -4.0
2v2  |  40.0%   38.0%  |  -2.0
3v3  |  38.0%   26.0%  | -12.0   ← #50 が入る前の 25.0% にほぼ戻った
```

**教訓 1 — 「できるようにする」と「使えるようにする」は別。**
物理的に可能な動きを AI に与えるとき、**いつ使うかを同時に決めないと常時使う。**
`shouldJump` には「目の前が塞がっているか」という発動条件が元からあったのに、
`shouldLeap` にはそれを付けなかった。判定の中身（跳躍の到達区間を物理から解く）に
気を取られて、外側のゲートを忘れていた。

**教訓 2 — 床にある構成では回帰も測れない。**
#50 を測ったときの master は 3v3 が 0.0%。差分 ±0 は「影響が無い」ではなく
「測れていない」だった。前々サイクルで「欠陥が見えない」、前サイクルで
「効果が見えない」と書いたが、**回帰も同じ**。3 回とも同じ原因で、
3 回目でようやく実害が出た。バランス側が帯を動かしたら、
床にあった時期の変更を洗い直すこと。

**教訓 3 — レビューが数字に気づいても止まらないことがある。**
#50 のレビューは +20.0 pt を明記したうえで「行動の欠陥修正なので採用します」と
判断している。**出す側が「これは回帰です」と書かない限り、数字だけでは止まらない。**
私は保留を要請するコメントを PR に足したが、それはマージ後だった。
draft のまま出すか、本文の冒頭に書くべきだった。

**次にやること** — PR #55（issue #51、見えていない相手が高所に居ると登れない）は
draft のまま。#66 がマージされたらその上で測り直す。#55 で入れた
`CLIMB_APPROACH` の拡張も、無駄跳びが止まった状態なら評価が変わる可能性がある。

## 人間が見つけた勝ち筋を実装したら勝率が落ちた（issue #48、取り下げ）

**やったこと** — ユーザーが逃げる側を実際にプレイして見つけた勝ち筋を実装し、
**機構は再現したが勝率は落ちたので取り下げた。**

> 低い台から少し離れたところに高い台を並べて設置し、低い台からそこに飛び移ることで
> 鬼が来れなくなって勝ちました
>
> ジャンプ台→高台→高台と飛び移ることで seeker が追ってこれなくなりました

**分かったこと 1 — 鬼は水平の跳び移りができない。**
ソースを読んで裏を取れた。鬼の登坂は 2 つの部品でできていて、どちらも垂直しか扱えない。

- `seeker.ts` の `climbTarget` は「今の高さから乗れる面」を踏み台に選ぶだけ
- `context.ts` の `shouldJump` は**進行方向の足元が塞がっているとき**にしか跳ばない。
  隙間の上には障害物が無いので `isBlockedWorld` が偽になり、跳ばない

物理としては跳べる（滞空 0.63 秒 × 8.8 で約 5.5m）。**思考が持っていないだけ。**
経路探索のグリッドでも隙間は通れないので、回り込む道も見つからない。

**分かったこと 2 — 高所の攻略が 4 回失敗した理由がはっきりした。**
issue #13 で「高台に乗る」を 4 回試して全部駄目だったが、失敗の理由はどれも
**「鬼も同じ踏み台で登ってくる」**だった。隙間を挟むとその前提が崩れる。
**欠けていたピースは「高さ」ではなく「隙間」だった。**

**分かったこと 3 — 機構は再現した。**
`hopToPerch`（上面が `CATCH_VERTICAL` 超 / 垂直に `CLIMB_REACH` 以内 /
その高台の近くに地上から登れる踏み台が無い）を実装し、直接届かないときは
ジャンプ台（到達高 3.0）を起点にした。トレースで確認:

```
[t= 40.0 hunt] 逃#0(-1.5,16.9)↑2.2 idle  |  鬼#1(6.5,4.4)↑0.6 investigate
```

逃げる側が大箱の上（2.2）に乗り、鬼は 0.6 のまま追ってこられていない。

**それでも勝率は落ちた。** CI（各構成 100 試合 / seed 4 本）:

```
版                              1v1     2v2     3v3
master                         37.0     8.0     0.0
跳び移りを逃走より優先          19.0    3.0     1.0    (-18.0)
追いつかれかけていないときだけ   26.0    7.0     0.0    (-11.0)
```

**意外だったこと — 「着けば安全」が正しくても、着くまでのコストで負ける。**
高台へ向かう間は一直線に走るので、逃走の采配（遮蔽・向きの保持・鬼から離れる）を
全部捨てることになる。**人間は「跳ぶ瞬間」を選べるが、AI は選べていない。**
1 回目の失敗（−18）は跳び移りを逃走より優先したせいで、門を付けたら −11 まで戻った。
つまり門の付け方をさらに詰めれば通る可能性はあるが、今回の 2 通りでは足りなかった。

**次に試すなら**（issue #48 に書いた）

- **視線が切れている間だけ移動する。**今回の門は「鬼が `fleeDashDist` より遠い」だけで、
  見られているかを見ていなかった。
- **高台までの距離で足切りする。**今は 20m まで許している。
- **準備フェーズのうちに高台の近くへ拠点を置く。**移動そのものを無くす。
  ユーザーが実戦でやったのは「高台を**並べて設置**」なので、本来はこちらが本筋。

**続き — ユーザーの一言で通った。**
「準備時間に飛び移ればいいのでは」。追跡フェーズでの跳び移りが負けていた理由は
移動コストだけだったので、**鬼が檻の中にいる準備フェーズで登ってしまえば
その弱点がそのまま消える**。実装を「準備フェーズの残りが `perchPrepMargin`(10 秒) を
切ったら荷物を捨てて高台へ登る」に変えたところ:

```
版                              1v1     2v2     3v3
master                         37.0     8.0     0.0
追跡中に跳ぶ（逃走より優先）    19.0     3.0     1.0    (-18.0)
追跡中に跳ぶ（門つき）          26.0     7.0     0.0    (-11.0)
準備フェーズで登る              39.0     8.0     0.0    (+2.0/±0/±0)
```

**どの構成も悪化しなくなった。**利得は 1v1 の +2 だけで、400 試合の標準誤差
（約 2.4 pt）に収まる大きさなので「効いた」と言い切れる幅ではない。
ただし**悪化が消えたこと自体が情報**で、負けていたのは高台の価値ではなく
移動コストだった、という切り分けがはっきりした。

**教訓 — 「いつやるか」を変えるだけで符号が変わる。**
同じ戦術を同じ条件で実行しても、追跡中は −18、準備中は +2。
戦術の良し悪しではなく**実行の窓**を間違えていた。
今後「良い手のはずなのに負ける」ときは、まず実行のタイミングを疑う。

**鬼側について** — ユーザーから「鬼には『ロックされていない箱を探しに行く』方向を
伝えてある」と共有あり。鬼が跳び移りを覚えるとこの穴は塞がる。
そのとき残るのは「移動コスト」の問題なので、**先に移動コストを下げる形
（準備フェーズで高台の近くに陣取る）を作っておく方が無駄にならない。**

## 人間が見つけた穴 — 高所へ跳び移れば鬼は来られない

**やったこと** — 隙間を挟んだ足場へ踏み切れるようにした（issue #20 の一部、PR #50）。
**ユーザーが hider で実際にプレイして報告してくれたもの。**

> 低い台から少し離れたところに高い台を並べて設置し、低い台からそこに飛び移ることで
> 鬼が来れなくなって勝ちました
> ジャンプ台→高台→高台と飛び移ることで敵が追ってこれなくなりました

**分かったこと 1 — この穴は仕組み上どうやっても測定に出てこなかった。**
成立の理由は仕様どおりで、

- `CLIMB_REACH` 1.64 → 地上からは小箱(1.3)にしか乗れない
- 小箱の上(1.3)からは 2.94 まで届く → 大箱(2.2)・2 段積み(2.6)へ渡れる
- `CATCH_VERTICAL` 1.6 → 地上の鬼は y=2.2 の相手に触れない

**AI の逃げ側がこの手を使わないので、勝率にもトレースにも一度も現れていない。**
issue #20 は「先回りの起票、まだ症状は出ていない」として priority:low で寝ていた。
自動測定だけを回していると、**AI が思いつかない戦術の穴は永遠に見つからない。**
人間が遊んだ 1 試合の方が、600 試合の勝率より情報量が多いことがある。

**分かったこと 2 — 原因は踏み切りの判定が「目の前が塞がっているか」だけだったこと。**
`shouldJump` は進行方向 1.65m 先が塞がっているときしか跳ばない。
**隙間を越えて高台に飛び移る場合、目の前にあるのは空きスペースなので条件を満たさない。**
再現環境で数えたら、低い台の上で接地していた 51 ティックの間、ジャンプ指示は 0 回だった。

跳躍の到達区間を物理から求め（`y(t) = JUMP_SPEED·t − (GRAVITY/2)·t²` がその面の高さ
以上になる区間）、その間に進める水平距離が足場の範囲と重なるときだけ踏み切るようにした。

**判定で 2 度間違えた。どちらも勝率では絶対に気づけず、再現環境で分かった。**

1. **縁ぎりぎりを狙うと側面に当たって跳ね返される。**
   着地に余裕を要求していなかったため、地上から低い台へ 4m 手前で跳び続けて
   側面に当たり、**逆に台に乗れなくなった**（最高到達 1.22m、台の上面 1.3m に届かない）。
   修正前より悪化していた。
2. **飛距離を基準速度（8.8）で見積もっていたが、追跡中の鬼はダッシュしていて 13.6。**
   1.5 倍の距離を飛ぶので足場を飛び越す。現在速度で計算し直して直った。
   **速度に依存する判定を定数で書くと、状態によって静かに壊れる。**

**結果**

```
再現環境（_probe-highground.ts、逃走者を高台に固定して鬼が登れるかだけを見る）
隙間 1m  登れず → 捕獲できた
隙間 2m  登れず → 捕獲できた
隙間 4m  登れず → 登れないまま（別件、#51 へ）

CI（回帰チェック。この経路は AI の逃げ側が使わないので勝率には出ない）
1v1 37.0 → 38.0（+1.0）/ 2v2 8.0 → 5.0（−3.0）/ 3v3 0.0 → 0.0
```

**分かったこと 3 — より根の深い穴が出てきた（#51）。**
隙間 4m で登れないのは踏み切りの問題ではなく、**`climbing` が「今見えている相手」に
紐づいている**こと。`climbTarget`・足場への直進・eager ジャンプの 3 つが全部これで
ゲートされているので、**見失った瞬間に高所へ登る手段が全部止まる。**
さらに目撃地点が箱の上だと nav では通行不可なので経路も取れず、
PR #35 の「進捗が無ければ諦める」が働いて高所が探索対象から消える。
priority:high で切り出した。

**分かったこと 4 — 「鬼が登ってきたら飛び降りて振り切る」は、まだ測れない。**
ユーザーから「鬼が対策として追ってくる可能性も考慮すること」と指摘をもらったので、
逃走者を固定せず AI に動かす `free` モードを再現環境に足して確かめた。
**結果は「高所の攻防が発生しない」**。鬼が近づいた時点で逃走者が台から降りて逃げるので、
鬼は登る必要すら無く、最高到達は 1.22m（地上のジャンプの頂点）のままだった。

つまり「登った鬼を高所から飛び降りて振り切り、鬼の時間を浪費させる」という反撃は、
**逃げ側が高所に留まる判断を持って初めて成立する**。今の AI は高所を即座に放棄する。
逃げ側にその判断が入った時点で、鬼が高所で無駄足を踏んでいないか測り直すこと。

今回の実装は「進行方向にある足場」にしか反応しない（`dir` との内積 0.7 以上）ので、
目標から逸れて登りに行くことは無い。CI でも回帰は出ていない（1v1 +1.0 / 2v2 −3.0）。
ただし**罠として成立するかは相手の行動次第**なので、安全だと結論はできない。

**分かったこと 5 — 壁も足場だった。**
ユーザーから「この遷移は壁の上を経由することもできるよね」と指摘をもらって確認したら、
**内壁は高さ 2.6 m で、小箱(1.3)の上からは 2.94 m まで届くので乗れる**
（`PAD_JUMP_SPEED` のコメントにも「内壁の上にも乗れる」と書いてあった）。
それなのに `shouldLeap` も `climbTarget` も `kind === 'wall'` を無条件で除外していた。
**逃げる側が壁の上を経由できる以上、鬼が壁を無視すれば同じ穴が壁の側に残る。**
除外をやめ、届くかどうかは高さ判定に任せるようにした（外周壁は 3 m なので自然に落ちる）。

ただし**壁経由の再現はまだ登れない。** 鬼が `investigate`/`patrol` のままで、
相手が見えていない。つまりこれは踏み切りの問題ではなく #51 に帰着する。
壁の除外を外した修正は #51 が直った後に効いてくる（直さないと壁だけ跳べないままになる）。

**次にやること** — #51（見えない相手が高所に居ると登れない）が本命。
issue #20 の本題（箱を運んで踏み台を作る）も残っている。ユーザーの案で、
`findGrabTarget` に陣営制限が無いので鬼も運べる。ただし運搬は時間がかかるので、
跳び移り（ほぼ無コスト）とは性質が違う。別サイクルで測る。

**運用の追加** — `in-progress` ラベルを導入した（CLAUDE.md とスキルに明記）。
複数のループが同時に走るので、着手が `gh issue list` の一覧で見えないと重複する。
コメントだけでは一覧に出ないので気づけない。

## 鬼の視界を人数で割った。効きが面積の理屈に従わなかった

**やったこと** — issue #43（3v3 で逃げる側 0%、行動側の手は 5 通り試して全部失敗）を
引き取り、`viewDistFor(seekers) = VIEW_DIST / seekers` を入れた。
鬼の視界だけ人数で割る（1v1 19.0 で不変 / 2v2 9.5 / 3v3 6.3）。

**分かったこと 1 — 「常に見えている」のではなかった。**
3v3 が 0% なので「見つかりっぱなしで何もできない」のかと思っていたが、
見られている割合は 3 構成とも 31〜40% でほぼ同じだった。違うのは
**視線を切ってから再発見されるまでの時間**で、1v1 3.9 秒 / 2v2 2.6 秒 / 3v3 2.5 秒。
見失う回数も 6.7 → 4.5 → 3.4 回。**切れるのに、切れている時間が短い。**
逃げ切りに使える 2.5 秒では足りない、というのが 0% の中身だった。

**意外だったこと — 面積の理屈が当たらなかった。**
「視界の面積は距離の 2 乗だから、鬼 n 人の合計探索能力を一定にするなら √n で割ればよい」
と考えて、先に √n を測った。**ほとんど効かなかった**（2v2 +4 / 3v3 +2）。
n で割ると +31 / +15 になる。

| 割り方 | 鬼 1 人の視界 | 1v1 | 2v2 | 3v3 |
| --- | --- | --- | --- | --- |
| 割らない | 19 / 19 / 19 | 37.0% | 8.0% | 0.0% |
| √n | 19 / 13.4 / 11.0 | 37.0% | 12.0% | 2.0% |
| n | 19 / 9.5 / 6.3 | 37.0% | 39.0% | 15.0% |

**効きが面積に比例しない。** 律速は「盤面の何割が見えているか」ではなく、
もっと n に近い何か（視界の縁が通り過ぎる頻度など）らしい。理由は分かっていない。
**原理から値を決めて満足せず、必ず 2 点以上測ること**という教訓。
1 点目だけ見て「この方向は効かない」と畳んでいたら、そこで終わっていた。

**成果** — 2v2 が 8% → 39% で目標帯に入った。3v3 は 0% → 15%。1v1 は完全に不変。
**2v2 と 3v3 が同時に上がった変更はこれが初めて**（行動側の 5 案はすべて
「片方を上げると他方が落ちる」だった）。

**次にやること** — 3v3 はまだ帯に届いていない。これ以上強めると 2v2 が上へ抜けるので、
単一の指数では両立しない。3v3 には別のレバーが要る。issue #43 は open のまま残す。
6.3 m は短いので、観戦での見え方も次に触るときに確かめること。

## 2v2 の負け筋を探して、ブーストが余っていることを見つけた（不採用）

**やったこと** — 1v1 37% に対し 2v2 8% と 29 ポイント落ちる理由を探した。
トレースの見立ては外れたが、途中で**未使用の仕様**を 1 つ見つけて試し、
**CI で通らなかったので取り下げた**（issue #47 に切り出し）。

**外れた仮説 — 「2v2 はアリーナを横断し続けている」。**
トレースで逃#0 が 6 秒ごとに端から端へ移動する試合を見たので、
横断のせいで見つかっているのだと思った。測ると逆だった（各 30 試合）:

```
                        1v1      2v2
移動距離 / 人           332m     205m
生存 1 秒あたり        7.90m/s  8.37m/s
中央(原点 10m 以内)へ    2.2回    0.5回
開けた場所に居た割合    54.9%    45.6%
見られていた割合        34.1%    39.9%
生存率                 36.7%     1.7%
```

**2v2 の方が開けた場所に居る割合は低い**（45.6% 対 54.9%）**のに、見られる割合は高い**。
横断が原因ではなく、単に鬼 2 人の視界が広いだけだった。
移動距離が少ないのも、早く死ぬぶん短いだけ（205m / 24.5 秒 対 332m / 42 秒）。

**見つけたこと — ブースト中はダッシュし放題なのに、取りに行っていない。**

```
ブースト中のダッシュ消費 = DASH_COST * BOOST_DASH_COST = 34 * 0.45 = 15.3/秒
スタミナ回復            = STAMINA_REGEN                        = 19/秒
```

差し引き +3.7/秒。**`BOOST_TIME`（6 秒）のあいだは走り続けても減らない。**
`hider.ts` は `BOOST` 系を一度も参照しておらず、パックへ寄るのは
「スタミナが足りないとき」だけ。実測（2v2 / 30 試合）:

```
逃げる側が取ったパック   1.97 個/試合
鬼が取ったパック         3.77 個/試合   ← 2 倍近い
盤上に残っていたパック   平均 2.7 個
逃走中のブースト         15.0%
```

**盤上には余っている。供給ではなく取りに行かないのが理由。**
前サイクルで測った「視線を切っても 2.5 秒で拾われる」に対して、
ブーストの 6 秒はちょうど噛み合う資源に見えた。

**駄目だった案 1 — 逃走中のパック加点から `stamina < 50%` を外す。**
機構は動いた（パック 1.97 → 2.43 個、逃走中のブースト 15.0% → 18.0%）。
CI は **1v1 +3.0 / 2v2 −4.0 / 3v3 ±0**。向きが揃わず不採用。

**駄目だった案 2 — 条件を 80% に緩める中間。**
**1v1 −3.0 / 2v2 −1.0 / 3v3 ±0** でさらに悪い。

**意外だったこと — 中間が両端より悪い。**
条件を「50%（現状）」「80%」「無し」と動かすと、1v1 は +0 / −3 / +3 と
真ん中がへこむ。単調でないので、これは重みの問題ではなく
**「どのタイミングで寄り道するか」の質の問題**だと思われる。
パックは開けた場所に湧くので、寄り道は被発見と引き換えになる。
「取りに行く」だけでは足りず、**「安全に取れるときだけ取る」判断**が要る。

**これで 2v2 を助ける変更は 7 通り連続で失敗している**
（脅威項 /n・/√n、遮蔽の割合化、拠点の遮蔽評価、味方回避の最近接化、
パック条件の撤廃・緩和）。1v1 か 3v3 が上がると必ず 2v2 が落ちる。

**次にやること** — issue #47（ブーストが余っている）に、
「追われ始めてから、視線が切れた瞬間に近くのパックを拾う」形を書いておいた。
`evade` の非逃走分岐で拾う形なら逃走の採点と競合しないので、
過去に唯一通っている「別モードとして足す」型に当てはまる。
2v2 そのものは issue #43（balance）の対象にも入れてある。

## 「見られていない間だけ」に限ったら通った（issue #47、1v1 +8.0）

**やったこと** — 前の節で「次に試すなら」と書いた形をそのまま実装した。
**追われている最中に視線が切れたら、その隙にパックを取りに行く。**

**結果** — CI（各構成 100 試合 / seed 4 本）:

## 見た目: プレイヤーを人型にして、カメラを操作できるようにした

**やったこと** — エージェントの見た目をカプセル 1 個から人型（頭・胴・腕・脚）に差し替え、
移動速度に応じて手足を振るようにした。あわせてカメラに拡大・縮小・追従・俯瞰を付けた
（既定は今までどおり俯瞰でアリーナ全体）。`src/render` と `src/ui` だけの変更で、
`src/core` と `src/ai` は触っていない。`npm run sim -- --games 4 --hiders 2 --seekers 2` が
master と 1 桁まで同じ（勝率 0.0%、初補足 54.3 秒）ことを確認した。

**分かったこと**

- **同じ色の球を積むと俯瞰では雪だるまにしか見えない。** 最初は頭も胴もチーム色そのままで
  作ったが、寄って見ると輪郭が溶けて 1 つの塊になった。頭＝チーム色、胴＝チーム色と
  暗色の中間、手足＝暗色、あいだに暗い首、と明度を 3 段に分けて初めて人型に読めた。
  形ではなく明度差が効いている。
- **アリーナは 44 m 四方、人は 1.7 m。** 全体を写す俯瞰では 1 人が 20 px 程度にしかならず、
  顔の作り込みは見えない。向きの手がかりは結局くちばし（白い円錐）で、これは元の
  カプセルから引き継いだ。目や指の作り込みは追従カメラで寄ったときだけ効く。
- **追従カメラで対象をそのまま画面中央に置くと、端に居るとき画面の半分が場外になる。**
  カメラの中心を `ARENA_HALF - 見えている半径 * 0.5` で頭打ちにして、はみ出しを抑えた。
  全体表示のときはこの上限が 0 になるので、俯瞰の見え方は今までと変わらない。
- **ズーム倍率は俯瞰と追従で別々に覚えさせた方がよい。** 共有にすると、全体を見ている
  状態から追従に切り替えても何も起きない（見え方が変わらない）ので、切り替えの意味が
  伝わらなかった。

**次にやること** — なし。追従の対象は「自分、居なければ生存している逃走者の先頭」の
固定で、観戦中に見る相手を選ぶ手段はない。必要になったら別途。

## 高台を「作る」— 台の予約で 3v3 の穴が塞がった（PR #67）

前サイクル（PR #63）で建設自体は成立していた。高台へ立てる割合が 10% → 20% になり、

**その形自体が原因を指していた。** 予約が無いので、同じ台を見た全員が
別々の箱を同じ場所へ運ぶ。高台は 1 つあれば足りるので 2 人目以降は準備時間を
捨てているうえ、**全員が 1 箇所に固まってまとめて狩られる。**

`coop` の `'target'` 予約は逃げる側で未使用だったので、そのまま使えた。

## 自分が起票した退行 issue が間違っていた（#64 を訂正して閉じた）

**教訓 — 古い測定に基づく issue は、直す前にもう一度測る。**
「効く手は相手の強さで変わる」を 3 度目に踏んだが、今回は**自分が書いた根拠**に
足をすくわれた。issue の本文に測定日と、そのときの master の勝率を書いていたのが
唯一の救いで、それが無ければ気づかずに 0 にしていた。
**測定値を書くときは必ず「いつ・どの master で」を添える。**

### 駄目だった案 1: 見つかるまでパックの隣で待つ（packCampDist）

追跡開始から初補足まで 2v2 で約 25 秒あり、その間ずっと拠点で立っている。
既存の寄り道は「最近そこに鬼が居た」ことが条件なので**この 25 秒では一度も発動しない。**
取ってしまうとブースト 6 秒を無駄撃ちし `PICKUP_RESPAWN`(22 秒) 復活しないので、
**取らずに 2.6m 隣で待つ**形にした。

**変化なし**（2v2 の生存率 31.7% → 31.7%、ブースト率 30.0% → 30.7%）。
理由は次で分かった。

### 駄目だった案 2: 逃走中に通り道のパックを拾う（packOnRoute）

**逃走ブランチはそこで return するので、パックの判定に一度も到達していなかった。**
真横 2m にブーストがあっても無視して走り抜けている。隣で待っても、
追われ始めた瞬間から拾えないので案 1 が効かなかったのはこれ。

逃走方向との内積で足切りして「もう向いている方向にあるとき」だけ拾うようにしたが、

| | 2v2 | 3v3 |
| --- | --- | --- |
| 素 | 31.7% | 20.0% |
| 内積 0.5 / 6m | 28.3% | 10.0% |
| 内積 0.88 / 4m | 31.7% | 16.7% |

**厳しくしても良くならず、緩めると悪化する。**ブースト率もほとんど動かない
（29.3% → 28.7%）ので、拾えていない。

**`fleeDirection` の出力に触る案は、これで 4 連敗。**
（`fleeOpenWeight` / `fleeLeadTime` / `fleePerchBonus` / 今回の上書き）
**逃走の方向決定は完成度が高く、外から足すと必ず負ける。**
効くのは「候補を増やす」か「別のモードを足す」かのどちらかだけ、という
これまでの整理がまた裏付けられた。

**次にやること** — 高台の予約（前節）が本命のまま。
パック系は `boostGrabDist` の現状値 10 が 2v2 で最良（0→20.0%、10→31.7%、14→26.7%、
いずれも旧ルール）なので、値をいじる余地も小さい。

## 構造的なねじれを 1 つ直した（3 構成すべてが帯に入った）

**やったこと** — `huntTimeFor` の人数補正を「3 人以上で +6 秒」から
「1 人のときだけ −6 秒」に変えた。追跡時間は 1v1 50 / 2v2 56 / **3v3 62 → 56 秒**。

**気づき方** — 勝率が 48 / 45 / **31** で 3v3 だけ帯の下なのに、
追跡時間は 1v1 50 / 2v2 56 / **3v3 62** と 3v3 が最長だった。
**最も弱い構成に最も長い時間を課していた。**

元の形（人数が増えるほど伸ばす）は「1 人でも残れば勝ち」の増幅を打ち消すためのもので、
入れた当時は釣り合っていた。行動側の変更で構成ごとの強弱が入れ替わったので、
その補正だけが取り残されていた形。config のコメントに自分で
「逃げ側が回復したら測り直すこと」と書いてあり、それが効いた。

**結果**

| 測ったときの master | 1v1 | 2v2 | 3v3 |
| --- | --- | --- | --- |
| 48 / 45 / 31 | ±0.0 | ±0.0 | **+6.0** |
| 47 / 42 / 33（取り込み後） | ±0.0 | ±0.0 | **+8.0** |

**3 構成すべてが目標帯（35〜50%）に入った: 47 / 42 / 41。**
master を取り込んで測り直しても同じ性質が出た。

**設計として良かった点 — 1v1 と 2v2 が 2 回とも厳密に ±0.0 だったこと。**
秒数を変えていないので当然の結果だが、**「秒数以外の経路で影響が出ていない」ことの
確認になっている**。もしここが動いていたら、追跡時間が AI の別の判断
（撤退のタイミングなど）に間接的に効いているということで、調べる必要があった。
**変えないつもりの構成が本当に動かないかを見る**のは、狙い撃ちのレバーでは毎回やる価値がある。

**予測を書かなかった判断は正しかった。**
同じ −6 秒でも 3v3 への効きは +11.0 / +5.0 / +6.0 / +8.0 と 4 例でばらつく。
**当てに行くより測る方が速い。**

**次にやること** — バランス側から積極的に動かすものは無い。
行動側のマージで帯から外れたら戻す役に回る。
戻し方は 2 通りとも実測済みで config のコメントに書いてある。
- 全構成を一律に動かす → `HUNT_TIME`
- 特定の構成だけ動かす → `huntTimeFor` の人数補正

## 予告した崩れが起きたので、用意したレバーで戻した

**やったこと** — PR #66（鬼の無駄跳びを直す）で逃げ側が 38 / 40 / 38 → 34 / 38 / 26 に
落ちたので、`HUNT_TIME` 68 → 62（追跡時間を一律 −6 秒）で戻した。
結果は **48 / 45 / 31**。1v1 と 2v2 は帯に戻り、3v3 は 4 ポイント足りない。

**うまくいったこと — 前サイクルの「取り下げ」が資産になった。**
この −6 秒は前サイクルで測って「不要どころか有害」として取り下げている
（当時の master は 43 / 46 / 40 で既に帯の中だった）。そのとき
**「効くレバーだが今は使う場面ではない」**という形で記録を残しておいたので、
今回は考え直さずにそのまま出せた。**取り下げた変更でも、条件を書いて残すと再利用できる。**

**意外だったこと — 秒あたりの効き量が構成ごとに入れ替わった。**

| 測ったときの master | 1v1 | 2v2 | 3v3 |
| --- | --- | --- | --- |
| 43 / 46 / 40（前回） | +6.0 | +4.0 | +11.0 |
| 34 / 38 / 26（今回） | +14.0 | +7.0 | +5.0 |

同じ −6 秒なのに、**前回は 3v3 が最も敏感、今回は最も鈍い**。
秒あたり 0.8〜2.3 ポイントの幅がある。前サイクルで「1 秒 ≒ 1 ポイント」と
書いたが、**当たりを付ける目安にしかならない**。予測（40 / 42 / 37）に対して
実測（48 / 45 / 31）で、特に 3v3 は 6 ポイントも外した。

理由は推測だが、3v3 は初補足が 49.9 秒（追跡開始から 18 秒）と早く、
**時間を縮めても「捕まる時刻の方が先に来る」割合が高い**ので、
時間のレバーが効きにくいのだと思われる。1v1 は初補足 59.4 秒（同 27 秒）で
終盤まで生き残る試合が多く、そのぶん時間短縮が直接勝ちに変わる。未検証。

**残っていること — 3v3 だけを動かすレバーが要る。**
一律のレバーではこれ以上詰められない（1v1 が 48% で上限に近い）。
`huntTimeFor` の人数補正が候補で、今は 1v1 が最短（50 秒）・3v3 が最長（62 秒）と
**最も弱い構成に最も長い時間を課している**。この向きは以前も一度逆転させていて、
config のコメントに「逃げ側が回復したら測り直すこと」と自分で書いてある。次はそこ。

**次にやること** — `huntTimeFor` の人数補正を 3v3 側に有利な向きへ振る。
1v1 が 48% で上限に近いので、1v1 を動かさない形にすること。

## 拠点は危なくなかった。ロックは «鬼を呼ぶ» が、それでも張る価値がある

**やったこと** — 前節の候補「鬼の巡回は `age` で選ぶので、動かない拠点は
いずれ必ず巡回目標になる。振り切ったあと拠点へ帰るのは自分から掃除待ちの場所へ
戻る動きでは」を検証した。**支持されなかった。**

| 3v3 / 30 試合 | 値 |
| --- | --- |
| 捕獲が自分の拠点から 6m 以内 | **13.0%** |
| 捕獲時の拠点からの距離（平均） | **20.8 m** |
| 逃げる側が自分の拠点の周りに居た時間 | 24.7% |

**時間の 24.7% を拠点付近で過ごしているのに、捕獲はそこで 13.0% しか起きていない。**
つまり**拠点は平均より安全**。2v2 も同じ（滞在 32.3% に対し捕獲 7.9%）。
死んでいるのは平均 20.8m 離れた場所で、「拠点へ帰るのが罠」ではなかった。

### ただし «鬼を呼ぶ» 効果は実在した

| 鬼が拠点の周りに居た時間 | 3v3 | 2v2 |
| --- | --- | --- |
| 実測 | 23.1% | 17.8% |
| 面積比 | 17.5% | 11.7% |

**面積比の 1.3〜1.5 倍。**ロックした箱は `lockedBoxLure`(8) で巡回の点数を上げるので、
拠点は確実に鬼を引き寄せている。

### ユーザーの指摘「敵が箱を動かさないからロックは不要では？」— 測って否定

**鬼は箱を動かす。** `seeker.ts` の `handleObstruction` は進路を塞ぐ箱に対し

- **ロックされていない** → `act.grab` で掴んで**自分の背後へ引き抜く**
- **ロックされている** → `act.lock` で**接触して解錠**（`UNLOCK_TIME` 1.6 秒）

`game.ts` の `findGrabTarget` も `if (o.lockedBy !== null) continue`（ロック中は掴めない）。
**ロックは「壁を押しのけられなくする」ための機能で、解錠に 1.6 秒を強いる。**
張るのに要る `LOCK_TIME` は 0.35 秒なので、**時間の交換比は 1 : 4.6 で逃げる側が得。**

実測でも、ロックをやめると**鬼の拠点滞在は狙いどおり減るのに、勝率は落ちる**:

| lockShelter | 1v1 | 2v2 | 3v3 | 3v3 の鬼の拠点滞在 |
| --- | --- | --- | --- | --- |
| **1（現状）** | **53.3%** | **36.7%** | **23.3%** | 23.1% |
| 0 | 53.3% | 35.0% | **17.8%** | 17.6% |

**3v3 で 5.5 ポイント落ちる。**「呼び寄せる損」より「壁として保つ得」が勝っている。
人数が多いほど拠点の壁が効くのは、同時に複数から来られたときに
押しのけられない壁が唯一の時間稼ぎになるからだと思われる。

**指摘は前提が違ったが、確かめる価値はあった。**「呼び寄せているのは事実」まで
数字で押さえられたので、`decoyLockDist`（囮ロック）の意味づけもはっきりした。
**鬼を呼ぶ性質は、拠点から離れた場所で使えば利得になる。**

### 意外だったこと

**中間指標が 3 回続けて «狙いどおり» 動いたのに、勝率はどれも改善しなかった。**
壁際滞在（前々サイクル）、逃走の再突入率（前サイクル）、今回の鬼の拠点滞在。
**動かしたい数字を動かせること自体は、もう仮説の裏付けにならない。**
次からは「その数字が動くと勝率が上がる」ことを先に確かめる。

**次にやること** — `decoyLockDist`(11) は既に実装済みだが、
**「鬼を呼ぶ」効果が面積比 1.3〜1.5 倍と定量化できた**ので、
囮の数・位置・タイミングを詰める余地がある。囮は拠点と違って
**引き寄せた鬼が来ても失うものが無い。**

## 開幕にケージを囲うと勝率 100%。ただし «閉じる» まで無価値（崖）

**ユーザーの案** — 「開始前に敵を囲ってしまうのはどう？」

**AI に建てさせる前に、盤面を手で組んで価値だけ確かめた**（`_probe-cage.ts`）。
準備フェーズの鬼は半径 `SEEKER_CAGE_RADIUS`(2.6) から出られず、
**箱には配置制限が無い**（ケージの判定は `game.ts` で agent にしか掛かっていない）。
大箱は上面 2.2 > `CLIMB_REACH`(1.64) なので登れず、ロックすれば掴めない。

半径 4.2 にロック済みの大箱を並べた結果（2v2 / 20 試合）:

| 囲いの個数 | 鬼が半径 6.2 を越えるまで | 出られなかった試合 | 逃げる側の勝率 |
| --- | --- | --- | --- |
| 0（現状） | 0.8 秒 | 0 / 20 | 50.0% |
| 3 | 1.2 秒 | 0 / 20 | 60.0% |
| 5 | 0.5 秒 | 0 / 20 | 50.0% |
| **8** | 7.2 秒 | **19 / 20** | **100.0%** |
| 10 | — | **20 / 20** | **100.0%** |

**5 個までは完全に無価値で、8 個で勝率 100% になる。**
連続的な効き方ではなく**閉じるか閉じないかの崖**。
壁は迂回されるので、隙間が 1 つでもあれば 0.5〜1.2 秒しか稼げない。

**鬼は解錠を試みない。** `handleObstruction` は
「進路を塞ぐ箱」を `clearDist`(2.2) 以内かつ `stuckTimer > 0.35` で拾うが、
囲まれた状態では経路探索が目標に到達できず、そもそも壁へ押し込む向きの
入力が出ないと思われる。**`UNLOCK_TIME`(1.6 秒) × 8 個 = 12.8 秒で抜けられるはずが、
抜けていない。**

**次にやること — 建てられるかの検証。**
8 個を準備時間 32 秒（実質 29 秒）で運べるかが唯一の争点。
`arena.ts` は初期配置の箱をケージ + 2.5 = 5.1m まで寄せているので、
**中心の近くに元から箱がある。**運搬距離が短ければ 3v3 なら届く可能性がある。
issue #79 に測定値を添えて起票した。

**注意 — これはバランス側にも関わる。**
閉じれば勝率 100% は、逃げる側の «勝ち» ではなく**ゲームが終わってしまう**形。
行動側としては「勝てる手があるなら取る」が方針なので実装を目指すが、
**成立した時点で `/improve-balance` に共有する。**

## 逃げる側は追跡中の 7.2% で「動いていない」（原因は情報、行動では埋まらない）

**やったこと** — 前節の「捕獲の 72.5% は鬼 1 人」をもう一段分解した。
追跡中（鬼が 13m 以内）に、逃げる側と鬼のどちらがより «詰まって» いるかを比べた
（3v3 / 30 試合、seed0=1234）:

| | 逃げる側 | 鬼 |
| --- | --- | --- |
| 上限の 60% 未満だったティック | **16.3%** | 7.4% |
| うち移動入力は出ていた（＝当たっている） | 9.1% | 5.9% |
| **差し引き＝入力自体を出していない** | **7.2%** | **1.5%** |
| 1 ティックあたりの進行方向の変化 | 3.52 度 | 3.97 度 |

**逃げる側は追跡中の 7.2% のティックで移動入力をほぼ出していない。鬼は 1.5%。**
「曲がりすぎて遅い」という読みは外れていて（向きの変化はむしろ鬼の方が大きい）、

**これは «知らない» のが正しい挙動なので、行動側では埋められない。**

### 次の候補: 鬼が掃除し終わった区画に居座る

`seeker.ts` の `pickPatrolGoal` を読んで見つけた穴。鬼の巡回目標は

```ts

```

**「最後に見てから最も時間が経ったセル」を選ぶ。**
つまり**鬼が通り過ぎた直後の区画は、当分そこへ戻ってこない。**

逃げる側はこれを一切利用していない。それどころか `routeIsRisky` は
「直近に鬼が居た場所」から `threatKeepAway`(10m) を**一律に避ける**ので、
**掃除済みで最も安全な区画を、同じ理由で捨てている。**

「鬼が居た場所を避ける」（PR #6、実測で改善）と
「鬼が掃除した場所に居座る」は両立する。分けるべき軸は
**«鬼が今どこに居るか» ではなく «鬼が最後にそこを見てから何秒経ったか»。**
逃げる側は自分が見た範囲でしかそれを知らないが、
**追われて逃げた直後の «自分が今さっき居た場所» は必ず掃除済み**なので、
振り切ったあとに拠点へ帰らず**その場に留まる**だけでも成立する可能性がある。

現状は振り切ると拠点へ帰る（`home` へ `moveTo`）。**拠点は試合を通じて動かないので、
鬼の `age` は溜まり続ける＝いずれ必ず巡回目標になる。**
「逃げ切ったら拠点に帰る」は、**最も掃除の優先度が高い場所へ自分から戻る動き**
だった可能性がある。次サイクルで測る。

## 速い側が 1 対 1 で捕まっている（行動側では解けないと判断して issue #74 を起票）

**やったこと** — 前節の「3v3 は見つかってからの粘りが半分」を追った。
仮説は「`fleeDirection` が追跡人数を見ていないので挟まれる」だったが、**外れた。**

### 外れた仮説: 挟み撃ち

捕獲時に 13m 以内に居た鬼の人数（3v3 / 30 試合）:

```
0 人 0.0% / 1 人 72.5% / 2 人 21.7% / 3 人以上 5.8%
```

**捕獲の 72.5% は鬼 1 人によるもの。**複数に追われていた時間は 14.7% で、
そこから 27.5% の捕獲が出ているので 1.87 倍の偏りはあるが、**絶対数が小さい。**
挟み撃ち対策を作っても届く範囲が狭い。

### 見つけたこと: 速度優位が実効では消えている

ルール上は逃げる側が 6.8% 速い（9.4 対 8.8）のに、追跡中の平均速度は:

| | 逃げる側 | 鬼 |
| --- | --- | --- |
| 上限 | 9.4 | 8.8 |
| 3v3 の実測 | **9.24** | **9.20** |
| 2v2 の実測 | 9.51 | 9.48 |

**鬼は自分の上限を超え、逃げる側は上限に届いていない。**
鬼はダッシュしていて、逃げる側はほとんどしていない。

**ここで «もっとダッシュさせる» に飛びつかなかったのは、
2026-08-11 に 3 通り試して全滅している記録があったから。**
日記を読む手順が実際に再発明を止めた。理由も既に測ってあって、
**逃げる側は毎ティック向きを選び直すので速度が上がるほど曲がりが甘くなり、
加速が距離に変換されない。**一方**鬼は直進でよい**のでダッシュがそのまま距離になる。
**同じ `DASH_MULT` でも追う側の方が得をする構造**で、これは行動では埋められない。
issue #74（balance, priority:high）として起票した。

### 駄目だった案: 逃走解除のヒステリシス

追跡が切れた 627 回のうち **64.3% が 3 秒以内に再開**していた（3v3）。
逃走の入口と出口が同じ `fleeTriggerDist`(13) なので、13m を挟んで出入りを繰り返し、
解除した数秒は拠点へ帰る側の思考に落ちて**開けた距離を自分から詰め直していた。**
出口だけ遠くする `fleeExitRatio` を入れた:

| ratio | 1v1 | 2v2 | 3v3 | 3v3 の再突入率 |
| --- | --- | --- | --- | --- |
| 1（現状） | 53.3% | 36.7% | 23.3% | 64.3% |
| 1.3 | 43.3% | 38.3% | 16.7% | 61.4% |
| 1.6 | 50.0% | **45.0%** | **13.3%** | 53.1% |

**機構は狙いどおり効いた**（再突入 64.3% → 53.1%）**のに、勝率は 3 構成中 2 つで悪化。**
2v2 だけ +8.3 と大きく伸びるが、1v1 −3.3、3v3 −10.0。

3v3 で壊れるのは、鬼が 3 人いると「最も近い鬼」が入れ替わり続けるので
**逃走モードから一生抜けられず、拠点にも遮蔽にも戻れない**からだと思われる。

**教訓 — 「往復が減った」は「良くなった」ではない。**
このサイクルは 2 回それをやった（前サイクルの壁際滞在も同じ形）。
**中間指標が意図どおり動いたことを、成果と読まないこと。**

**次にやること** — 行動側で残っている大きな穴が見当たらなくなってきた。
issue #74 の判断待ちの間は、**捕獲の 72.5% を占める「1 対 1 で追いつかれる」**の
中身をもう一段分解する（どのくらいの距離から詰められ始めるのか、
遮蔽を挟めているのか）。

## どこで負けているかを広く測った（採用なし、候補を 2 つ潰した）

**やったこと** — 高台まわりが 4 サイクル続けて不採用だったので、対象を決め打ちせずに
**捕獲された瞬間の状態**の分布を測った（30 試合 / seed0=1234、現在の master）。

```
                            3v3      2v2
全体の生存率                23.3%    36.7%
一度も見つからなかった       6.7%     0.0%
見られていたティック         1.7%    11.3%
初めて見られてから捕まるまで 13.1 秒  25.1 秒
--- 捕まった瞬間 ---
煙幕が残っていた            53.6%    18.4%
壁際 3m 以内                63.8%    42.1%
スタミナ 25% 未満            8.7%    13.2%
高台の上                     4.3%     2.6%
```

**スタミナ切れと高台はほぼ関係が無い。**残るのは壁と煙幕の 2 つ。両方潰した。

### 潰した候補 1: 壁際に寄りすぎている（issue #9）

捕獲の 63.8%（3v3）が壁から 3m 以内で起きている。面積では 25.4% しかないので
2.5 倍の偏り。**滞在時間で割っても偏りは残った**（3v3 で 47.7% の時間を壁際で
過ごしていて、そこで 63.8% が捕まる = 1.34 倍）。2v2 も同じ向き。

`fleeDirection` の壁ペナルティは即値で、`wallGap < 6` のとき `(6-wallGap) * 4`。
**最大 24 で、距離項（脅威 1 人あたり最大 +80）に対して弱すぎる。**
壁に向かえば «遠ざかれる» ので吸い寄せられていた。パラメータ化して振った:

| margin, cost | 3v3 生存 | 壁際滞在 | 2v2 生存 | 壁際滞在 |
| --- | --- | --- | --- | --- |
| 6, 4（現状） | 23.3% | 47.7% | 36.7% | 32.7% |
| 6, 12 | 20.0% | 37.8% | 40.0% | 20.2% |
| 9, 8 | 24.4% | 44.1% | 28.3% | 26.5% |
| 9, 16 | **11.1%** | 29.8% | **10.0%** | 10.4% |

**壁際滞在は狙いどおり下がるのに、生存率は良くならない。**
強くすると壊滅する（9,16 で 3v3 11.1% / 2v2 10.0%）。

**壁は症状であって原因ではなかった。** 壁際には遮蔽があり、中央は見つかる。
「壁際で死んでいる」は「追跡は端で終わる」というだけで、
**今の均衡（6, 4）はほぼ正しい。**相関を見て原因だと思い込むところだった。

### 潰した候補 2: 煙幕を使い切らずに死んでいる

3v3 では **53.6% が煙幕を残したまま捕まる**（1 人あたり 1.42 / 2 しか使わない）。
使用条件は `nearest < 8 && watched` の 2 つ。まず距離を振った:

| smokeDist | 3v3 生存 | 2v2 生存 |
| --- | --- | --- |
| 8（現状） | 23.3% | 36.7% |
| 11 | **23.3%** | 31.7% |
| 14 | **23.3%** | 30.0% |
| 17 | **23.3%** | 30.0% |

**3v3 は 1 ティックも変わらない**（捕獲件数まで同一）。
つまり**距離は門になっていない。効いているのは `watched` の方。**
2v2 はむしろ悪化するので、距離を緩める価値も無い。

そこで `watched` を外した（コードのコメントには
「見られていないのに撒くと、そこに居ることを教えるだけになる」とあるが、
**測った形跡が無い想定**だった）:

```
             3v3      2v2
現状        23.3%    36.7%
watched なし  7.8%    31.7%   ← 煙幕の使用は 1.42 -> 1.71 に増えている
```

**想定は正しかった。**使用回数は増えるのに生存率は 3 分の 1 になる。
`SMOKE_RADIUS` は 4 しかないので、見られていないときに撒くと
**自分を隠す効果より「ここに居る」という標識の効果が勝つ。**
コメントに根拠が付いた。

### 意外だったこと

**「使われていない資源がある」は、それ自体では欠陥の証拠にならない。**
53.6% が煙幕を残して死ぬのは無駄に見えるが、**使わせると弱くなる。**
これまで「使っていない仕様を使う」型の改善が当たってきたので同じ筋で見たが、
**使っていないのが正しい仕様もある。**

**次にやること** — この分布から残る手がかりは
**3v3 の「初めて見られてから捕まるまで 13.1 秒」**（2v2 は 25.1 秒）。
人数が増えると見つかった後の粘りが半分になる。これは issue #28
（鬼が同じ相手に群がる）の裏返しでもあるので、**逃げる側で
「複数人に追われている」ことを検知して動きを変える**余地がある。
`fleeDirection` は脅威を足し合わせるだけで、人数を見ていない。

## 既存の高台に予約を入れたら悪化した — 固まるのは損ではなかった（取り下げ）

**やったこと** — 前節の「次サイクルの第一候補」をそのまま実装した。
`hopToPerch` が選ぶ高台を `coop` の `'target'` 予約（`perch:<id>`）で 1 人に絞り、
**乗ったあとも主張し続ける**ようにした（TTL 0.4 秒なので黙ると空きに見える）。

**逆効果だった**（3v3 / 30 試合、seed0=1234）:

| | 予約なし | 予約あり |
| --- | --- | --- |
| 追跡開始時に高台へ立てていた | 22.2% | **16.7%** |
| そのうち生存 | 25.0% | **13.3%** |
| 全体の生存率 | 23.3% | **18.9%** |

2v2 は両方 36.7% で変化なし。

**意外だったこと — 固まっている人の方が生き残っていた。**
probe に「追跡開始時、4m 以内に別の高台組が居たか」を足して測ったら:

```
固まっていた人      4 / 20 人 (20.0%)   そのうち生存 50.0%
高台組ぜんぶ       20 / 90 人           そのうち生存 25.0%
```

**固まりは損ではなく得だった。**予約で追い出された人は、より悪い場所へ行っている。

**なぜ建設では効いて、ここでは効かないのか。**
差は**その資源が競合するかどうか**だった。

- **建設は競合する。** 2 人目が同じ台へ箱を運ぶと、**準備時間を丸ごと捨てる**うえ
  高台は 1 つしか増えない。だから排他が効いた（生存率 21.7% → 38.1%）。
- **既に在る高台に乗るのは競合しない。** 2 人目が乗るコストはゼロで、
  上面が `CATCH_VERTICAL` を超えていれば**何人乗っても全員が捕まらない。**
  排他する理由が無い。

**「同じ場所に集まる = 悪」ではない。**悪いのは
「同じ場所を作るために、複数人が同じ支払いをすること」だった。
予約を入れる前に、**その資源が本当に排他的かを確かめる。**

**次にやること** — 固まりの生存率が倍だったのは 4 人しか居ないサンプルなので
まだ何とも言えないが、向きが逆なら**積極的に同じ高台へ集める**方に振る価値がある。
`perchIsolation` で「踏み台の無い高台」に絞っている今の条件はそのままに、
味方が既に乗っている高台を**加点**する形が試せる。

## 運搬の 86.6% は «掴みが切れて» 終わっていた（原因の特定・修正は取り下げ）

**やったこと** — issue #31 の「掴み直しが 1 人 25 回」の中身を測った（3v3 / 30 試合）。

```
運搬の開始            2291 回
  拠点に届いた          307 回
  途中で掴みが外れた   1984 回  (86.6% が失敗)
```

**7 回に 6 回は箱を置き去りにして終わっている。**

**機構が `game.ts` に書いてあった:**

```ts
// 手が届く範囲を大きく超えたら離す。箱が動かせずに置いていかれた場合など。
if (gap > C.GRAB_RANGE + 1) { o.heldBy = -1; a.grabbed = -1; }   // 2.6m
```

**箱が詰まっているのに運び手が置き場所へ歩き続けるので、自分で掴みを切っている。**
`boxStall > 0.35` で跳ぶ処理も前へ進むので同じ向きに効く。
外れると仕事が idle に戻って選び直す。`avoid` は «諦めたとき» にしか入らないので、
**掴みが切れただけの箱はすぐ再選択できる。**これがループになっていた。

### 駄目だった案: 離れかけたら箱へ戻る（haulLeash）

| haulLeash | 運搬の開始 | 拠点に届いた | 失敗率 |
| --- | --- | --- | --- |
| 0（現状） | 2291 | 307 | **86.6%** |
| 0.8 | 5518 | 88 | **98.4%** |
| 1.0 | 3269 | 452 | 86.2% |

**0.8 は壊滅的。**戻る → 進む → また離れる の**振動**になり、開始回数が 2.4 倍。
1.0 は届いた回数が 1.5 倍になるが開始も増えるので失敗率は動かない。
**「戻る」だけでは、戻ったあとまた同じ向きに押して同じことが起きる。**

これで運搬まわりは **横ずらし（前サイクル）→ 掴み維持（今回）** と 2 連敗。
**どちらも «その場の動き» をいじる形だった。**次は仕事の側
（切れても `fetch` に戻して続行する / 押すのをやめて引く）を試す。

**次にやること** — issue #31 に 2 案を書いた。
順序として **#31 → #15（積み上げ）**。積むのは運ぶより難しいので、
運搬が 86.6% 失敗している間は積み上げも動かない。

## 運搬の失敗は «壁» ではなく «ルートを変えないこと» だった（取り下げ）

**やったこと** — issue #81（ユーザー報告「壁越しに箱を運ぼうとして失敗する」）に着手し、
まず割合を測った（3v3 / 30 試合、seed0=1234）。

```
運搬の開始                          2291 回（逃げる側 1 人あたり 1 試合で 約 25 回）
  うち箱と拠点の間に壁がある        72.9%
運搬中に箱が動いていなかったティック  33.3%
  壁を挟む運搬に限ると              34.9%
  壁を挟まない運搬に限ると          31.9%
準備フェーズに占める運搬の時間        14.5%
```

**壁は原因ではなかった。**壁の有無で詰まり率がほとんど変わらない（34.9% 対 31.9%）。
報告の «壁越しに失敗している» という見え方は正しいが、
**壁の向こうを選んだこと自体が失敗を作っているわけではない。**

**代わりに桁違いの数字が出た。拠点に要る箱は 8 個なのに、掴み直しが 1 人 25 回。**
そして**運搬時間の 3 分の 1 は箱が 1 ミリも動いていない。**

### 駄目だった案: 詰まったら横へずらす（haulNudge）

押す向きに直交する方向へ振り、詰まっている時間で左右を切り替える。**悪化した:**

| haulNudge | 箱が動いていなかったティック | 運搬の開始 |
| --- | --- | --- |
| 0（現状） | **33.3%** | 2291 |
| 0.4 | 40.1% | 2454 |
| 0.7 | 41.2% | 2735 |

**横へ振っている間も箱は進まない**ので、詰まり時間が伸びて掴み直しも増える。

### ユーザーの追加報告が方向を示していた

> ひっかかったあと何度も同じルートで運ぼうとして失敗し、諦めるパターンが多々ある

**問題はルートの側で、私が触ったのは微小な動きの側だった。**
運搬は `moveTo` で置き場所へ向かうだけで、**箱が通れる経路かを一度も評価していない。**
詰まっても同じ線を押し続け、1.2 秒で諦め、`avoid` が切れるとまた同じ組を選ぶ。

### 基準の取り違えを直した（issue #31 を low → high に戻した）

> 31 を見る限り、勝敗に影響がないから放置ってこと？

**そのとおりで、私の誤り。**このループの目的は
**「勝率を上げること」と「挙動の欠陥を潰すこと」の 2 つ**であり、
勝率が動かないことは見えている欠陥を放置してよい理由にならない。
「36.9% → 37.1% で変わらなかった」を根拠に priority を下げたのは基準の取り違えだった。

**教訓 — 採否の基準が 2 つあるとき、片方だけで判断していないか毎回確かめる。**
このサイクルで «勝率が動かないから低優先» を 1 回、
«中間指標が動いたから成果» を 3 サイクル続けてやっている。**どちらも同じ間違い方。**

**次にやること** — issue #31 に書いた 3 つ。
(1) 詰まったら箱ではなく置き場所を替える、(2) 箱の経路を nav で取る、
(3) 同じ (箱, 置き場所) の組を再選択しない。

# バランス変更の記録

改善サイクル（`/improve-seeker`、`/improve-hider`、`/improve-balance`）の
1 サイクルごとに追記する。勝率はすべて「逃げる側」のもの。

**測定のぶれについて。** 24 試合の勝率は 3v3 で 20 ポイント以上ぶれる（同じコードで
16.7% と 37.5% が出た）。144 試合でも、1v1 と 2v2 はシードによって改善と悪化が
入れ替わることがある。採否の判断は**最低 300 試合、かつ 1v1 / 2v2 / 3v3 の
3 構成が同じ向きに動いているか**で行うこと。24 試合は「異常終了しないこと」の確認用。

## 2026-08-10 逃走中の方向決めの振れを抑える

- 変更: `fleeDirection` に「直前のティックで選んだ方向から離れるほど減点する」項
  （`fleeTurnCost`、既定 30）を追加。`npm run tune` の探索対象にも入れた（範囲 [0, 60]）。
- 理由: `_probe` で、逃走モード中の平均速度が逃げる側 8.45 m/s に対して鬼 8.81 m/s だった。
  最高速度は逃げる側が上（9.4 対 8.8）なのに、実際に追われている間は遅い。
  毎ティック 24 方向を採点し直すため選択が隣の候補へ飛び移り続け、
  平均 10.7 度/tick・5.2% のティックで 90 度超の切り返しが起きていた。
  修正後は 6.4 度/tick、平均速度 9.05 m/s（鬼 9.00）で、鬼を上回った。
- 勝率: 1v1 23.0% / 2v2 36.3% / 3v3 40.0%（前回: 20.3 / 28.3 / 33.3）
  1v1・2v2 は各 300 試合、3v3 は各 180 試合（3 シード）。`fleeTurnCost` を
  0 / 14 / 30 と振ると 3 構成すべてで単調に上がった（平均 27.3 → 30.4 → 33.1%）。
  30 でもまだ頭打ちになっていない。
- 注意: **24 試合の勝率は 3v3 で 20 ポイント以上ぶれる。**
  同じコードが 24 試合で 16.7%、80 試合で 37.5% になった。144 試合でも、
  1v1 と 2v2 はシード次第で改善と悪化が入れ替わった。
  採否の判断は最低 300 試合、かつ 3 構成の向きが揃うかで見ること。

## 2026-08-11 箱を乗り越える向きを逃走候補に入れた

- 変更: `fleeDirection` のレイが箱で止まっていたのを、`CLIMB_REACH`（1.64）以下の
  高さの箱なら通過扱いにした。その向きを選んだときは詰まる前にジャンプする。
  代償として `fleeClimbCost`（既定 20）を減点。`tune` の探索範囲は [0, 40]。
- 理由: 小箱の高さは 1.3 で跳べば登れるのに、`nav` が登れる箱も一律で塞がれた扱いに
  するため `clear < 2` で候補から外れ、**箱を挟める向きを最初から全部捨てていた**。
  1v1 の計測で、逃走中に地面より高い位置に居るティックは 7.2% → 11.3%、
  生存率 52.5% → 72.5%、捕獲 19 → 11 件。視線を切る回数は 13.0 → 14.0 回/分で横ばいなので、
  効いているのは遮蔽ではなく「行き止まりが減ること」。
- 勝率（`_ab.ts`、1v1・2v2 は各 300 試合、3v3 は 180 試合、3 シード）:

  | 構成 | 前 | 後 |
  | --- | --- | --- |
  | 1v1 | 55.3% | **62.0%** |
  | 2v2 | 59.0% | **64.0%** |
  | 3v3 | 61.7% | **67.8%** |

  前の値は自分でも測り直して 55.3% と一致。3 構成が同じ向きに動いた。
  `fleeClimbCost` は 0〜45 まで振ったが単調ではなく、どの値でも前を下回らなかった。
  効いているのは値ではなく「乗り越えを候補に入れたこと」自体。
- 駄目だった案: 鬼の位置を速度で外挿して距離の基準にする案は壊滅した
  （1v1 53.3% → 5.0%）。追ってくる相手の速度はこちらを向いているので、
  予測点が自分の真上に来て「離れる向き」の勾配が消える。詳細は日記。

## 2026-08-11 鬼のダッシュ消費を逃げる側と揃えた（52 → 34）

- 変更: `SEEKER_DASH_COST` 52 → 34（`DASH_COST` と同じ）。**両陣営の差は速度だけになった**
  （逃 9.4 / 鬼 8.8）。他の定数は触っていない。
- 理由: 逃げる側が全構成で目標帯（35〜50%）を +12〜+18 も超えていた
  （1v1 62.0% / 2v2 64.0% / 3v3 67.8%）。原因を測ると、**鬼はやることをやったうえで
  届いていなかった**。

  | | 1v1 | 2v2 | 3v3 |
  | --- | --- | --- | --- |
  | 初発見まで（追跡開始から） | 2.7 秒 | 5.4 秒 | 6.6 秒 |
  | 見られている割合 | 41.0% | 80.8% | 91.1% |
  | 鬼のダッシュ率 / 平均スタミナ | 83.1% / 23 | 84.7% / 23 | 79.2% / 29 |
  | 逃げる側のダッシュ率 / 平均スタミナ | 34.6% / 75 | 23.3% / 88 | 26.2% / 86 |

  **見つけている。ずっと見えている。全力で追っている。それでも捕まえられない。**
  探索の問題ではなく追走の問題で、しかも鬼はスタミナを使い切っている。
  回復は共通 19/秒なので持続ダッシュ率は逃げ側 19/34 = 56%、鬼 19/52 = 37%。
  使い切ったときの平均速度は逃げ側 12.3 m/s に対し鬼 10.6 m/s。**構造的に届かない。**
- 3 段階で測った（1v1・2v2 は各 300 試合、3v3 は各 180 試合、3 シード合算）。

  | `SEEKER_DASH_COST` | 1v1 | 2v2 | 3v3 |
  | --- | --- | --- | --- |
  | 52（変更前） | 62.0% | 64.0% | 67.8% |
  | 42 | 48.3% | 56.7% | 60.6% |
  | **34（採用）** | **47.0%** | **48.0%** | **51.1%** |

  3 構成すべてで単調に下がり、34 で全構成が目標帯に収まった（3v3 の 51.1% は +1.1 で
  180 試合の誤差の内側）。42 では 2v2・3v3 が残るので 34 を採った。
- 遊び心地: 追いかけっこは成立したまま。発見から捕獲まで 20.9〜35.1 秒、
  視線切りは 7.4〜10.6 回/人、5 秒窓で距離が開くのは 33〜37%。
  鬼のスタミナも 29〜38 まで落ちるので「ここぞで使う」判断は残っている。
  消費を揃えても「速い方が勝つ」にはならない — 鬼の方が遅いので、
  逃げる側が全力で走れば依然として振り切れる（同条件で 11.5 対 12.3 m/s）。
- **注意: この値は「逃げる側がダッシュを使っていない」前提で釣り合っている。**
  issue #10 が直って逃げる側が全力で走るようになったら、勝率は上へ戻る。
  逆に鬼側の行動（issue #11 の探索・分担）が良くなると、今度は下へ外れる。
  **どちらかが動いたら必ず測り直すこと。**

## 2026-08-11 遮蔽を増やす案は不採用（変更なし）

- 変更: **なし。** 小さい箱の高さを 1.3 → 1.5 に上げる案を測って取り下げた。
  箱の高さを `BOX_HEIGHT_SMALL` / `BOX_HEIGHT_BIG` として `config.ts` に出しただけ
  （値は据え置き）。issue は GitHub issue へ移した。
- 理由: 視線は目線（`EYE_HEIGHT` = 1.4）から相手の頭（同じ高さ）へ引くので、
  **1.4 以下の箱は遮蔽としてまったく働いていない**。箱の 6 割が小さい箱なので、
  遮蔽として数えられるのは 11 個中 4 個だけ。準備フェーズで 32 秒かけて積んだ砦が
  視線を素通しにしていた。1.5 に上げれば効くはずだった。
- 結果: 遮蔽としては狙いどおり効いた（見られている割合は 3v3 で 76.0% → 50.4%、
  2v2 で 71.1% → 56.0%）のに、勝率は 3 構成そろってわずかに下がった。

  | 構成 | 小箱 1.3 | 小箱 1.5 | 試合数 |
  | --- | --- | --- | --- |
  | 1v1 | 24.7% | 20.3% | 各 300（100 × 3 シード） |
  | 2v2 | 35.3% | 33.3% | 各 300 |
  | 3v3 | 38.3% | 36.1% | 各 180（60 × 3 シード） |

  1 構成あたりの差は誤差に埋もれるが、**3 構成の向きが揃っている**ので
  「効果なし」ではなく「わずかに悪い」と読む。
- **なぜ悪化するのかは分かっていない。**「遮蔽は逃げる側の索敵にも効くので、
  遮蔽を増やすと不意打ちされる」という仮説を測ったが、鬼に見られているのに
  逃げる側が鬼を把握できていない時間の割合は 1.3% → 1.7%（2v2）しか動かず、
  説明になっていない。仮説は外れ。
- **注意: この A/B は issue #8 の修正が入る前のコードで測っている**（だから基準値が
  24.7/35.3/38.3 と低い）。修正後の現在は 1v1 55.3% / 2v2 59.0% / 3v3 61.7% で
  状況が反転しているので、遮蔽を増やす案を再検討するなら測り直すこと。
  「遮蔽を増やしても勝敗は決まらない」という結論自体は、
  補給パックのときと同じ形の空振りが 2 回続いたという事実として残す。
- 計測用に `src/sim/_probe-chase.ts`（追跡フェーズの視界と追走）と
  `src/sim/_ab.ts`（3 シード合算の採否判定）を置いた。

## 2026-08-11 逃げ道の多い場所を優先する案は不採用（変更なし）

- 変更: **なし。** `fleeDirection` に「着地点から走り出せる向きの割合」を加点する項
  （`fleeOpenWeight`）を試したが、測って取り下げた。`npm run sim` に `--seed` だけ追加。
- 理由: 3 構成すべてで 0（＝入れない）が最良だった（各値 120 試合 / 3 シード、3v3 は 90 試合）。
  単調ではなく 2v2 は 40 より 80 の方が高いので、効いているのは重みの大きさではなく
  項の有無の方。

  | fleeOpenWeight | 1v1 | 2v2 | 3v3 |
  | --- | --- | --- | --- |
  | 0（現状のまま） | 53.3% | 65.0% | 65.6% |
  | 40 | 41.7% | 55.8% | 53.3% |
  | 80 | 26.7% | 57.5% | 48.9% |

  開けた場所は逃げ道が多いと同時に鬼から見通せる場所でもあり、`fleeCoverBonus` と
  逆を向く項を足していた。詳細は `docs/journal/2026-08-11.md` と issue #9。
- 勝率: 変更なしなので 1v1 53.0% / 2v2 55.0% / 3v3 56.0% のまま（issue #11 の実測値）。

## 2026-08-10 見失った鬼の方へ帰らないようにした

- 変更: 逃走を解いたあとの待機・帰還で、目的地までの道のりが「直近に鬼が居た場所」へ
  近づくなら、その移動をやめて離れる向きへ退くようにした（`hider.ts` の `evade`）。
  逃走判定の `knownThreats`（記憶 4 秒）とは別に、判断用の記憶
  `threatMemory`（10 秒）と、割ってはいけない距離 `threatKeepAway`（10 m）を追加。
- 理由: `_probe` で、1v1 の捕獲 21 件のうち **76.2% が「捕まる直前 1.5 秒に鬼へ向かって
  走っていた」**、捕獲地点は拠点から平均 6.6 m だった。逃走判定の記憶が 4 秒で切れると
  `evade` は「拠点へ帰る」分岐に落ち、鬼と拠点の間に自分が居る形（逃げた直後は必ずこうなる）
  だと最短経路で鬼の正面に出ていた。修正後は同じ指標が 12.5%、捕獲地点と拠点の距離は 17.8 m。
- 勝率: **1v1 53.0% / 2v2 55.0% / 3v3 56.0%（前回: 24.7 / 35.3 / 40.0）。各 300 試合。**
  この数字はマージ時に `fleeTurnCost` 込みの master を取り込んだうえで測り直したもの。
  作業中は 24 試合 ×2 シードで 39.6 / 43.8 / 52.1 と読んでおり「3v3 だけ超過」と
  結論しかけたが、300 試合では **3 構成すべてが目標帯（35〜50%）の上**だった。
  超過幅は 1v1 +3 / 2v2 +5 / 3v3 +6 で、人数が増えるほど大きい。
  初補足までの時間も 1v1 で 49.4 → 64.0 秒と伸びており、鬼が見つけられていない。
  逃げる側を弱めて帳尻を合わせる話ではないので、鬼側の課題として issue #11 に立てた。


## 2026-08-10 逃走中の硬直を解消

- 変更: `fleeDirection` が「どの向きにも走れる幅が無い」と判断したときに
  移動入力を空で返していたのをやめ、一番遠くまで進めて脅威から離れる向きへ押し込むようにした。
  速度が出ない状態が続いたら乗り越えも試みる。
- 理由: `_probe` で、3v3 の追跡フェーズのうち 4.7% のティックで逃走者の移動入力が
  ゼロになっており、その大半が箱の近くだった。最長で 32.3 秒その場に固まっていた。
  1v1 では硬直は 0% で、こちらは純粋に追いつかれている（原因が別）。
- 勝率: 1v1 12.5% / 2v2 25.0% / 3v3 29.2%（前回: 12.5 / 33.3 / 16.7）
  3v3 の平均生存人数は 0.25 → 0.46。硬直ティックの割合は 4.7% → 0%。

## 2026-08-10 遊び心地の調整

- 変更: 移動速度を 6.6 → 9.4（鬼 8.8）に引き上げ、アリーナを 36x36 → 44x44 に拡大。
  ジャンプに踏み切りの推進力を追加、ジャンプ台を設置。逃げる側に煙幕（2 回）を追加。
  鬼のダッシュ消費を逃げる側の 1.5 倍にした。拠点の評価に隅のペナルティを追加。
- 理由:
  - 速度を上げただけでは逃げ側勝率が落ちた（AI の先読み距離が旧速度のままで壁に突っ込んでいた）。
    `fleeDirection` のレイと `followPath` の到達判定を速度に合わせて伸ばして回復。
  - トレースで、拠点が隅（壁まで 1.9 m）に選ばれ、追跡開始 1.1 秒で発見されて
    逃げ道が無いまま捕獲される試合を確認。「中央から遠いほど良い」の評価が隅を選ばせていた。
- 勝率: 1v1 12.5% / 2v2 33.3% / 3v3 16.7%（前回: 12.5 / 20.8 / 25.0）

## 2026-08-10 初期構築

- 変更: ルールベース AI 一式、拠点の分散、補給パック、ジャンプ台、移動速度の引き上げ。
- 理由: トレースで判明した主な欠陥は次の 3 つ。
  - 逃げる側が状態遷移のたびに入力を空で返し、1 ティックおきに停止していた。
  - 掴んだ箱を衝突解決の後に動かしていたため、押している本人に押し戻されて箱が永久に動かなかった。
  - 準備フェーズの経路が中央のケージを突っ切り、境界に押し戻されて追跡開始まで動けなかった
    （拠点まで届かず、開幕 2.4 m の距離で即捕獲されていた）。
- 勝率: 1v1 12.5% / 2v2 20.8% / 3v3 25.0%

### 未解決

- **1v1 だけが目標に届いていない。** 現状（`fleeTurnCost` 導入後、3 シード合算）は
  1v1 24.7% / 2v2 35.3% / 3v3 38.3%。2v2 と 3v3 は目標帯（35〜50%）に入った。
- 残っている最大の筋は **追われている間に逃げる側がダッシュを使っていない**（issue #10）。
  使用率は逃げ側 20〜29%（平均スタミナ 84〜91 残し）、鬼 67〜76%（同 26〜35）。
  ルールとしては逃げ側が有利（速度 9.4 対 8.8、ダッシュ消費 34 対 52）なので、
  これは行動側で解く問題。バランス側で速度や視界を触ると、行動が直った後に逆へ振れる。
- 目標はどの構成でも 35〜50%。

# バランス変更の記録

改善サイクル（`/improve-seeker`、`/improve-hider`、`/improve-balance`）の
1 サイクルごとに追記する。勝率はすべて「逃げる側」のもの。

**測定のぶれについて。** 24 試合の勝率は 3v3 で 20 ポイント以上ぶれる（同じコードで
16.7% と 37.5% が出た）。144 試合でも、1v1 と 2v2 はシードによって改善と悪化が
入れ替わることがある。採否の判断は**最低 300 試合、かつ 1v1 / 2v2 / 3v3 の
3 構成が同じ向きに動いているか**で行うこと。24 試合は「異常終了しないこと」の確認用。

## 2026-08-11 鬼が到達できない目標を選び直すようにした

- 変更: 目標への最短距離を更新できない時間が `repickAfter`（既定 2 秒）を超えたら、
  その目標を諦めて選び直す。諦めた目標は 12 秒のあいだ半径 5m を避ける。
  `chase` 中は対象外。
- 理由: `pickPatrolGoal` は到達したときしか選び直さないので、到達できない目標を
  掴むと二度と選び直さない。3v3 のトレースで鬼 3 人が試合の後半 36〜54 秒間
  まったく動かない試合を確認した（追跡時間 68 秒のうち 50 秒以上、鬼が 1 人も
  探索していない）。壁は `findBlocker` の対象外なので詰まり時の復帰も働かない。
- 勝率: 1v1 37.0% / 2v2 8.0% / 3v3 0.0%（master: 42.0 / 10.0 / 1.0）
  CI 測定、構成ごとに 4 seed × 25 試合。3 構成すべてで鬼が強くなった。
- **勝率の伸びが小さいことに注意。** 2v2 / 3v3 は既に 1〜10% で伸びしろが無い。
  この修正の価値は勝率よりトレース（半分の時間止まっていた鬼が動く）に出ている。
  **勝率が飽和している構成では、数字だけ見ていても欠陥は見えない。**

  | --- | --- | --- | --- |
  | 1v1 | 42.0% | 40.0% | −2.0 pt |
  | 2v2 | 10.0% | 8.0% | −2.0 pt |

- 判断: 逃げ側が 3v3 で 1% とほぼ全滅している状況で、わずかでも逃げ側を弱める変更は
  入れない。設計上の主張（目線より高い箱は視線を止めるべき）は残るので、
  **逃げ側が目標帯に戻ってから再挑戦する**こと。

## 2026-08-11 待機先を高所にする案は不採用（変更なし）

  拠点から高所に差し替える」形で実装したが、勝率が動かなかったので取り下げた。

  3v3 1.0% → 1.0%（±0）。向きが揃わないので差なし。

  **高所に居る時間を倍にしても勝率が動かない。**高所へ行くコスト（拠点の遮蔽を捨てる、
  登る間に足が止まる）が、捕獲されない利得と釣り合っている可能性がある。
- これで高所の攻略は 4 回目の失敗（`fleePerchBonus` / 降りない / 待機先の差し替え / 本件）。
  「捕獲 88 件中 87 件が高さ 1.6 未満」という賞金は本物なのに手段が成立しない。
  次に触るなら「なぜ高所に居ても勝率が上がらないのか」を測る側から入ること。
- 副産物として 2 つ分かった（どちらも issue にした）。
  - **運搬の空回りは「再挑戦」ではなく「検出の遅れ」だった**（issue #31 に訂正）。
    `abandon` の避ける時間を 6 秒 → 無限大にしても数字が動かない（36.9% → 37.1%）。
    空回り 6.9 秒/試合 ÷ 詰まり判定 1.2 秒 ≒ 諦めた回数で説明がつく。
  - **ロックした箱が鬼を呼び寄せている**（issue #32）。鬼の巡回先の採点は
    ロック箱の 5m 以内に最大 +8 点する。逃げる側は 7.5 個を自分の拠点の外周に
    ロックしており、砦を作る行為が居場所の宣伝になっている。

  3 人いても網が 1 人ぶんにしかなっていなかった。
- 勝率: 1v1 28.3% / 2v2 4.0% / 3v3 5.6%（前回: 28.3 / 45.0 / 57.8）
  1v1・2v2 各 300 試合 / 3v3 180 試合、3 シード合算。`_sweep.ts` と `_ab.ts` の
  両方で同値を確認。1v1 はシード別まで完全に同一（鬼が 1 人なので分岐に入らない）。

- **逃げ側が目標帯（35〜50%）を大きく下回る。** 鬼の行動改善としては正しいが、

## 2026-08-11 鬼が現在位置ではなく迎撃点を追う

- 変更: 鬼の追跡目標を相手の現在位置から、速度で先読みした迎撃点に変更
  （`chaseLeadTime`、既定 0.6 秒）。視線は相手に置いたまま体だけ先回りさせる。
- 理由: 鬼は逃げ側より遅い（8.8 対 9.4）ため、現在位置を追う純追尾では真後ろに
  つくだけで原理的に追いつけない。1v1 のトレースで、鬼が 50 秒間 `chase` のまま
  9〜13 m の距離を一度も詰められていないのを確認した。
  先読みは 0.6 秒が最良で、1.2 秒以上はほとんど効かない（相手が曲がる前提の
  位置へ先行してしまい、直進されると置いていかれる）。
- 勝率: 1v1 29.7% / 2v2 45.7% / 3v3 60.6%（前回: 61.0 / 61.7 / 65.0）
  同一コードでの A/B、1v1・2v2 各 300 試合 / 3v3 180 試合、3 シード合算。
  シード別 9 個のうち 8 個が改善（3v3 の 1 つだけ 50.0 → 61.7 と逆を向いた）。
  **3v3 は効きが弱く -4.4 ポイントに留まる。** 鬼が 3 人いる方が取り逃す傾向は
  迎撃を入れても残っており、担当領域の分散か挟み込みに次の筋がある。
- 取り下げ: 追跡中に補給パックへ寄り道してブーストを取る案。3v3 seed=1234 で
  43.8% → 25.0% と大きく効いたが、seed=555001 では 30.0% → 32.5% と符号が反転した。
  試合数を増やして測り直す（issue #17）。

## 2026-08-10 逃走中の方向決めの振れを抑える

- 変更: `fleeDirection` に「直前のティックで選んだ方向から離れるほど減点する」項
  （`fleeTurnCost`、既定 30）を追加。`npm run tune` の探索対象にも入れた（範囲 [0, 60]）。
- 理由: `_probe` で、逃走モード中の平均速度が逃げる側 8.45 m/s に対して鬼 8.81 m/s だった。
  最高速度は逃げる側が上（9.4 対 8.8）なのに、実際に追われている間は遅い。
  毎ティック 24 方向を採点し直すため選択が隣の候補へ飛び移り続け、
  平均 10.7 度/tick・5.2% のティックで 90 度超の切り返しが起きていた。
  修正後は 6.4 度/tick、平均速度 9.05 m/s（鬼 9.00）で、鬼を上回った。
- 勝率: 1v1 23.0% / 2v2 36.3% / 3v3 40.0%（前回: 20.3 / 28.3 / 33.3）
  1v1・2v2 は各 300 試合、3v3 は各 180 試合（3 シード）。`fleeTurnCost` を
  0 / 14 / 30 と振ると 3 構成すべてで単調に上がった（平均 27.3 → 30.4 → 33.1%）。
  30 でもまだ頭打ちになっていない。
- 注意: **24 試合の勝率は 3v3 で 20 ポイント以上ぶれる。**
  同じコードが 24 試合で 16.7%、80 試合で 37.5% になった。144 試合でも、
  1v1 と 2v2 はシード次第で改善と悪化が入れ替わった。
  採否の判断は最低 300 試合、かつ 3 構成の向きが揃うかで見ること。

## 2026-08-11 箱を乗り越える向きを逃走候補に入れた

- 変更: `fleeDirection` のレイが箱で止まっていたのを、`CLIMB_REACH`（1.64）以下の
  高さの箱なら通過扱いにした。その向きを選んだときは詰まる前にジャンプする。

- 理由: 小箱の高さは 1.3 で跳べば登れるのに、`nav` が登れる箱も一律で塞がれた扱いに
  するため `clear < 2` で候補から外れ、**箱を挟める向きを最初から全部捨てていた**。
  1v1 の計測で、逃走中に地面より高い位置に居るティックは 7.2% → 11.3%、
  生存率 52.5% → 72.5%、捕獲 19 → 11 件。視線を切る回数は 13.0 → 14.0 回/分で横ばいなので、
  効いているのは遮蔽ではなく「行き止まりが減ること」。
- 勝率（`_ab.ts`、1v1・2v2 は各 300 試合、3v3 は 180 試合、3 シード）:

  | 構成 | 前 | 後 |
  | --- | --- | --- |
  | 1v1 | 55.3% | **62.0%** |
  | 2v2 | 59.0% | **64.0%** |
  | 3v3 | 61.7% | **67.8%** |

  前の値は自分でも測り直して 55.3% と一致。3 構成が同じ向きに動いた。
  `fleeClimbCost` は 0〜45 まで振ったが単調ではなく、どの値でも前を下回らなかった。
  効いているのは値ではなく「乗り越えを候補に入れたこと」自体。
- 駄目だった案: 鬼の位置を速度で外挿して距離の基準にする案は壊滅した
  （1v1 53.3% → 5.0%）。追ってくる相手の速度はこちらを向いているので、
  予測点が自分の真上に来て「離れる向き」の勾配が消える。詳細は日記。

## 2026-08-11 追跡時間の人数補正を反転した（人数が増えるほど長く）

- 変更: `huntTimeFor` を `HUNT_TIME - (seekers-1)*8` から
  `HUNT_TIME - max(0, 3-seekers)*6` に。あわせて `HUNT_TIME` を 70 → 68 にして
  「HUNT_TIME が最長」の不変条件を保った（`src/sim/*` の打ち切り上限がこれを前提にしている）。
  追跡時間は **1v1 70 → 56 秒 / 2v2 62 秒（変更なし）/ 3v3 54 → 68 秒**。
- 理由: 元の式は「鬼が増えれば盤面を虱潰しにする速度が上がるので、そのぶん短くして
  釣り合いを取る」という理屈だった。**測ると逆だった。**
  探索が速くなる効果より「1 人でも残れば逃げ側の勝ち」の増幅の方が強く、
  逃げ側勝率は人数に対して単調に上がる。つまり**最も強い側に最も短い時間を与えていた**。
  PR #18（鬼が迎撃点を追う）が入った状態で、構成間の開きが 29.5 ポイントに達していた。
- 勝率（**PR #18 が入った状態**、1v1・2v2 各 300 試合 / 3v3 180 試合、3 シード合算）:

  | | 1v1 | 2v2 | 3v3 | 開き |
  | --- | --- | --- | --- | --- |
  | 反転前（70/62/54） | 28.3% | 45.0% | 57.8% | 29.5 pt |
  | **反転後（56/62/68）** | **44.0%** | **45.0%** | **48.3%** | **4.3 pt** |

  3 構成すべてが目標帯（35〜50%）に収まった。
  **2v2 は追跡時間が 62 秒のまま変わらないので 45.0% で完全に不動** — 対照群として、
  動いたのが追跡時間の効果であることを裏付けている。
- **マージ時の実測（各 600 試合、CI）— 上の表とは別の絵になった。**
  この PR のあとに PR #23（1 つの目撃情報へ向かう鬼を 1 人に制限）がマージされ、
  前提が変わったため、取り込み時に現 master 基準で測り直した。

  | | 1v1 | 2v2 | 3v3 | 開き |
  | --- | --- | --- | --- | --- |
  | 反転前（現 master） | 27.0% | 10.0% | 1.0% | 26.0 pt |
  | **反転後（この PR）** | **42.0%** | 10.0% | 1.0% | **41.0 pt** |

  **残ったのは 1v1 を帯に入れる効果だけ**（+15.0 pt）。2v2 は時間が変わらないので当然不動、
  3v3 が動かないのは効果が無いのではなく、初補足 41.0 秒・平均生存 0.01 人で
  **54 秒の時点で既に全員捕まっており、68 秒に伸ばしても差が出ようがない**（マスク）。
- **この節の「逃げ側勝率は人数に対して単調に上がる」はもう成り立たない。**
  #23 のあとは 27 → 10 → 1% と単調に下がる。人数が増えるほど時間を伸ばす今の向きは、
  逃げ側が回復したときに 3v3 へ不利に働く。**逃げ側が帯に戻ったら必ず測り直すこと。**
  取り込み時点では退行が無く 1v1 が改善するので採用した。
- **この変更は PR #18 が入っていることが前提。** #18 抜きの master 単体で測ると
  1v1 68.7% / 2v2 65.0% / 3v3 53.3% で、**1v1 が大きく上振れして逆効果になる**。
  #18 は 1v1 の鬼を劇的に強くする（61.0% → 29.7%）一方 3v3 はほとんど変えない（65.0% → 60.6%）ので、
  人数に対する傾きそのものを変える。補正はその傾きに合わせて決まる。
  **鬼側・逃げ側の行動が大きく変わったら、この式は毎回測り直すこと。**

## 2026-08-11 箱を持ち上げて積めるようにした（機能追加）

- 変更: 箱を掴んだままジャンプすると箱も持ち上がり、別の箱の上で手を離すと積み上がる。
  `Obstacle` に底面の高さ `y` を追加し、上面を `y + h` にした（既存はすべて `y = 0`
  なので `h` の意味は変わらない）。視線・支え・通行判定をすべて上面基準に直した。
- 理由: 遊びの手札を増やすため（ユーザー要望）。低い箱（1.3 m）は目線（1.4 m）より
  低いので単体では視線を止められないが、2 段に積めば 2.6 m になって遮蔽になる。
  準備フェーズ 32 秒の使い道が増える。
- 設計上の判断: 垂直の重なりが `STEP_HEIGHT`（0.35）以内なら「上に乗っている」とみなす。
  ジャンプの頂点 1.29 m から高さ 1.3 m の箱へ載せるのに必要で、
  エージェントが段差を越えるのと同じ許容なので新しい概念を持ち込まずに済む。
  副産物として大きい箱（2.2 m）の上には跳んでも載らず、ジャンプ台が要る。段階になった。
  ジャンプ台だけは薄い（0.25 m）ため許容内に入ってしまうので、
  従来どおり footprint ごと箱を置けないままにしてある（塞ぐと踏めなくなる）。
- 勝率: 1v1 55.3% → 55.3% / 2v2 59.0% → 59.7% / 3v3 61.7% → 60.0%
  （1v1・2v2 は各 300 試合、3v3 は各 180 試合、3 シード合算）。
  **3 構成の向きが揃わないので差なし。** AI がまだ意図的に積んでいないため
  （追跡開始時点で積まれている箱は 0.03〜0.33 個/試合）。
  積み方の作り込みは issue で `/improve-hider` へ渡した。
  **AI が積むようになったら必ず測り直すこと。** 遮蔽が増えるぶん逃げる側が強くなり、
  現在すでに目標帯の上（55〜60%）なのでさらに離れる可能性がある。
- 検証: `src/sim/_stacktest.ts`。入力を手で組んで
  掴む → 跳ぶ → 運ぶ → 離す、で下の箱の上面 1.30 に着地することを確認する。

## 2026-08-11 遮蔽を増やす案は不採用（変更なし）

- 変更: **なし。** 小さい箱の高さを 1.3 → 1.5 に上げる案を測って取り下げた。
  箱の高さを `BOX_HEIGHT_SMALL` / `BOX_HEIGHT_BIG` として `config.ts` に出しただけ
  （値は据え置き）。issue は GitHub issue へ移した。
- 理由: 視線は目線（`EYE_HEIGHT` = 1.4）から相手の頭（同じ高さ）へ引くので、
  **1.4 以下の箱は遮蔽としてまったく働いていない**。箱の 6 割が小さい箱なので、
  遮蔽として数えられるのは 11 個中 4 個だけ。準備フェーズで 32 秒かけて積んだ砦が
  視線を素通しにしていた。1.5 に上げれば効くはずだった。
- 結果: 遮蔽としては狙いどおり効いた（見られている割合は 3v3 で 76.0% → 50.4%、
  2v2 で 71.1% → 56.0%）のに、勝率は 3 構成そろってわずかに下がった。

  | 構成 | 小箱 1.3 | 小箱 1.5 | 試合数 |
  | --- | --- | --- | --- |
  | 1v1 | 24.7% | 20.3% | 各 300（100 × 3 シード） |
  | 2v2 | 35.3% | 33.3% | 各 300 |
  | 3v3 | 38.3% | 36.1% | 各 180（60 × 3 シード） |

  1 構成あたりの差は誤差に埋もれるが、**3 構成の向きが揃っている**ので
  「効果なし」ではなく「わずかに悪い」と読む。
- **なぜ悪化するのかは分かっていない。**「遮蔽は逃げる側の索敵にも効くので、
  遮蔽を増やすと不意打ちされる」という仮説を測ったが、鬼に見られているのに
  逃げる側が鬼を把握できていない時間の割合は 1.3% → 1.7%（2v2）しか動かず、
  説明になっていない。仮説は外れ。
- **注意: この A/B は issue #8 の修正が入る前のコードで測っている**（だから基準値が
  24.7/35.3/38.3 と低い）。修正後の現在は 1v1 55.3% / 2v2 59.0% / 3v3 61.7% で
  状況が反転しているので、遮蔽を増やす案を再検討するなら測り直すこと。
  「遮蔽を増やしても勝敗は決まらない」という結論自体は、
  補給パックのときと同じ形の空振りが 2 回続いたという事実として残す。
- 計測用に `src/sim/_probe-chase.ts`（追跡フェーズの視界と追走）と
  `src/sim/_ab.ts`（3 シード合算の採否判定）を置いた。

## 2026-08-10 見失った鬼の方へ帰らないようにした

- 変更: 逃走を解いたあとの待機・帰還で、目的地までの道のりが「直近に鬼が居た場所」へ
  近づくなら、その移動をやめて離れる向きへ退くようにした（`hider.ts` の `evade`）。
  逃走判定の `knownThreats`（記憶 4 秒）とは別に、判断用の記憶
  `threatMemory`（10 秒）と、割ってはいけない距離 `threatKeepAway`（10 m）を追加。
- 理由: `_probe` で、1v1 の捕獲 21 件のうち **76.2% が「捕まる直前 1.5 秒に鬼へ向かって
  走っていた」**、捕獲地点は拠点から平均 6.6 m だった。逃走判定の記憶が 4 秒で切れると
  `evade` は「拠点へ帰る」分岐に落ち、鬼と拠点の間に自分が居る形（逃げた直後は必ずこうなる）
  だと最短経路で鬼の正面に出ていた。修正後は同じ指標が 12.5%、捕獲地点と拠点の距離は 17.8 m。
- 勝率: **1v1 53.0% / 2v2 55.0% / 3v3 56.0%（前回: 24.7 / 35.3 / 40.0）。各 300 試合。**
  この数字はマージ時に `fleeTurnCost` 込みの master を取り込んだうえで測り直したもの。
  作業中は 24 試合 ×2 シードで 39.6 / 43.8 / 52.1 と読んでおり「3v3 だけ超過」と
  結論しかけたが、300 試合では **3 構成すべてが目標帯（35〜50%）の上**だった。
  超過幅は 1v1 +3 / 2v2 +5 / 3v3 +6 で、人数が増えるほど大きい。
  初補足までの時間も 1v1 で 49.4 → 64.0 秒と伸びており、鬼が見つけられていない。
  逃げる側を弱めて帳尻を合わせる話ではないので、鬼側の課題として issue #11 に立てた。


## 2026-08-10 逃走中の硬直を解消

- 変更: `fleeDirection` が「どの向きにも走れる幅が無い」と判断したときに
  移動入力を空で返していたのをやめ、一番遠くまで進めて脅威から離れる向きへ押し込むようにした。
  速度が出ない状態が続いたら乗り越えも試みる。
- 理由: `_probe` で、3v3 の追跡フェーズのうち 4.7% のティックで逃走者の移動入力が
  ゼロになっており、その大半が箱の近くだった。最長で 32.3 秒その場に固まっていた。
  1v1 では硬直は 0% で、こちらは純粋に追いつかれている（原因が別）。
- 勝率: 1v1 12.5% / 2v2 25.0% / 3v3 29.2%（前回: 12.5 / 33.3 / 16.7）
  3v3 の平均生存人数は 0.25 → 0.46。硬直ティックの割合は 4.7% → 0%。

## 2026-08-10 遊び心地の調整

- 変更: 移動速度を 6.6 → 9.4（鬼 8.8）に引き上げ、アリーナを 36x36 → 44x44 に拡大。
  ジャンプに踏み切りの推進力を追加、ジャンプ台を設置。逃げる側に煙幕（2 回）を追加。

- 理由:
  - 速度を上げただけでは逃げ側勝率が落ちた（AI の先読み距離が旧速度のままで壁に突っ込んでいた）。

  - トレースで、拠点が隅（壁まで 1.9 m）に選ばれ、追跡開始 1.1 秒で発見されて
    逃げ道が無いまま捕獲される試合を確認。「中央から遠いほど良い」の評価が隅を選ばせていた。
- 勝率: 1v1 12.5% / 2v2 33.3% / 3v3 16.7%（前回: 12.5 / 20.8 / 25.0）
